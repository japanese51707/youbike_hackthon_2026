# 條件參數分類與設定群組

> 定義「有哪些參數、參數怎麼來、影響單站還是全體」。
> 最後更新：2026-08-31

---

## 核心分類軸：參數的「來源方式」

你提出的關鍵洞察：每個參數要先分清楚它是怎麼產生的，因為方法完全不同。

| 來源方式 | 意義 | 舉例 |
|---------|------|------|
| **A. 外部資源批次換算** | 從外部資料（地圖、地形、POI）自動換算，一次套用到 1583 站 | 地形、區域類型 |
| **B. 全體共用係數** | 全市共用一個係數，不分站 | 天氣影響係數、假日係數 |
| **C. 單站歷史學習** | 從該站自己的歷史資料學出來 | 潮汐特性、基礎流量 |
| **D. 事件動態計算** | 依事件輸入即時換算，影響方圓內的站 | 活動影響 |
| **E. 人工即時覆寫** | 緊急時人工介入（③層） | 緊急優先級 |

## 設定群組總覽

### 群組 1：地理靜態參數（來源 A — 外部批次換算）

**特性：跟單站的地理位置有關，但用外部資源一次算好，不用一站站設定。**

| 參數 | 來源資料 | 換算方式 | 影響 |
|------|---------|---------|------|
| `terrain`（地形） | 高程 API / 等高線圖 | 站點經緯度 → 查高程 → **7 種精細分類**（坡度×坡向，見下方團隊定義第1點） | 坡上易空、坡下易滿 |
| `area_type`（區域類型） | Google Places / OSM POI | 站點周邊 500m 內 POI 統計 → 判定主類型 | 住宅早流出、商業日間需求高 |
| `nearby_stations`（鄰近站） | 站點經緯度 | 計算 500m 內的站 → 站群 | 站群緩衝 |
| `capacity_class`（容量級距） | 站點總車柱數 | 直接分級 | 小站容錯低 |

> ✅ 這群組的實作重點：**寫一支批次腳本，讀外部資源，一次算完 1583 站的參數，存進設定。** 不是手動一站站填。

### 群組 2：時間週期參數（來源 C — 單站歷史學習）

**特性：每站自己的歷史規律，從資料學出來。**

| 參數 | 來源 | 說明 |
|------|------|------|
| `base_flow_by_hour`（時段基礎流量） | 該站歷史 | 每站 × 星期 × 時段的基礎借還量 |
| `tidal_direction`（潮汐方向） | 該站歷史 | 早流出 or 早流入 |
| `outflow_rate` / `inflow_rate`（流出/流入率） | 該站歷史 | 借車/還車速率 |
| `target_level`（動態目標水位） | 該站歷史 | 每時段的理想借用率 |

> ✅ 這群組由 ② AI 每日最適化持續調整。

### 群組 3：外部環境係數（來源 B — 全體共用）

**特性：全市共用，不分站（或分大區）。**

| 參數 | 來源 | 說明 |
|------|------|------|
| `weather_factor`（天氣係數） | 氣象 API | 晴/陰/雨/豪雨/颱風（sunny/cloudy/rain/heavy_rain/typhoon）各一係數，全市共用 |
| `holiday_factor`（假日係數） | 行事曆 | 平日/假日/連假係數 |
| `season_factor`（季節/寒暑假係數） | 行事曆 | 學期 vs 假期 |

> ✅ 這群組是「乘數」，套在基礎流量上。但注意（依審查決策 D2）：天氣×尖峰不是單純相乘，正式模型會把這些當特徵餵進 LightGBM 學交互作用。此處的「係數」是可解釋 baseline 用。

### 群組 4：事件動態參數（來源 D — 事件輸入即時換算）

**特性：依輸入的活動資訊，動態計算影響哪些站、影響多少。**

輸入：
```json
{
  "event_name": "跨年演唱會",
  "location": {"lat": 25.04, "lng": 121.51},
  "expected_attendance": 50000,
  "event_type": "concert",
  "start_time": "2026-12-31T20:00:00",
  "end_time": "2027-01-01T01:00:00"
}
```

換算邏輯：
```
影響半徑 = f(人數, 性質)
  例：5萬人演唱會 → 影響半徑 2km

對每個站：
  距離活動地 < 影響半徑 → 計算影響度
  影響度 = f(距離, 人數) — 越近影響越大
  → 暫時調高該站的需求參數（活動前後時段）
```

> ✅ 這群組不改基礎參數，是「臨時疊加」，活動結束後消失（類似 ③ 層的臨時性，但是系統自動算的，不是人工）。
> 而且結合異常標籤：如果過去有類似規模活動的歷史，可調出來估算。

### 群組 5：即時人工覆寫（來源 E — ③ 層）

見 `model_architecture.md` 的第 ③ 層。緊急時人工拉高優先級，臨時性。

# 因子的兩種角色（重要觀念）

因子扮演兩種不同角色，模型建置者必須分清楚：

## 角色 A：預測因子 — 決定「未來供需會怎樣」
餵給預測模型，算出「未來這站會有幾台車」。

## 角色 B：緊急度因子 — 決定「現在有多急」
在預測結果的基礎上，算出緊急度分數。

**關鍵流程：**
```
預測因子 → 預測模型 → 預測未來供需（含區間） → 加緊急度因子 → 緊急度分數 0~100 → 排任務
```
天氣不直接產生緊急度，而是：天氣影響預測（雨天需求降）→ 預測影響緊急度。

# 完整因子清單（依角色分類）

## 預測因子（餵進預測模型）

| 因子 | 群組 | 來源方式 | 說明 |
|------|------|---------|------|
| 星期（一~日） | 2 時間 | 內建 | 平日/假日 pattern 不同 |
| 24 小時時段 | 2 時間 | 內建 | 每半小時 pattern |
| 近期 lag（前1~3時段） | 2 時間 | 單站歷史 | ★預測最強特徵（實測 importance 第一） |
| 前一時段淨流量方向 | 2 時間 | 單站歷史 | 當下正在流出/流入 |
| 潮汐特性 | 2 時間 | 單站歷史 | 早流出 or 早流入 |
| 天氣 | 3 環境 | 全體共用 | 晴/陰/雨/豪雨/颱風 |
| 假日/連假 | 3 環境 | 全體共用 | 連假方向與平日相反 |
| 寒暑假/季節 | 3 環境 | 全體共用 | 學區站差異大 |
| 地形 | 1 地理 | 外部批次 | 坡上易空、坡下易滿 |
| 區域類型 | 1 地理 | 外部批次 | 住宅/商業/學區/捷運/休閒 |
| 容量級距 | 1 地理 | 外部批次 | 影響基礎水位 |
| 活動 | 4 事件 | 事件換算 | 影響方圓內站點 |

## 緊急度因子（算緊急度分數）

| 因子 | 說明 | 角色 |
|------|------|------|
| ★預測到達時存量 | 調度員到達時剩幾台（前瞻窗口核心） | 主要 |
| 空/滿門檻距離 | 離空站/滿站還有多少緩衝 | 主要 |
| 站群緩衝（鄰近站） | 隔壁 300m 有車 → 降急；隔壁也空 → 升急 | 修正 |
| 影響人數/站點重要性 | 高流量站（捷運）比冷門站更急 | 加權 |
| 調度到達時間 | 離調度車越遠 → 越要提早 → 越急 | 加權 |
| 容量級距 | 小站容錯低 → 同樣缺車更急 | 修正 |
| 時效敏感度 | 持續惡化 vs 尖峰過了自然緩解 | 修正 |
| 即時人工覆寫（③層） | 緊急直接拉滿 100 | 覆寫 |

# 緊急度分數計算（0~100）

```
【第一步：預測】
  預測因子 → LightGBM → 預測「調度員到達時」的可借車數（含區間下界）

【第二步：算緊急度】
  緊急度分數 = 加權組合：
    • 預測到達時存量 vs 空/滿門檻    ← 主要（越接近 0 越急）
    • 站群緩衝                        ← 修正（隔壁有車就降急）
    • 影響人數（站點重要性）          ← 加權（大站更急）
    • 調度到達時間                    ← 加權（越遠越要提早）
    • 容量級距                        ← 修正（小站容錯低）
    • 時效敏感度                      ← 修正
    • 即時人工覆寫                    ← 覆寫（拉滿 100）
  = 緊急度分數 0~100

【第三步：排任務】
  按緊急度分數排序 → 結合調度員位置 → 產生任務
```

各因子的權重 → 放 `config.yaml`（可調），初始值待團隊定義。

# 團隊定義結果（已討論）

## 1. 地形分類門檻（有文獻依據，採精細 7 分類）

參考自行車坡度研究，坡度分級 × 坡向 = **7 種精細分類**（與 api_contract.md 2.1 一致）：

| terrain 值 | 坡度 | 坡向 | 騎乘體感 / 影響 |
|-----------|------|------|----------------|
| `flat` | 0~3% | — | 幾乎無感，中性 |
| `gentle_up` | 3~5% | 上坡 | 舒適上限，略易空 |
| `gentle_down` | 3~5% | 下坡 | 略易滿 |
| `moderate_up` | 5~8% | 上坡 | 開始吃力，易空 |
| `moderate_down` | 5~8% | 下坡 | 易滿 |
| `steep_up` | >8% | 上坡 | 多數人不願意，很易空 |
| `steep_down` | >8% | 下坡 | 很易滿 |

**坡向原則：**
- 上坡站（站點在坡上）→ 使用者傾向「騎下坡離開」→ **容易空站**
- 下坡站（站點在坡下）→ 使用者傾向「騎下坡抵達」→ **容易滿站**

實作：用站點經緯度查高程 API，計算站點相對周邊 500m 的坡度與坡向，換算成上述 7 種 `terrain` 之一。**採精細分類（越細越能反映真實騎乘行為）。**

> 文獻依據：休閒騎士舒適坡度約 4~5%、健壯騎士上限約 8%（Bicycling）；一般騎士搭配變速勉強可應付 12~15%（Roadman Cycling）。內容已改寫以符合授權規範。

## 2. 區域類型判定（政府地段 + POI）

雙來源判定：
1. **政府都市計畫用地分區**：查該地段的法定用途（住宅區/商業區/工業區等）
2. **周邊 POI 加權**（500m 內）：
   - 觀光熱門景點 → 高人流，假日爆量
   - 運動中心 / 河濱 → 休閒型，天氣敏感
   - 學校 → 學區型，寒暑假差異大
   - 捷運/轉運站 → 通勤型，尖峰潮汐強
   - 商圈/百貨 → 商業型，日間需求高
   - 醫院、市場、公家機關 → 各有 pattern

實作：政府分區當底，POI 統計當修正，綜合判定 `area_type`。

> 文獻依據：約 80% 共享單車使用來自站點 300m 內；商業區使用量最高、稀疏住宅區最低。內容已改寫以符合授權規範。

## 3. 係數初始值 → 延後

各係數初始值先不定死。**先確定有哪些參數（已完成），再由 B 工程師針對模組逐項優化。**

## 4. 事件影響半徑 + 影響程度（結合步行意願 + 供需比）

### 影響半徑：基於「人願意走多遠」，不是活動規模

半徑的上限由「人願意步行的距離」決定，**最遠 1~2 公里**，不會因為活動大就無限擴大（沒人會為了借車走 3 公里）。

```
基礎半徑 = 0.5 km（借車集水區，80% 使用集中在 300~500m）
最大半徑 = 2.0 km（上限，再遠人不會走）
```

### 影響程度：活動人數 vs 半徑內站點總容納量的比例

半徑決定「影響哪些站」，人數決定「影響多嚴重」。用**供需比**量化：

```
影響比 = 預估活動人數 / 半徑內所有站點的總車柱數

例：1 萬人湧入，周圍站點總容量 500 個車柱 → 影響比 = 20
   代表嚴重供需失衡，該區站點需求參數要大幅上調

例：500 人小活動，周圍總容量 500 → 影響比 = 1
   代表供需大致平衡，影響輕微
```

- 影響比越高 → 該區越可能瞬間被借空/還爆 → 需求參數上調越多
- 單站影響度 = 影響比 × 距離衰減（離活動地越近影響越大）
- 影響比設上限（如 10）避免極端值爆表

> 文獻依據：300m 步行門檻覆蓋 94% 加權需求；借車集水區約 250~500m。內容已改寫以符合授權規範。

## 5. 緊急度權重初始值 → 延後（同第 3 點）

先確定因子，權重由 B 工程師優化。

## 6. 站點重要性/影響人數 → 歷史數據計算

用該站的**歷史日均借還量**量化重要性：
- 高借還量站（如捷運站）= 影響人數多 = 同樣缺車更緊急
- 冷門站 = 影響人數少 = 相對不急

## 7. 調度到達時間 = 兩項加總（不需定義調度基地）

```
調度到達時間 = 目前任務需完成的預估時間
             + 調度員「當前位置」→ 目標站的交通時間（依距離換算）
```

- **起點用調度員當前位置**（GPS 即時擷取，或手動輸入），**不需要定義固定的調度基地**
- 若調度員正在執行任務 → 先加上「當前任務完成的預估時間」，再算從那個點出發的交通時間

這個時間就是「前瞻窗口」——預測模型要預測的是「這個時間之後」的存量。

## 8. 時效敏感度判定 = 看是否趨近緊急

判斷預測趨勢是否**持續往緊急度更高的方向移動**：
- 若預測顯示存量持續下降、越來越接近空站 → 時效敏感度高（越晚處理越糟）
- 若預測顯示尖峰過後會自然緩解 → 時效敏感度低（可稍後處理）
