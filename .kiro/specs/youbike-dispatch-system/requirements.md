## 1. 專案背景

### 1.1 題目來源
新北市交通局黑客松，主題：**解決 YouBike 站點空滿率問題、提升調度反應速度、增加預判能力**。

題目明確要求（原文重點）：
- 具備**即時數據視覺化**與 AI 預測模型
- 易於理解、可顯示即時租賃站車輛情形之視覺化模板
- AI 預測或即時反映站點租借需求，優化調度模式
- **現行機關系統無警示通知功能**（← 我們的差異化切入點）

### 1.2 現狀痛點
- 調度員發現空/滿站時往往已經來不及（被動反應）
- 沒有系統化的預判工具，依賴個人經驗
- 尖峰時間多站同時出問題，不知道優先處理哪站
- 調度路線靠感覺規劃
- 現行系統沒有主動警示

### 1.3 我們的目標
建立一套「**預測 + 規則引擎 + 調度管理 + 即時視覺化 + 警示**」系統，讓調度從「事後補救」變成「事前預防」。

## 2. 使用者角色

| 角色 | 誰 | 用系統做什麼 |
|------|-----|------------|
| **調度中心主管（調派員）** | 值班管理者 | 看儀表板、確認調度建議、監控 KPI、處理警示、緊急覆寫 |
| **調度員（外勤）** | 開調度車的人 | 接收任務佇列、導航、執行搬運、回報狀態 |
| **長官** | 主管機關長官 | 看全域調度總覽（宏觀成效、人力、站點壓力） |
| **系統管理者/維護人員** | 技術維護 | 每日確認 AI 最適化、調整參數、監控模型、管理資料 |

> 一般使用者（騎車的人）不直接使用此系統。使用者引導列為未來規劃（P2）。

## 3. 功能需求

### FR-1：預測模型（LightGBM，本機運行，非生成式 AI）
- **這不是 ChatGPT 那種 AI** — 是用歷史資料訓練的數學模型（LightGBM），存在本機，推論免費、毫秒級
- 訓練一次產出「方程式」檔案，上線後每次用這個方程式算，不呼叫外部 API、不花錢
- 預測每站未來某時刻（動態 horizon = 調度到達時間）的可借車數
- 輸出**不確定區間**（非僅點估計），供規則引擎用下界觸發
- 單一統一模型 + 每站條件參數（非 1583 個模型，見 model_architecture.md）
- 詳見 `docs/模型怎麼跑的（給隊友）.md`

### FR-2：規則引擎
- 根據預測區間下界判斷是否觸發調度
- 產出調度建議清單（站點、動作、數量、優先級、觸發原因）
- 觸發原因為人可讀中文
- 所有閾值/權重從外部設定檔讀取

### FR-3：後台儀表板（調派員視角）
- 地圖即時站點狀態（顏色分級）
- 各站即時水位 vs 動態目標水位
- 調度建議清單，支援人工確認（閘門）
- KPI 看板

### FR-4：調度員任務介面
- 任務佇列（有前後順序的排程）
- 每個停靠點獨立任務框，逐站完成回報
- 路線圖 + Google Maps 導航連結
- 預估交通時間、工時、總時間、油錢
- 回報完成/故障/異常 → 系統重算派發下一個

### FR-5：模擬重放（成效驗證）
- 還原「無人工干預」的自然曲線
- 模擬系統決策後的車輛演變
- 輸出 Before/After 對比

### FR-6：調度介入辨識
- 從歷史辨識人工調度痕跡（MAD + 時段方向 + 鄰近站同時性）
- 輸出信心分數（非二元標籤）
- 用途：清洗訓練資料、成效驗證基準

### FR-7：模型參數三層架構（見 model_architecture.md）
- ① 規則化基礎參數（人設定，依站點靜態條件）
- ② AI 每日最適化（回看預設 3 天，可調；排除異常日；幅度上限；版本回溯；人工確認）
- ③ 即時人工覆寫（緊急拉高優先級；任務完成或時效恢復；不影響未來）

### FR-8：警示通知（★題目明確要求，現行系統沒有）
- 系統每次收到最新站點狀況 → 自動跑警示確認
- 三級警示（info/warning/critical）
- Demo：前端即時顯示
- 預留 API：機關可訂閱 webhook，系統主動 POST 警示

### FR-9：即時視覺化（★題目明確要求）
- 即時熱點地圖
- 多維度切換（區域類型/地形/行政區）
- 時間軸播放（看整區熱點流動，讀預存歷史）
- 歷史資料分頁（近一週）

### FR-10：調度員排程與動態轉派
- 每位調度員一個任務佇列（排程）
- 一般任務：綁定調度員，不可轉派
- 緊急任務：未執行前可轉派給更適合的調度員，並通知原調度員
- 位置導向分配（依當前位置 + 最優先 + 急迫度）

### FR-11：異常標記
- 歷史資料標記異常（調度介入/活動/假日/寒暑假/極端天氣/站點改造/資料錯誤）
- 用途一：歷史回顧時一眼看懂當時發生什麼
- 用途二：模型排除異常避免學壞；保留供同類情境預估

### FR-12：資料保留策略
- 熱資料（近 1~2 週）：即時推論
- 溫資料（近 1~3 個月）：重訓練、趨勢比對
- 冷資料（3 個月以上）：歸檔或刪除
- 理由：模型參考近期資料才準確

### FR-13：站點動態管理（新增/刪除站別）
站點數量會變動（目前 1,583，未來可能增減），系統要能在畫面上操作：

- **新增站別**：
  - 後台可在地圖上新增站點（輸入位置、容量等）
  - 新站**冷啟動**：沒有歷史資料 → 自動套用「當時的模型設計」+ 鄰近類似站的參數當起始值
  - 新站的地理參數（terrain、area_type、鄰近站）自動批次換算（同群組 1 邏輯）
- **刪除站別**：
  - 後台可停用/刪除站點
- **動態連動**（關鍵）：
  - 新增或刪除一站，會改變**鄰近站的站群組成** → 需重算受影響站的 `nearby_stations` 和站群緩衝
  - 這是動態的：不是只改自己，是連帶更新方圓內相關站的參數
- 對應 model_architecture.md 的冷啟動與站點改造機制

## 4. 非功能需求

### NFR-1：可解釋性
- AI 只做估計，規則引擎做決策
- 決策可追溯（為什麼觸發、依據什麼數字）
- 預測錯了不會導致錯誤決策（區間下界觸發）

### NFR-2：人在迴圈
- 調度指令走「預覽 → 人工確認 → 執行 → 驗證」
- 系統不自動執行真實世界動作

### NFR-3：可維護與交接
- 閾值/權重外部化（YAML）
- 程式碼模組化，清楚介面邊界（見 steering: development_principles.md）
- 文件齊全，黑客松後交通局能接手

### NFR-4：低成本
- **資料層 Serverless**（S3 + Athena），無持續費用
- **運算層** 用 EC2 Free Tier（後端 API + 模型推論需要常駐服務，非 Serverless）
- 研發期每月 < NT$100
- 註：資料層無伺服器、運算層 EC2 是刻意取捨（後端需常駐），非矛盾。記於 ADR。

### NFR-5：失敗可見
- 不靜默失敗
- 任務有明確狀態（pending/in_progress/completed/retryable/manual_required）

### NFR-6：可稽核
- 即時覆寫、任務轉派、AI 最適化都留稽核痕跡
- 用於工作分析、流動修正、未來稽核

### NFR-7：資料源可抽換
- 透過 data_source 介面切換（歷史 Parquet / TDX 即時 / Mock）
- 現場 Demo 換資料源只改設定檔

### NFR-8：安全性
- **存取控制**：關鍵動作需權限
  - 只有調派員/主管能按「確認派發」（閘門）與「緊急覆寫」
  - 只有維護人員能確認每日 AI 最適化、調整參數
  - 調度員只能回報自己的任務
- **機關 webhook 驗證**：`/alerts/subscribe` 的 callback 需驗證來源（token/簽章），避免任意端點被推資料
- **不暴露內部資料**：前端只透過 API 存取，不直接連資料庫（見 api_contract 架構觀念）
- **輸入驗證**：活動輸入、參數調整等外部輸入需驗證，避免異常值污染模型
- **稽核**：關鍵動作留痕（誰、何時、做了什麼）

### NFR-9：效能（依使用情境分級）
效能要求不是一刀切，依「誰在用、需不需要即時」分級：

| 情境 | 即時性要求 | 範圍 | 目標 |
|------|-----------|------|------|
| **後台派遣作業**（調派員） | 不需即時 | 全市 | 收資料→處理→顯示，數秒內完成即可 |
| **現場調度員任務更新** | **即時** | **僅該調度員工作範圍內**（非全市） | 任務更新後 1~2 秒內反映 |
| **時間軸播放**（後台） | 不需即時 | 讀預存歷史 | 拖曳流暢、不卡頓即可 |
| **即時熱點地圖**（後台監控） | 準即時 | 全市 | 隨資料源更新（1~5分）刷新 |

設計要點：
- 現場調度員的即時更新**只推該工作範圍內的站點**，不推全市資料 → 大幅降低頻寬與運算
- 後台的全市處理走批次/準即時即可，不強求毫秒級
- 時間軸讀預存歷史，不即時計算

### NFR-10：錯誤處理與降級策略
當即時資料源（TDX API）失效時，系統要能降級運作而非崩潰：

1. **第一層降級**：改用**最後一次成功取得的資料**（並標記為「資料過期」，前端顯示提醒）
2. **第二層降級**（API 持續掛掉時啟用）：改用**歷史同星期同時段的資料**做回顧判斷
   - 例：週一早上 8 點 API 掛了 → 用過去幾週「週一 8 點」的歷史平均當估計
3. 降級狀態必須明確標示（呼應 NFR-5 失敗可見），不能讓使用者誤以為是即時真實資料
4. API 恢復後自動切回即時

## 6. 影響因子模型

> 完整定義見 **parameter_groups.md**。此處為摘要。

因子分**兩種角色**：
- **預測因子**（餵進模型算「未來供需」）：星期、24小時、近期lag、潮汐、天氣、假日、寒暑假、地形、區域類型、容量、活動
- **緊急度因子**（算「現在多急」）：預測到達時存量、站群緩衝、影響人數、調度到達時間、容量、時效敏感度、即時覆寫

**五大參數群組**（依來源方式分類）：
1. 地理靜態（外部批次換算：地形、區域、鄰近站、容量）
2. 時間週期（單站歷史學習：基礎流量、潮汐、流出入率、目標水位）
3. 外部環境（全體共用：天氣、假日、季節係數）
4. 事件動態（事件輸入換算：活動影響方圓）
5. 即時覆寫（人工：緊急優先級）

## 7. 設計原則（已定案）

1. **AI 只做估計，規則引擎做決策，人在迴圈中確認**
2. **失敗時必須看得到**（不靜默失敗）
3. **預覽 → 確認 → 執行 → 驗證**（閘門鏈）
4. **預測可失手，判斷不跟著失手**（分層互補）
5. **控制平面 / 執行平面分離**
6. **所有閾值外部化**
7. **模組化：一個檔案一件事，改一處不毀他處**（見 steering）

## 9. 成效驗證方式

| 驗證手段 | 指標 | 目標 | 現況 |
|---------|------|------|------|
| 模擬重放 Before/After | 尖峰空站率 | 比現狀降低 | 已驗證可降低 |
| 預測模型 MAE | 台數誤差 | < 2 台 | ✅ 1.51 |
| 區間覆蓋率 | 落在區間內比例 | ~80% | 🔶 78.7%（接近，B 可再校準） |
| 緊急度校準 | 當下緊急度吻合歷史後續 | 貼近 | B 校準中 |
| 規則引擎輸出 | 觸發原因可讀性 | 人話 | ✅ |
| Demo 流暢度 | 問題發現→調度完成 | < 3 分鐘展示 | — |

## 10. 不做的東西（明確排除 — 展現取捨判斷力）

| 項目 | 原因 |
|------|------|
| VRP 路線最佳化精確求解 | 博士論文等級，用 heuristic 夠了 |
| 使用者引導 App 推播 | 需求面調控，未來規劃 |

| 全真 App（上架） | 時間不夠，做可互動 Web Demo |
