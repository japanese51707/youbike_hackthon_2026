# 模型參數三層架構（核心設計）

> 這是整個系統最核心的設計決策。定義「預測模型」如何運作。
> 最後更新：2026-08-31

---

## 核心理念：單一模型 + 分層參數

### 為什麼不是 1583 個模型

新北市目前有 1,583 個租賃站（題目文字約 1,576，以實際資料 1,583 為準），每站情況不同。但**不該建立 1583 個獨立模型**——那不可維護、不可解釋、無法統一升級。

正確做法：**一個統一模型 + 每站一組「條件參數」**。

```
┌─────────────────────────────────────────────────────┐
│         統一基礎模型（全市共用一個公式/模型）          │
│  預測值 = Model(站點條件參數, 時間, 外部因子)          │
│  站點差異 → 靠不同的「條件參數」，不是不同的模型        │
└──────────────────────┬──────────────────────────────┘
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
  站點A 參數組      站點B 參數組      站點C 參數組
  (地形/學區/       (商業區/          (住宅區/
   潮汐特性...)      平地...)          坡地...)

  1 個模型，N 組參數。改模型 = 全市一起升級。
```

### 這個設計對「站點動態增減」的天然優勢

因為只有一個模型、參數是外掛的，新增站別時**不需要訓練新模型**：
- 新站冷啟動 → 直接套用當前模型 + 鄰近類似站的參數當起始值
- 累積資料後，② AI 每日最適化會逐步校準它的專屬參數
- 刪除站別 → 移除該站參數組即可，模型不受影響

## 三層參數來源

參數有三種修改方式，優先順序由上而下覆寫：

```
③ 即時人工調整（最高，臨時）
        ↓ 覆寫當下
② AI 每日最適化參數
        ↓ 覆寫基準
① 規則化基礎參數（最底層預設）
```

平常用 ①，AI 每天用 ② 微調，緊急時 ③ 臨時蓋過；③ 事後消失，回到 ②。

---

## ① 規則化基礎參數

| 項目 | 內容 |
|------|------|
| 誰設定 | 人（建置時） |
| 依據 | 站點的靜態條件：地形、區域類型（住宅/商業/學區）、容量、歷史潮汐特性 |
| 頻率 | 建置時一次，之後很少動 |
| 持久性 | 持久，存在設定檔 |
| 角色 | 所有預測的基準線 |

---

## ② AI 每日最適化

| 項目 | 內容 |
|------|------|
| 誰執行 | AI（自動排程） |
| 頻率 | **每天一次**（回看天數預設 3 天，可在後台調整） |
| 調整對象 | **條件參數**，不是模型本身（微調概念，不動整體） |
| 邏輯 | 檢視前 N 天實際 vs 預測，微調每站的條件參數 |

### 必要機制（已確認）

1. **異常日排除 + 標籤化**
   - 異常資料（颱風、大型活動）打上標籤
   - 最適化時排除有異常標籤的時段，避免把模型教壞
   - **同時，異常標籤資料保留下來**：未來遇到同類情境（如颱風天），可調出歷史颱風資料估算該站表現 → 反而變成「特殊情境預估」的依據

2. **調整幅度上限**
   - 單次調整幅度有上限（例如 ±10%）
   - 一點一點慢慢修正，避免頻繁暴衝震盪

3. **版本控制 + 回溯**
   - 每次最適化後，舊參數留存一份
   - 調整時必須備註調整原因
   - 可一鍵回到前一版

4. **人工確認機制**
   - AI 算出新參數後，不直接套用
   - 產出**格式化的調整摘要**給後端維護人員：
     - 大致調整了什麼
     - 哪些站/參數調整幅度較大（重點標示）
     - 調整原因
   - 維護人員每日確認後才更新

### 待團隊定義
- [ ] 具體的「檢視條件」：什麼情況要調、調多少、依據什麼指標（MAE？偏差方向？）

## ③ 即時人工調整（緊急覆寫）

| 項目 | 內容 |
|------|------|
| 誰執行 | 調度員 / 後台主管 |
| 時機 | 臨時緊急狀況 |
| 效果 | 該站排到**最優先層級** |
| 影響範圍 | **僅當下**，不影響模型參數、不影響未來 |
| 恢復時機 | 任務完成 OR 設定時效到期，先到先觸發 |

### 覆寫如何生效（C-02，重要 — 定死實作位置）

覆寫**不進 `calc_urgency()`**。原因：`urgency` 在無狀態的執行平面（B），覆寫是有狀態的控制平面動作（A 的 `override_service`），兩者不可混。

實作方式：**覆寫在 `dispatcher` 排序時當「最前綴」**——
- `calc_urgency()` 照常算原始緊急度（不知道覆寫存在）
- `dispatcher` 排序時，先把「有生效中覆寫」的站排在所有站之前，再按原始緊急度排其餘
- 等於「覆寫站 > 任何非覆寫站」，但不竄改 urgency 分數本身
- 覆寫恢復後，dispatcher 下一輪自然不再前綴它

這樣決策邏輯只在 dispatcher 一處，不會散到 urgency。

### 必要機制（已確認）

1. **恢復雙條件**
   - 任務完成 → 恢復正常
   - 設定時效到期（例如 2 小時）→ 自動恢復
   - 避免手動拉高後沒人處理，那站永遠掛最優先

2. **多緊急的排序（結合調度員位置）**
   - 同時多站被拉到最優先時，**以調度員位置為核心做最適化分配**
   - 調度員完成一個任務、要接下一個時：
     - 系統看他當前位置 → 最近的最優先站先安排
     - 若他的工作區內有 2 個最優先站 → 兩站都排給他
     - 站間處理順序 → 綜合「按下的時間」+「離空/滿的急迫度」
   - 多位調度員同時出動，各自依位置分配

3. **稽核留痕**
   - 記錄：誰、何時、對哪站、做了什麼緊急調整、任務花費時間
   - 用途：
     - 分析調度員實際工作狀況
     - 後續調度流動修正
     - 未來稽核
     - 反推「常被手動介入的站」→ 檢討基礎參數是否該調

4. **任務歸屬與動態轉派（彈性調度）**

   **一般任務（normal）：綁定，不可轉派**
   - 一般任務一旦指派給某調度員，就固定是他的責任
   - 系統不能中途把它指派給別人
   - 前端每個停靠點是獨立任務框，逐站完成、逐站回報

   **緊急任務（emergency）：未執行前可轉派**
   - 情境：調度員 X 手上有 2 個緊急任務，正在處理第 1 個，第 2 個還沒做
   - 此時有另一位調度員 Y 空出來、且更接近第 2 個任務
   - 系統應：
     - 持續偵測「已接緊急任務但**尚未開始執行**」的任務
     - 若出現更適合的調度員（更近/更空） → 把該未執行緊急任務轉派給 Y
     - **通知 X：此任務已由 Y 接手，你不用處理了**
     - X 的任務清單即時更新，移除該任務
   - **一旦緊急任務開始執行 → 鎖定，不再轉派**
   - 系統排程時，會把「所有未完成的緊急任務」納入計算（不限於原指派對象）
   - 目的：讓調度更有彈性，不會因為某人先接了就卡住
   - 轉派要留稽核痕跡（原派給誰、轉給誰、為什麼）

## 站點動態管理（新增/刪除站別）

站點數量會變動，系統設計要能動態處理。因為是「單一模型 + 外掛參數」架構，這件事變得單純。

### 新增站別（冷啟動）
1. 後台在地圖上新增站點（位置、容量）
2. **地理參數自動批次換算**：terrain、area_type、鄰近站（同群組 1 邏輯，用經緯度查高程/POI）
3. **冷啟動參數**：沒有歷史 → 套用「當前模型」+ 鄰近類似站（同 area_type、同 terrain）的參數當起始值
4. 累積資料後，② AI 每日最適化逐步校準成專屬參數

### 刪除站別
- 移除該站參數組，模型本身不受影響

### 動態連動（關鍵）
新增或刪除一站，會改變**鄰近站的站群組成**：
- 需重算方圓內受影響站的 `nearby_stations` 與站群緩衝
- 這是連動的：不只改自己，連帶更新相關站
- 觸發時機：站點增減時自動觸發一次鄰近關係重算（不需全市重算，只算受影響範圍）

## 後台維護畫面需求（給 C / 維護人員）

1. **每日最適化確認畫面**
   - 顯示 AI 的調整摘要（格式化）
   - 標示調整幅度大的站
   - 一鍵確認更新 / 退回

2. **站點參數檢視畫面**
   - 點擊任一站 → 清楚顯示該站當前參數設定
   - 每個參數背後代表的條件是什麼（例如「流出率參數 1.3 ← 因為此站為捷運轉乘 + 學區」）
   - 顯示參數來源（① 基礎 / ② AI最適化 / ③ 即時覆寫中）

3. **回看天數設定**
   - 維護人員可調整 AI 最適化的回看天數（預設 3 天）

## 三層對照總表

| 層 | 名稱 | 誰改 | 頻率 | 持久性 | 關鍵機制 |
|----|------|------|------|--------|---------|
| ① | 規則化基礎參數 | 人 | 建置時 | 持久 | 依站點靜態條件 |
| ② | AI 每日最適化 | AI | 每天（天數可調） | 持久、可回溯 | 排除異常日、幅度上限、版本控制、人工確認 |
| ③ | 即時人工調整 | 調度員/主管 | 緊急時 | 臨時 | 完成或時效恢復、位置導向分配、稽核留痕 |

---

## 對應第二大腦的設計原則

- ① 規則化參數 → 確定性、可解釋（規則引擎的底）
- ② AI 最適化 → 執行平面的自適應工作 + 人在迴圈確認
- ③ 即時覆寫 → 控制平面的人工介入，且「臨時覆寫不污染長期狀態」
- 稽核留痕 → 可稽核 Journal
- 版本控制回溯 → 可續跑 / 可回溯
