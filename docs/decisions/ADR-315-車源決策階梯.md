# ADR-315：車源決策階梯（就近取車優先，總部載滿為最後手段）

## 背景與問題

以站為起點組單時（ADR-119 入口 b），系統會為緊急補車站規劃一趟派工。原本的規劃可能直接
安排「補車」動作，卻沒有先確認車從哪裡來——若調度車車上沒有足夠的車，光排補車是補不了的
（沒有車源）。owner 指出這個缺口：規劃必須先考慮鄰近站有沒有可以先取車的地方，讓緊急站
真的有車可補。

同時 owner 希望這是一個有優先序的決策，而非一律「從總部載滿車出發」——能就近湊到車源就
不動用總部，總部載滿是成本較高、應留作最後手段的選項（為後續全自動化流程鋪路）。

不決策的後果：組出「無車源卻排補車」的無效派工單，或一律動用總部載滿車，浪費資源。

## 決策

以站為起點組單時，補車的**車源**依下列**階梯**決定（`dispatch_builder.build_from_station`
複用 `dispatcher._pack_supply_aware_trip`）：

1. **車上既有載量**（`onboard`）：先用車上已有的車補。
2. **同區取車站就近取**：同一行政區內有「取車」需求的站，順路併入本趟先取後補（在主挑站池內）。
3. **同區湊不足 → 跨區取一站補足車源**：同區的車上載量＋取車量仍不足以補到需求時，允許從
   跨區的取車站拉入一站補足（同區優先、跨區次之，見 ADR-316）。
4. **都湊不到 → 總部載滿車出發並警示**：補車需求量仍超過（車上載量＋趟內取車站可取量）時，
   標記 `needs_depot_refill=True` 與 `supply_shortfall`（缺口台數），並在草稿附醒目提示
   「附近無足夠車源可取，需由總部載滿車出發調度」；此時**執行車與人員都優先派總部待命資源**
   （總站待命車 `is_depot` + 總站待命人力 `depot_standby`），而非當地閒置車人。

判斷缺口的口徑：`需求 = Σ 補車站 quantity`；`供給 = onboard + Σ 趟內取車站 quantity`；
`需求 > 供給` 即需總部載滿（`needs_depot`／`needs_depot_refill`）。

## 理由與判準

- **正確性**：先確保車源再排補車，避免無效派工單（「補車有了卻沒車可補」）。
- **成本 / 資源效率**：能就近取車就不動用總部載滿車，把總部戰備留給真的湊不到的死結。
- **對齊全自動化方向**：階梯是可程式化的明確規則，人不必逐張判斷車從哪來；缺口以
  `needs_depot_refill` 顯性警示，供未來自動流程升級為「自動改派總部」。
- **同區優先**：先在同區湊，湊不足才跨區（與 ADR-316 一致），減少不必要的長程跨區。

## 考慮過的替代方案

### 方案 A：就近取車優先的車源階梯，總部載滿為最後手段（採用）

- 優點：車源可行、成本低、規則明確、缺口顯性化。
- 缺點：規劃邏輯較複雜（要 supply-aware 併站）。
- 未採用原因：無——採用方案。

### 方案 B：一律從總部載滿車出發

- 優點：規劃最簡單，永遠有車源。
- 缺點：浪費總部戰備、長程移動成本高，且不符「先看鄰近能不能湊」的直覺。
- 未採用原因：owner 明確要求分兩情況、能就近湊就湊。

### 方案 C：不管車源，只排補車動作

- 優點：最簡單。
- 缺點：組出無效派工單（沒車可補）。
- 未採用原因：這正是 owner 指出要修的缺口。

## 影響與後果

### 正面

- 補車趟一定有可行車源；資源動用有優先序，總部戰備不被濫用。
- 湊不到車源時以醒目警示 + 缺口台數顯示，並自動改派總部待命人車。

### 負面與代價

- 組單規劃需做 supply-aware 併站與缺口計算，邏輯較重。
- 跨區補足會讓本趟涵蓋多區（`draft_district` 標「跨區」），顯示與落地需處理多區標示。

### 尚未解決

- 目前跨區補足取「一站」補足，未做多站最優組合的成本最小化；未來可再優化。

## 介面與相容性

- **行為**：`build_from_station` 依階梯挑站源與決定車／人；草稿新增 `needs_depot_refill`
  與 `supply_shortfall` 欄位（前端 `OrderBuilder` 以 error banner 醒目呈現）。
- **相容性**：入口 a（以車為起點）、入口 c（緊急出車）不受本階梯改動；既有草稿欄位不變，僅新增。
- **設定**：沿用 `fleet` 容量／每趟最大站數等既有參數，無新增必要欄位。

## 資安與隱私

- 無新增對外邊界；只讀既有即時站況與車隊／人力主檔。不涉個資。

## 回復或取代方式

- 可將 `_pack_supply_aware_trip` 退回單純的緊急度切趟（不併取車站），即回到舊行為；
  未來調整階梯策略以新 ADR supersede。

## 驗證方式

- `tests/test_dispatch_builder.py`：以站為起點組單會併入取車站作為車源、湊不足時標
  `needs_depot_refill` 並改派總部待命資源，皆通過。
- 後端全套測試僅餘 pre-existing 失敗（與本次無關）。
