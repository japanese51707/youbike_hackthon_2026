# ADR-313：需調度清單背景預算快取（顯示端點讀快取，派工維持即時）

## 背景與問題

`recommendations` / `alerts` / `escalations` 顯示端點原本每次 request 都對全市 1606 站重跑
`build_dispatch_list`（逐站 LightGBM 預測 + 同時段歷史代理 lag 查表），且多端點各算一次。
前端一進畫面同時打好幾個端點，後端（小 task）就同時跑好幾次全量預測 → recommendations 冷
22–32 秒、alerts 5–31 秒，超過前端 timeout → 地圖與需調度清單全空（KPI 較輕仍顯示，造成
「連上卻沒資料」假象）。即時站況約 5 分鐘才更新，這期間每次 request 重算是純浪費。

## 決策

背景預算 + TTL 快取（`core/dispatch_cache.py`）：
- 背景 daemon thread 每 `ttl_sec`（預設 60）秒算一次全量 `build_dispatch_list`（含 override，
  apply_capacity=False），結果進記憶體快取。
- **顯示端點讀快取**：recommendations（limit/priority 在讀取端切）、alerts、escalations
  改讀 `dispatch_cache.get_snapshot()`（站況 + recs），不再各自重算。
- **派工端點維持即時**：組單三入口 `_current_dispatch_list`、confirm 仍即時重算（派工要最新）。
- 首次讀取或快取過期而背景尚未補上時，同步算一次（不回空）。
- 僅真實資料源（非 mock）且 config `dispatch_cache.enabled` 為真時啟動背景 thread。

## 理由與判準

- 效能：實測 recommendations/alerts 從 14–32 秒降到約 1 秒；併發載入全部 <3 秒。
- 正確性不變：快取內容與即時重算相同，60 秒刷新；站況 5 分鐘才更新，延遲無感。
- 關鍵路徑保鮮：派工/確認不吃快取，維持最新資料。
- 可控可逆：config 開關關閉即回到每次即時重算。

## 考慮過的替代方案

### 每次 request 即時算（現狀）
- 缺點：重複全量計算，慢且超時。未採用。

### 只算「可能需調度」的站（先便宜篩再預測）
- 優點：減少預測站數。缺點：仍每 request 算、且「哪些站免預測」的判斷本身有漏判風險。
- 未採用原因：背景快取更徹底且不影響正確性；此法可作未來進一步優化。

## 影響與後果

### 正面
- 顯示端點秒回，前端載入順暢，不再因超時而清單/地圖全空。

### 負面與代價
- 顯示資料最多有 `ttl_sec`（60 秒）延遲；派工端點不受影響仍即時。
- 多一個背景 daemon thread（與 auto_detect 同模式，daemon 隨程序結束）。

### 尚未解決
- `build_dispatch_list` 內部仍有逐站預測 + 二次 predict 算緊急度的重複，可再優化（不影響本決策）。

## 介面與相容性

- 新增 `core/dispatch_cache.py`；`config.yaml` 新增 `dispatch_cache`（enabled / ttl_sec）。
- recommendations/alerts/escalations 回傳內容與語意不變（只是資料來源改為快取）。
- main.py lifespan 啟動/停止背景 thread。無 schema / 前端契約變更。

## 資安與隱私

- 快取只存站況與需調度建議（皆非敏感）；不涉金鑰、不對外。

## 回復或取代方式

- config `dispatch_cache.enabled: false` 即回到每次即時重算。

## 驗證方式

- 本機：get_snapshot 首次算全量（1606 站/648 建議），第二次讀快取 0ms。
- 雲端：重部署後 recommendations/alerts 約 1 秒、併發載入全部 <3 秒。
- 回歸：後端測試套除既有 pre-existing 失敗外全通過（含 recommendations 契約測試）。
