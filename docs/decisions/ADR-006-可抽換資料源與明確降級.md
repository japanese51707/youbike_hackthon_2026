# ADR-006：可抽換資料源與明確降級

> 追溯說明：accepted 表示 owner 核准「資料源可抽換、失敗必須可見」作為目標決策，不代表現行實作已完整達成。替代方案是依現況重建的取捨分析，不表示當時曾逐項留下討論紀錄。

## 已確認的實作缺口

- 即時源與 Historical 都失敗時，`degradation.py` 目前回傳空 list，API 沒有同步暴露 `degradation_status()`；呼叫端仍無法區分「真的沒有站」與「所有來源失敗」。
- Mock fixtures 把 `data_freshness` 標成 `live`，但它不是真正即時來源；Demo 不應據此宣稱已串即時資料。
- API 契約／Pydantic 使用 `historical_fallback`，Historical adapter／degradation 實作使用 `historical`，枚舉尚未統一。

上述是待修正缺口，不是 accepted 決策允許的例外。

## 背景與問題

開發期有 Mock 與 S3 歷史 Parquet，現場可能提供 TDX 或 YouBike 官方即時源。若上層直接依賴任一供應者格式，換源會連帶修改 API、規則引擎與前端；即時來源故障時若回空資料或假裝成功，還會造成錯誤調度。

## 決策

- 所有站況來源實作共同 `DataSource` 介面，統一輸出標準站點欄位。
- 來源透過外部設定選擇，支援 `mock`、`historical`、`tdx`、`youbike_official`。
- 各 adapter 負責把第三方欄位轉成內部標準格式，上層不依賴供應者原始格式。
- 不可用或尚未實作的來源必須明確回報失敗，不得以空值或 Mock 假裝成功。
- 降級結果必須附帶 `data_freshness`／來源狀態，讓使用者與規則引擎知道資料不是即時值。
- 即時來源故障時可退回歷史同時段策略，但降級不等於成功取得即時資料。

## 理由與判準

- 現場換資料源只改設定與 adapter，不改控制平面。
- 第三方回應可在單一邊界驗證、正規化與追溯。
- 明確標記 freshness，避免系統用過期資料做出看似即時的結論。
- 未完成 adapter 以 `NotImplementedError` 顯示缺口，符合「失敗要看得見」。

## 考慮過的替代方案

### 直接綁定 TDX

- 優點：程式較少。
- 缺點：憑證、格式或可用性改變會衝擊整個系統。
- 未採用原因：現場正式來源尚未確定。

### 來源失敗時回空 list 或 Mock

- 優點：API 不會丟例外。
- 缺點：呼叫端無法分辨「真的沒有站」與「資料源壞了」。
- 未採用原因：會造成靜默失敗與錯誤決策。

## 影響與後果

### 正面

- 上層只依賴穩定介面。
- 能在離線 Mock、歷史回放與未來即時模式間切換。
- 來源與 freshness 可追溯。

### 負面與代價

- 每個來源都要維護欄位對映、驗證、超時與健康檢查。
- 歷史降級只能提供近似值，不能宣稱為即時資料。

### 尚未解決

- `tdx.py` 與 `youbike_official.py` 在相關歷史 commit 中仍是明確失敗的骨架。
- Historical adapter 直接讀 S3；`.env.example` 中 Athena 設定尚未成為此路徑的執行期依賴。
- 正式即時來源的欄位、憑證、重試與 SLA 尚待主辦確認。

## 介面與相容性

新增來源必須回傳 `STANDARD_STATION_FIELDS`，不得迫使上層判斷供應者。更改標準欄位屬跨模組契約變更，需同步評估 ADR-005。

## 資安與隱私

第三方回應視為不可信輸入；憑證只從安全設定來源取得，不寫入版控或 log。正式 adapter 必須有 HTTPS、timeout、有限重試、回應驗證與憑證最小權限。

## 回復或取代方式

可透過設定切回 `mock` 或 `historical`。若未來改成事件串流或資料湖中介層，建立新 ADR 定義新的介面、freshness 與遷移策略。

## 驗證方式

- 相同查詢在不同 adapter 下輸出一致欄位。
- 未實作／故障來源明確顯示 unavailable。
- 降級結果標示來源與 freshness，不冒充即時資料。
