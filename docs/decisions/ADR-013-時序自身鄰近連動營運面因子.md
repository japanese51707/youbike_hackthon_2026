# ADR-013：站點時序自身 / 鄰近連動 / 營運面因子（第三批）

## 背景與問題

ADR-011/012 已建兩批因子（外部環境類、時空 POI 類）。經 owner 提供附件（群組2 時間週期/站點自身、群組5 營運面）與工程學檢視，發現數個**最強但漏掉**的因子，尤其站點自身時序特徵（附件標「免費、優先級最高」）。同時 owner 要求所有因子以工程學三維度分類，因為這直接決定「訓練能用 vs 推論能不能用」。

不決定的後果：漏掉最強特徵（lag、歷史空滿頻率）；且 lag 類若不明確約束，會在訓練時用到「未來資訊」造成資料洩漏，模型驗證虛高、上線失準。

## 決策

新增第三批因子，各自模組化（延續 ADR-011/012），並確立**工程學三維度分類**與**資料洩漏防範約束**。

### 新增因子

1. **站點時序自身** `station_timeseries.py`（附件群組2，最強）：
   - lag：前 30 分 / 前 1 小時 / 昨日同時段 / 上週同日同時段的存量
   - 近 1~2 小時變化率與方向（動能）
   - 變化加速度（「正在加速掏空」比「已經很少」更早示警）
   - 歷史空滿頻率（該站期間內空過/滿過幾次，最強先驗之一）
   - 波動度（P90-P10 帶寬，判斷該站好不好預測、要不要信任預測）
   - 日均周轉量（篩掉低流量站）

2. **站點容量** `station_capacity`（靜態）：總車柱數（S3 已有），大小站緩衝不同。併入 station_timeseries 或獨立輕量欄。

3. **鄰近站連動** `neighbor_stations.py`：站間地理距離 → 「人願意走過去的意願隨距離指數衰減」→ 鄰近站狀態的連動影響。權重 = exp(-距離/特徵距離)，特徵距離可 config（如 300m）。

4. **日出日落** `daylight.py`（天文可算）：日出/日落時間、是否白天，影響天黑後騎乘意願。

5. **溫度倒 U 修正**（weather.py 延伸）：溫度對騎乘的影響是**倒 U 型**（適中最多、太熱太冷都少），非線性。加「舒適度」衍生欄（距最適溫的偏離），或明確交給 LightGBM 學非線性但提供舒適度特徵。

6. **故障車柱缺口**（間接推）：缺口 = 總柱數 − 可借 − 可還（S3 可算，23.5% 紀錄有缺口）。屬弱訊號但保留。電輔車比例 S3 無資料，不做。

7. **營運面 level shift** `operations.py`（附件群組5，進階）：費率政策變動、YouBike 1.0→2.0 轉換、鄰近站新增/退場、是否在既有調度路線上。造成需求階梯位移，訓練資料跨越變動點要小心。初期以資料表/旗標記錄，資料後補。

### 工程學三維度分類（所有因子，決定訓練/推論可用性）

| 維度 | 類別 | 意義 |
|------|------|------|
| 可得性 | 已知未來確定 / 已知未來有誤差 / 僅事後可知 | 「僅事後可知」的當下值不可當即時預測輸入 |
| 更新頻率 | 靜態一次算 / 每日批次 / 即時串流 | 決定計算與快取策略 |
| 涵蓋範圍 | 全市共用 / 分區 / 少數站 | 決定特徵粒度 |

### 資料洩漏防範（不可違反的工程約束）

- **lag / 變化率 / 加速度 / 鄰近站狀態**屬「僅事後可知」：預測 t+1 時，只能用 **≤ t 的已發生值**，絕不可用 t+1 當下值（那正是要預測的目標）。
- **歷史空滿頻率 / 波動度 / 日均周轉量**：用**訓練期之前**的歷史統計，驗證期不可回看驗證期資料。
- 時間切分驗證（ADR-002：1~5月訓、6月驗），禁隨機切分。
- 特徵組裝時對每個 lag 特徵標註「相對 t 的時間位移」，確保全部 ≤ 0。

## 理由與判準

- 附件明確標站點自身時序為「最強、優先級最高」，且免費（從既有存量序列算）
- 歷史空滿頻率是「最強先驗之一」——直接反映該站體質
- 鄰近站連動用指數衰減符合「人願意走多遠」的真實行為（owner 洞見）
- 溫度倒 U 是物理事實，線性假設會錯
- 工程三維度分類避免「訓練虛高、上線失準」的資料洩漏陷阱

## 考慮過的替代方案

### lag 特徵：直接用當前值
- 未採用：會資料洩漏（用到要預測的未來），驗證虛高

### 鄰近站連動：用行政區當群組
- 未採用：行政區邊界不等於「走得到」，距離指數衰減更貼近行為

### 溫度：當線性特徵
- 未採用：倒 U 型物理事實，線性會系統性偏誤

## 影響與後果

### 正面
- 補齊最強特徵，預測力預期大幅提升
- 工程三維度分類讓「哪些特徵推論時能用」一目了然

### 負面與代價
- lag/鄰近特徵計算需嚴謹的時序對齊，防洩漏工作量高
- 營運 level shift 資料需後補；故障車柱僅間接推（非官方數）

### 尚未解決
- 交叉影響仍留待後續
- level shift 變動點的精確日期待查（費率調整、1.0→2.0 時程）

## 介面與相容性

- 新增 `backend/features/` 數模組，輸出特徵欄位
- 特徵組裝層（下一步）需實作「防洩漏的時序對齊」
- 不改 core/interfaces.py 的 PredictionInterval

## 資安與隱私

- 全部由 S3 既有資料 + 天文計算衍生，無外部請求、無個資
- level shift / 故障資料表為內部維護，無敏感資訊

## 回復或取代方式

- 各因子模組可獨立停用
- 設計變更以新 ADR supersede

## 驗證方式

- 各因子單元測試（給定序列 → 正確 lag/變化率/頻率）
- **防洩漏測試**：確認所有 lag 特徵的時間位移 ≤ 0（不含未來）
- 模型層：時間切分比較含/不含時序特徵的 MAE 與區間覆蓋
