# ADR-305：開發模式資料源降級與逐筆新鮮度標記

## 背景與問題

專案已將 `data_source.mode` 預設改為 `youbike_official`（真實新北市 YouBike 官方 API），
以真實資料為主呈現（見 ADR-303、ADR-006）。現況降級契約（ADR-303）為：

- 即時來源失敗 → 用「同來源最後成功快照」並標 `stale`。
- 完全沒有可信快照 → 回 HTTP 503，**刻意不以歷史或 mock 冒充**。

這個嚴謹契約在正式路徑是對的：假資料混進調度決策會造成錯誤決策，牴觸「AI 只估計、
規則引擎吃真實區間下界、正式來源拒絕 stale/historical/offline 站點」的核心約束。

但它帶來一個開發期的實務問題：**任何人在本機把後端跑起來，就會被外部 API 綁住**——
沒網路、API 掛掉或官方服務不穩時，站點端點連「首次」都拿不到快照而直接 503，
開發者無法在離線環境驗證前端畫面與互動邏輯。

不做決策的後果：開發者被迫手動改 `config.yaml` 的 mode 才能離線開發，改完常忘了改回，
又造成「repo 預設值」與「測試/開發需求」互相污染（本次已發生：mode 被改成 official 後測試全紅）。

同時，owner 希望**單筆站點資料就能看出這筆是即時（live）、先前快照（stale）還是模擬（mock）**，
讓點開單站詳情時能判斷資料可信度。

## 決策

**一、正式模式（`mode = youbike_official` 等真實源）維持 ADR-303 契約，完全不變**：
失敗→同來源最後成功快照標 stale→無快照回 503，**絕不自動降級到 mock 或歷史**。
正式模式的預覽與確認仍拒絕 stale/historical/offline 站點。本 ADR **不** supersede ADR-303 的正式路徑條款。

**二、新增一個「開發環境專用」的 mock 降級開關**，預設關閉：

- 開發時 `mode` 仍設真實源（如 `youbike_official`），資料**先跟真實走**；只有真實源
  「連同源 stale 快照都沒有」而原本會 503 時，才降級到 mock。
- 是否允許此降級由兩個條件同時成立控制：
  1. 設定 `data_source.dev_fallback_to_mock = true`（預設 `false`）。
  2. 執行環境為開發環境：環境變數 `APP_ENV` 不等於 `production`（預設視為開發）。
- **正式環境（`APP_ENV=production`）即使開關為 true 也一律不降級 mock**，維持 ADR-303 的 503。
  這用「部署環境」而非「資料源 mode」來區分正式/開發，因為開發時 mode 本就設真實源。
- 生效時：真實源在原本會 503 的情況下改用 mock 資料源回站況，
  但**每一筆都明確標記為降級資料**（見下）。

**三、降級到 mock 的資料一律標記且不可進入調度決策**（護欄，不可違反）：

- 每筆降級站點：`data_freshness = "mock"`、`source = "mock"`、
  `quality_reasons` 含 `"upstream_unavailable_using_mock"`、`dispatch_eligible = false`。
- 因 `dispatch_eligible = false`，這些 mock 資料**不會進入派工池、不影響觸發與派工量**，
  守住 ADR-303／ADR-004「不得用假資料誤導決策」的底線。

**四、逐筆新鮮度標記（本就存在，明文化為契約並確保欄位完整）**：

- 每筆站點資料都帶 `data_freshness`（`live` 即時／`stale` 先前快照／`historical`／`mock`）、
  `observed_at`（觀測時間）、`observation_age_sec`（資料多舊）、`quality_reasons`、`dispatch_eligible`。
- `/api/v1/data/status` 新增 `degrading_to_mock`（bool）與 `mock_fallback_reason`（失敗原因字串），
  供前端顯示「⚠ 真實源失敗，目前顯示模擬資料」與上次成功時間。

## 理由與判準

- **正確性優先**：正式決策路徑不碰 mock，維持既有嚴謹契約；mock 只在明確開發情境、且標記為
  不可派工，杜絕假資料污染決策。
- **可維護性**：開發者用一個預設關閉的開關離線開發，不必手動改 mode、不再污染 repo 預設與測試。
- **可觀測性**：逐筆新鮮度 + status 旗標讓「資料哪來、多新、可不可信」在畫面上一眼可辨。
- **可逆性**：開關預設關，移除只需刪設定與對應分支，正式路徑不受影響。

## 考慮過的替代方案

### 方案 A：正式模式也自動降級到 mock

- 優點：任何情況畫面都不開天窗。
- 缺點：假資料可能被當正式資料、進入調度決策，直接牴觸 ADR-303／ADR-006／ADR-004。
- 未採用原因：owner 明確表示現有正式契約更好，正式模式維持 503；本 ADR 僅開放開發情境。

### 方案 B：維持現狀（完全不提供 mock 降級）

- 優點：最嚴謹，零假資料風險。
- 缺點：開發者離線無法跑前端畫面，被迫手動改 mode 造成 repo 預設與測試污染。
- 未採用原因：開發便利性與「預設值污染」的實務痛點需要解，但要用護欄解而非放寬正式路徑。

### 方案 C：靜默降級到 mock 不標記

- 優點：實作最簡單。
- 缺點：使用者無法分辨資料真假，正是 ADR-303 否決的「靜默 mock fallback」。
- 未採用原因：違反「失敗要看得見」（開發原則 §四）與 ADR-303。

## 影響與後果

### 正面

- 開發者可離線開發，不必改 repo 預設 mode；測試與正式預設不再互相污染。
- 前端可逐筆顯示資料新鮮度，單站詳情可判斷可信度。
- 正式路徑零改動、零新增假資料風險。

### 負面與代價

- degradation 層多一個條件分支與一份設定；需測試涵蓋「開關開/關 × 正式/開發模式」矩陣。
- 開發者若誤把開發開關帶到類正式環境，仍靠「正式 mode 時開關不生效」這層防護擋住。

### 尚未解決

- 「開發環境」以環境變數 `APP_ENV != production`（預設開發）界定。部署到正式環境時
  須設 `APP_ENV=production` 才能確保永不降級 mock；此環境變數的佈署規範待部署 ADR 補齊。

## 介面與相容性

- 新增設定鍵 `data_source.dev_fallback_to_mock`（預設 false）；不改既有鍵。
- `get_stations_with_degradation()` 行為在正式模式完全不變；僅在開發情境且開關開時多一條 mock 降級分支。
- 站點回傳欄位不新增必填欄位（`data_freshness` 等本就存在）；`/data/status` 新增兩個可選欄位，向後相容。
- Pydantic schema 若有嚴格欄位需同步允許新增的 status 欄位。

## 資安與隱私

- 無新增憑證或個資。mock 為本地合成資料。
- 出向：正式路徑仍只打 `data.ntpc.gov.tw` HTTPS，降級到 mock 為本地行為、不新增外部請求。

## 回復或取代方式

- 移除 `dev_fallback_to_mock` 設定與 degradation 層對應分支即可完全回到 ADR-303 現狀。
- 若未來要調整正式路徑降級策略，須以新 ADR supersede ADR-303，不改本 ADR 的開發情境條款。

## 驗證方式

閘門執行後須實際跑過（不得只宣稱）：

- pytest：
  - 真實源 + 開關 false → 失敗仍回 503（ADR-303 不變）。
  - 真實源 + 開關 true + `APP_ENV=production` → 仍回 503（正式環境開關不生效）。
  - 真實源 + 開關 true + 開發環境 + 真實源失敗且無快照 → 回 mock 資料，且每筆 `data_freshness=mock`、
    `dispatch_eligible=false`、`quality_reasons` 含 `upstream_unavailable_using_mock`。
  - `/data/status` 在降級時回 `degrading_to_mock=true` 與 `mock_fallback_reason`。
  - 既有 301 測試不因本變更破壞（測試環境沿用 conftest 強制 mock，行為不變）。
- `git diff --check`。
