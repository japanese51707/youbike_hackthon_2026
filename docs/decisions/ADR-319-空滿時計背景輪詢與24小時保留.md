# ADR-319：空滿時計背景輪詢與 24 小時保留

## 背景與問題

ADR-318 把時計掛在 `service_problems`，但同步發生在有人打站況 API 的時候。
後端剛啟動或沒人開看板，空／滿站的 `opened_at` 會從第一次被看到才起算，各區平均排除時間也幾乎是空的。

不做決策的後果：看板數字依賴「有沒有人開著頁」，不是站況真實經過時間。

## 決策

1. **後端自己輪詢**：程序啟動後以背景 thread 定期拉完整站況並同步時計，不依賴前端、不跑全量預測。
2. **預設 60 秒**一輪（官方站況約 5 分鐘更新）；`config.yaml` `service_problems` 可改間隔。僅真實源啟動，mock 不啟。
3. **只留過去 24 小時**：已結案且 `closed_at` 早於現在減 24 小時的列刪除（覆蓋窗口）。進行中案件保留，時計繼續走。
4. **看板平均改看近 24 小時**已排除（`recovered`），不再用台北日曆日「今日」當唯一窗口。
5. 既有「請求打到站況也同步」仍保留，當背景失敗時頁面刷新仍能補一筆。

## 理由與判準

- **正確性**：時計跟進程走，不跟瀏覽器走。
- **成本**：只拉站況，不重跑調度預測。
- **可逆**：關開關即停輪詢；刪除只動已結案舊列。

## 考慮過的替代方案

### 只靠 dispatch_cache 背景預算

- 優點：少一條 thread。
- 缺點：那條迴圈還做全站預測，失敗或關閉時時計也停。
- 未採用原因：時計與預測解耦。

### 前端開著就一直打 API

- 優點：不必改後端。
- 缺點：沒人開頁就沒時計，正是本問題。
- 未採用原因：owner 否決。

## 影響與後果

### 正面

- 後端活著就持續開／關時計；近 24 小時排除平均才有意義。

### 負面與代價

- 每分鐘多一次官方站況請求（與 cache／auto_detect 可能重疊）。
- 進程重啟前的空窗仍無法回補（第一次看到才開案）。

### 尚未解決

- 官方歷史「這站其實空了三小時」無法在上線前補齊。

## 介面與相容性

- `config.yaml`：`service_problems.enabled` / `輪詢間隔_秒` / `保留小時`。
- `GET /api/v1/service-problems` 增加 `window_hours`、`window_start`。
- 表結構不變；多 `DELETE ... closed_at < 窗口`。

## 資安與隱私

- 無新對外寫入；仍只存站名與行政區。

## 回復或取代方式

- 以新 ADR supersede；設 `enabled: false` 即停背景，看板退回「有人打 API 才同步」。

## 驗證方式

- 真實源啟動 log 出現背景輪詢已啟動。
- 結案超過 24 小時的列被刪；未結案列仍在。
- 平均只含窗口內 recovered。
