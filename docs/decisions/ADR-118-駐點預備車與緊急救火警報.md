# ADR-118：駐點預備車、車隊保留率與緊急救火警報

## 背景與問題

題目宗旨明言：「提升調度反應速度：縮短從供需失衡發生到機關人員獲知/介入的時間差」。
owner 據此定調——**「示警與反應速度」與「排程」同等重要**。常態排程（ADR-117）處理可預測的失衡，
但突發狀況（天氣劇變、大眾運輸異常、調度車出意外、活動爆量）常態排程來不及反應，需要獨立的
**緊急救火機制**：預先保留的機動車力 + 自動觸發的警報。

此外，駐點人員（ADR-116）在熱門站現場調節，需要「駐點預備車」作為現場即時車力。

這些不歸大數據預測管，歸「緊急警報」管——是縮短反應時間差的核心。

## 決策（proposed，待 owner 核准）

### 一、駐點預備車（現場即時車力）

- **設在哪**：尖峰週轉量最高、最易空/滿的熱門站（dispatch_ops_analysis Top 站，多為捷運大站）。
- **備多少**：**該站尖峰週轉量**（歷史）為目標總量，**扣掉柱點上現有車** = 實際要放的預備車。
  - 例：某站尖峰週轉 40 台、當下站上已有 10 台 → 預備車放 30 台（避免備過頭，owner 確認「含站上現有車」）。
  - 不用「柱數一半」（對大站過量、且柱數是容器非需求；比照 ADR-115 用需求而非絕對值的判準）。
- **用途**：駐點人員在尖峰時用預備車即時補位（缺車放車、滿站不夠位時預備車先承接週轉）。
- 記錄：vehicles 加 `is_reserve`（是否駐點預備車）與（若綁站）`reserve_at_station`。

### 二、車隊靜態保留率（Reserve Capacity Constraint）

- 全車隊固定保留 **10~15%（config `reserve.保留率=0.12`）** 為 standby，不參與常態派單（ADR-117）。
  - 例：41 台 → 保留約 5 台 standby。
- standby 車在系統顯示 `status=standby`，只由緊急救火觸發轉 `active`。
- Provider 的 `available_vehicles()`（ADR-114）需排除 standby（常態排程拿不到它們）。

### 三、緊急救火觸發（死結警報 → 派預備車）

自動觸發條件（config 可調）：

- **條件 A（區域死結）**：某行政區同時 ≥ N 個（`emergency.死結站數門檻=3`）精華大站，
  連續 ≥ M 分鐘（`emergency.死結持續分鐘=15`）處於死結（100% 滿或 0% 空），
  且現有在途調度車抵達時間均 > `emergency.在途門檻分鐘=30`。
- **觸發動作**：系統跳紅字警報 → 將 standby 預備車轉 active → 指派「緊急救火任務」給待命人員
  （最近的可用 standby 車 + 待命人員）。
- 緊急救火任務**可跨區**（救火優先於分區約束）、優先級最高（排在常態任務之前）。

### 四、即時天氣偵測（突發調度觸發源，新資料源）

- 現況天氣是「每日批次特徵層」，無即時源。本 ADR 導入**即時天氣源**（中央氣象署 CWA 開放資料 API）。
- 用途：偵測突發天氣轉變（如驟雨 → 還車率暴增），作為緊急救火的**額外觸發訊號**：
  - 天氣突變（惡化 ≥2 級）→ 預警該區可能大量滿站 → 提前備援。
- 比照 ADR-006 資料源可抽換：新增 `WeatherSource` 介面（cwa / mock），工廠依 `config.weather.mode` 切換。

**精細度：觀測站級（owner 於 2026-09-10 決定，由原「行政區級」升級）。** 理由：一個行政區內
YouBike 站可能上百個，行政區級太粗；改用「最近測站對應」——任一 YouBike 站（有經緯度）用
haversine 找最近測站取值（Voronoi 最近鄰）。

**雙資料集（實測確認）：**
- **雨量站 `O-A0002-001`**（新北約 100 站）：Now / Past10Min / Past1hr 雨量 → 偵測驟雨主力（密度高，4 倍於氣象站）。
- **氣象站 `O-A0003-001`**（新北約 25 站）：氣溫 / 濕度 / 天氣現象 → 一般天氣輔助。

**介面：** `get_rainfall_by_location(lat,lng)`（驟雨）/ `get_weather_by_location(lat,lng)`（氣溫等）/
`get_weather(district)`（相容行政區級）。測站清單本地快取（避免每查一站打一次 API）。

- 出向資安（steering §11）：CWA 為第三方——回應當不可信輸入（欄位缺失/型別容錯）、超時/重試上限、
  API key 由環境變數 `CWA_WEATHER_API_KEY`（.env，不進版控/不寫 log）；政府平台憑證鏈問題用 `verify=False`
  （比照 youbike_official；key 在參數非靠 SSL 保護）。

### 五、示警與反應速度機制（與排程同等重要）

統整本專案所有「示警」，明確定義**觸發 → 通知 → 介入**的最短路徑（縮短時間差）：

| 警報類型 | 觸發 | 通知對象 | 建議動作 |
|---------|------|---------|---------|
| 區域死結 | 條件 A | 後台管理人員（紅字） | 派緊急救火預備車 |
| 天氣突變 | 即時天氣 + 還車暴增 | 後台管理人員 | 預先備援該區 |
| 工作警示 | 連續工時近上限（ADR-116） | 後台管理人員 + 當事人 | 安排休息、暫停派任務 |
| 站點警示 | 規則引擎 warning/critical（既有 alert_service） | 後台管理人員 | 依緊急度排程 |

- 沿用既有 `alert_service` + `alerts` 表 + `alert_subscriptions`（webhook 通知機關，出向 SSRF 已防）。
- 反應速度指標（KPI）：從「失衡發生」到「警報產生」到「派遣」的時間差，供 controller 監控與簡報。

### 不改
- ADR-117 常態排程（緊急救火為獨立的最高優先分支，插隊於常態之前）。
- ADR-116 角色/班別、ADR-114/115 資源與目標水位、既有 alert_service/override_service 主體。

## 理由與判準

- **對準題目宗旨**：縮短「失衡→獲知→介入」時間差是核心 KPI，緊急救火 + 自動警報直接命中。
- **常態與緊急分流**：可預測失衡走排程（大數據預測），突發走警報（規則觸發），職責清晰。
- **預備車量用需求非絕對值**：尖峰週轉扣站上車，避免過量（比照 ADR-115 判準）。
- **保留率保機動**：固定 standby 確保突發時有車可派，不會全被常態任務吃光。
- **即時天氣填補盲區**：天氣突變是預測模型（30 分格歷史）反應不及的情境，即時源補上。
- **資料源可抽換**：天氣源比照 ADR-006，demo 用 mock、正式接氣象署。

## 考慮過的替代方案

### 突發狀況也靠常態排程反應
- 缺點：常態排程基於預測，突發（天氣/意外/爆量）預測反應不及，時間差過大。未採用。

### 不保留 standby，全部投入常態
- 缺點：突發時無車可派，只能等常態任務完成，反應慢。未採用（保留率是機動保障）。

### 駐點預備車用柱數一半
- 缺點：大站過量、柱數非需求指標。未採用，改尖峰週轉扣站上車。

### 不接即時天氣，沿用每日批次
- 缺點：無法偵測「當下」天氣突變。未採用，導入即時源（可抽換，demo 可 mock）。

## 影響與後果

### 正面
- 突發狀況有獨立快速反應路徑；駐點現場有即時車力；警報縮短反應時間差（命中題目宗旨）。
- 天氣突變可提前備援。

### 負面與代價
- vehicles 加 is_reserve/reserve_at_station；config 加 reserve/emergency/weather 區塊。
- 新增 WeatherSource 介面 + 即時天氣源接取（出向資安）。
- available_vehicles 需排除 standby；緊急救火分支插隊邏輯。

### 尚未解決
- 「精華大站」的具體名單（用 dispatch_ops_analysis Top 站 + 柱數門檻，離線定期更新）。
- 即時天氣「還車率暴增」的門檻（待資料回饋校準）。
- 緊急救火任務完成後 standby 車是否歸隊 standby 或轉常態（實作時定，預設歸隊）。

## 介面與相容性

- vehicles 加 `is_reserve INTEGER`、`reserve_at_station TEXT`（migration，比照 ADR-114）。
- config 加 `reserve`（保留率）、`emergency`（死結門檻/持續/在途/救火可跨區）、
  `weather`（mode: cwa/mock、county、timeout_sec、max_retries；雙資料集 O-A0002-001/O-A0003-001）。
- 新增 `WeatherSource` 介面 + 工廠（比照 DataSource）。
- available_vehicles 排除 standby；alert_service 加死結/天氣/工作警示類型。
- 緊急救火為最高優先，排在 ADR-117 常態任務之前。

## 資安與隱私

- **出向（steering §11）**：氣象署 API 為第三方——回應當不可信、SSRF 檢查、超時/重試上限、不外洩憑證、
  API key 放環境變數不進版控（steering §11.1）。
- webhook 通知機關沿用既有 alert_subscriptions 的出向 SSRF 防護。
- 無新增 PII。

## 回復或取代方式

- 保留率設 0、移除緊急救火分支與天氣源即回復常態排程；改方向以新 ADR supersede。

## 驗證方式

- 保留率：available_vehicles 正確排除 standby（41 台保留約 5 台）。
- 死結觸發：構造「某區 ≥3 站連續死結 + 在途 >30 分」→ 正確產生救火警報 + 派 standby。
- 駐點預備車量：尖峰週轉 − 站上車，正確計算、不過量。
- 天氣源：可抽換（mock/即時），出向逾時/SSRF 防護生效。
- 警報：四類警報正確觸發、通知、記錄反應時間差。
- 跑既有 alert_service/override 測試不破壞。
