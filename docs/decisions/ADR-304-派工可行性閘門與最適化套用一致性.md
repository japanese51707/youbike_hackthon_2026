# ADR-304：派工可行性閘門與最適化套用一致性

## 背景與問題

第三批審查在 API 契約層查到兩組不一致：

**派工可行性的對外語意**：三入口組單（`build_from_vehicle`／`build_from_station`／`build_emergency`）完全不呼叫 `validate_resources`／`validate_stations`，只有確認時的 `_persist_trip` 才驗證。後台會看到一張預覽正常、按下確認才回 409 的草稿，且無法從草稿內容判斷哪裡不可行。ADR-123 導入逐站載量與工時檢查後，這個落差會更明顯。

**optimizer 套用的一致性**：
- `compute_daily_review` 用 `except Exception` 把所有失敗壓成 `status="no_data"`；樣本不足則是靜默跳過，呼叫端無法區分「沒有資料」「樣本不足」「計算失敗」「有效更新」。
- `_pending_review` 是模組全域變數，`approve` 不帶任何識別，可對同一份建議重複套用，重啟後狀態消失。
- `approve` 在迴圈內逐站 `commit_optimized`，以 `except` 吞掉個別失敗並把失敗站名塞進成功清單回傳；任一站失敗時前面的站已寫入，形成部分套用。
- `rollback` 只呼叫 `activate_version`，未驗證回溯後實際生效參數等於目標版本。
- 另經 `grep` 確認：`params.station_params`／`get_effective_params` 的消費端只有 `api/stations.py` 三個唯讀端點，`rule_engine`、`dispatcher`、`prediction` 沒有任何讀取——ADR-120「做法 Y：建議層，生效接線待補」屬實。

## 決策

沿用 ADR-004、009、010、120、302、303 與 ADR-123；不取代任何 ADR。

1. **預覽即回報可行性**：三入口組單回傳的草稿包含 `blocking_reasons`（阻擋原因陣列，空陣列代表可確認）與逐站載量／到達計畫。預覽與確認呼叫同一份可行性評估（ADR-123），確認時以當下資源與觀測重新執行。預覽通過而確認失敗，只允許源於期間內狀態改變。
2. **錯誤語意不變**：不可行的確認一律沿用 ADR-302 的 409，訊息指明第一個阻擋原因；授權與輸入錯誤維持 401／403／422。不新增錯誤碼。
3. **最適化狀態必須可區分**：`daily-review` 回傳 `status ∈ {ok, no_data, insufficient_samples, failed}` 與對應 `reason`，並列出被跳過的站與跳過原因。計算失敗不得偽裝成「沒有資料」，也不得回傳部分結果卻標為成功。
4. **套用需綁定 review 且冪等**：`approve` 必須帶 `review_id`，與後端持有的建議比對；不符或已過期回 409。同一 `review_id` 重複送出回傳原結果，不重複寫版本（比照 ADR-302 的確認收據語意）。
5. **套用是全成或全退**：一次 `approve` 內所有站的 `commit_optimized` 在單一交易提交，任一站失敗全部回滾並回錯誤，不再回傳「部分成功」。不完整的最適化結果不得套用。
6. **回滾須驗證實際生效**：`rollback` 完成後重讀當前生效參數，確認等於目標版本才回成功，並寫稽核；不一致視為失敗。
7. **不接生效接線**：調整係數本批**仍不**被 `rule_engine`／`dispatcher`／`prediction` 讀取，維持 ADR-120 做法 Y 的定位。回應保留誠實標記，並以測試固定「approve 後規則引擎行為不變」這個事實，使其可回歸而非口頭宣稱。要讓係數生效須另立 ADR。
8. **不啟用雲端部署與常駐排程**：optimizer 仍為手動觸發的離線分析，不新增背景常駐服務、排程器或雲端資源。

## 理由與判準

- **失敗要看得見**：把四種不同狀況壓成同一個字串，會讓後台以為系統正常運作。
- **人在迴圈需要正確資訊**：預覽若不顯示阻擋原因，人工確認就不是有效閘門。
- **一致性優於便利**：部分套用的參數版本無法回溯到一個明確狀態，寧可整批失敗重來。
- **誠實邊界**：係數未生效是事實，應該被測試固定住，而不是靠註解提醒。

## 考慮過的替代方案

### 方案 A：預覽維持寬鬆，只在確認擋

- 優點：預覽快。
- 缺點：後台無法在組單階段調整，且無從得知原因。
- 未採用原因：人在迴圈閘門失效。

### 方案 B：`approve` 維持逐站 best-effort，回傳失敗清單

- 優點：部分成功總比全失敗好。
- 缺點：留下無法描述的中間狀態，回溯時不知道該回到哪一版。
- 未採用原因：與 ADR-009／302 的交易一致性原則衝突。

### 方案 C：本批直接把調整係數接進 rule_engine

- 優點：閉環完整，demo 好看。
- 缺點：在指標尚未驗證前讓未經檢驗的係數影響實際調度決策，違反 ADR-004。
- 未採用原因：明確排除，留待另立 ADR。

## 影響與後果

### 正面

- 後台在預覽階段就知道能不能派、為什麼不能派。
- 最適化的四種狀態可分辨，套用結果可回溯到單一明確版本。
- 「係數尚未生效」成為可回歸的測試事實。

### 負面與代價

- `approve` 請求新增必填 `review_id`，既有呼叫端需同步。
- 草稿回應變大（逐站計畫與阻擋原因）。
- 全成或全退會讓單站資料異常導致整批需重跑。

### 尚未解決

- 調整係數的生效接線。
- `_pending_review` 仍為單程序記憶體，多實例部署需另行設計。
- 雲端部署與常駐排程另案。

## 介面與相容性

草稿回應新增 `blocking_reasons` 與逐站計畫欄位（新增，不移除既有欄位）。`POST /optimization/daily-review/approve` 新增必填 `review_id`，缺少回 422、不符或過期回 409、重送回原結果。`daily-review` 回應的 `status` 值域擴充，既有 `pending_approval` 與 `no_data` 保留語意。資料庫無新表；參數版本沿用既有 `station_params`。前端未同步時，預覽仍可顯示，`approve` 需補帶 `review_id`。

## 資安與隱私

沿用既有角色檢查：組單／確認需 dispatcher 或 maintainer，最適化套用與回溯需 maintainer。不新增憑證、外部服務或個資。不信任 client 提供的可行性結論或參數值；`review_id` 只作為比對用的不可猜測識別，不作為授權憑證。

## 回復或取代方式

`blocking_reasons` 可保留為空陣列以停用預覽阻擋；`review_id` 檢查可放寬為選填以回到舊行為，但不得重新開放部分套用。改變方向以新 ADR supersede 本 ADR。

## 驗證方式

- pytest：預覽阻擋原因與確認結論一致、缺 `review_id` 回 422、錯誤或過期 `review_id` 回 409、重送回原結果不重複寫版本、單站失敗整批回滾、四種 `status` 各一案、回滾後生效版本驗證、approve 後規則引擎輸出不變。
- 既有 `test_params`、`test_p2_endpoints`、`test_dispatch_safety` 回歸不破壞。
- `git diff --check`；不 commit／push。
