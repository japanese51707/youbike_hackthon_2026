# ADR-336：預備車庫存與駐點員排程

> **狀態說明：本 ADR 為 proposed，尚未取得 owner 核准，實作不得開始。**
> 依 `.kiro/steering/decision_governance.md`，只有 owner 能將狀態改為 accepted。

## 背景與問題

Owner 於 2026-09-13 提出「預備車與駐點員」需求：依歷史數據找出兩個尖峰時段有固定全空風險的熱門站，
於尖峰前固定時距（例如 120 分鐘，可調）由總部車批次送指定數量的預備車到現場備用，
標記該站有預備車；站點全空時派駐點員把預備車補進車柱，站點全滿且無人處理時由駐點員把車收出來。

既有系統的現況：

- `operators.role_type` 已支援 `stationed` 與 `stationed_at`（ADR-116），並有各區、各班別配額種子。
- `core/emergency.py` 已有 `reserve_bikes_for_station()`（含 `capped_by_space`）與 `plan_stationed_reserves()` 骨架（ADR-118）。
- DEPOT 待命車已可 seed 與列出（ADR-119），目前 `config.yaml` 設定為 5 台。
- 自動配單已有背景執行緒與診斷統計（ADR-331／ADR-333）。

也就是說零件多半已存在，缺的是「歷史名單 → 每日排程 → 站上庫存帳 → 與既有配單引擎的接合」。

不做決策的後果：預備車功能會被實作成「提早派一趟車」。由於送進車柱的車會立即被市民借走，
該實作在營運上無效，且會消耗本就不足的總部車產能。

## 決策

採用「**站上鎖定庫存 + 駐點員為閥門**」模型，並全部掛在既有派工管線上，不新建第二套引擎。

1. **預備車定義為不可借庫存。** 送達站點後不進車柱，由駐點員看管；
   `on_hand = delivered_qty − released_qty + recalled_qty` 為唯一真相，不另存快照。
2. **預備車不計入該站可借車數。** 水位計算、預測特徵與負載守恆（ADR-123）一律排除 `on_hand`，
   僅在 `released` 當下轉入。
3. **新增兩張表**：`reserve_plan`（station × weekday × peak × qty，來源 history／manual，可停用）
   與 `station_reserves`（當日實況與任務關聯）。
4. **排程掛在 `auto_dispatch._loop()` 的同一個時鐘**，不新增背景執行緒。三個時點：
   尖峰前 T 分鐘產生佈車批次、尖峰中站空時優先由預備車自解、尖峰後回收窗收回剩餘。
5. **佈車一律為草稿，需人工確認**（守 ADR-302）。自動化只到偵測與建議為止。
6. **候選池必須經上限與優先序裁切**，且被裁掉的站要以「產能不足未佈署」清單呈現，不得無聲丟棄。
7. **沒有在班駐點員的站不佈預備車。** 無人看管的預備車等同於直接送給市民借走。
8. **長期缺車站（全時段空站率 ≥ 35%）排除在預備車機制外**，改由基準配置量處理。

決策邊界：本 ADR 不變更既有緊急派工判準、不變更司機工作台的任務卡片結構
（佈車與回收皆為一般 task，僅 action 文字不同），不引入新的即時資料來源。

## 理由與判準

- **正確性優先於直覺**：歷史分析顯示 9 個站的反覆率為 100%，但其全時段空站率亦達 ~50%，
  屬長期配置不足而非尖峰風險；若不排除，將佔用全部預備車產能且無法改善。
- **產能誠實**：週一早尖峰候選為 103 站／948 台／約 64 車次，而總部待命車僅 5 台。
  設計必須把「做不完」視為常態並顯性呈現，而非視為錯誤或隱藏。
- **可維護性**：複用 `role_type=stationed`、`reserve_bikes_for_station()`、DEPOT 車與既有 task／診斷管線，
  新增面積最小，回復成本最低。
- **可逆性**：功能可由設定整體關閉，關閉後既有配單行為不變。

## 考慮過的替代方案

### 方案 A：預備車直接補進車柱

- 優點：不需要駐點員看管，實作最簡單。
- 缺點：送進去的車在尖峰前即被借走，等同於提早一小時做一次普通補車。
- 未採用原因：無法達成「尖峰當下有車可用」的目的，且浪費總部車產能。

### 方案 B：完全即時判斷，不用歷史名單

- 優點：不需離線分析，隨時反映真實狀況。
- 缺點：站點變空時才出發，車程本身即造成缺口；且尖峰期間車輛已全數在途。
- 未採用原因：這正是目前的行為，也是「無足夠車源」問題的來源。

### 方案 C：獨立的預備車排程服務（新執行緒／新引擎）

- 優點：與既有配單邏輯解耦。
- 缺點：兩個時鐘、兩套鎖、兩份站況快取，狀態不一致的風險高。
- 未採用原因：維運成本與競態風險不成比例。

## 影響與後果

### 正面

- 尖峰最可預期的那部分缺口移出即時派工，可直接緩解「附近無足夠車源」的情形。
- 貨車產能釋出給沒有預備車的站。
- 既有診斷面板可直接呈現「由站上預備車自解 N 站」。

### 負面與代價

- 新增兩張表與一組每日排程，維運面積增加。
- 依賴現場實體隔離（拖車／圍欄／鎖具）；系統只能保證帳，無法保證鎖。
- 駐點員在班與否成為佈車前置條件，人力排班與預備車排程產生耦合。

### 尚未解決

- 現場預備車的實體存放方式尚未與業主確認；若無實體隔離，本 ADR 前提不成立。
- 每日車次上限、優先序權重與回收窗長度的初始值尚未定案。
- 歷史名單的更新頻率（每月重算或每季重算）尚未決定。

## 介面與相容性

- **Schema**：新增 `reserve_plan`、`station_reserves` 兩表，以冪等 migration 建立；既有表不變更。
- **API**：新增預備車名單檢視／調整、當日佈車草稿、駐點員釋放與回收端點；既有端點不變更。
- **設定**：`config.yaml` 新增 `reserve` 子項（前置分鐘、回收窗分鐘、每日車次上限、長期缺車排除門檻）。
- **前端**：後台新增預備車名單與當日佈署頁；司機工作台不需變更。
- **遷移**：功能預設關閉；關閉狀態下行為與現況完全一致。

## 資安與隱私

無新的對外入向或出向邊界。歷史分析使用既有 parquet 資料，不含個資。
駐點員指派沿用既有 operator 權限模型，不新增身分或憑證。

## 回復或取代方式

由設定整體關閉即可停用，兩張新表可保留不用。
未來若改變預備車的存放或計帳方式，應以新 ADR supersede 本案，不得改寫本文件。

## 驗證方式

- 單元測試：`on_hand` 公式在交付／釋放／回收各路徑下的正確性。
- 負載守恆測試：`on_hand` 未計入可借車數，`released` 後計入（ADR-123）。
- 排程測試：無在班駐點員的站不產生佈車草稿；超出每日上限的站進入「產能不足未佈署」清單。
- 整合觀測：自動配單診斷出現「由站上預備車自解」計數；回收窗後 `on_hand` 歸零。
- 資料佐證：`docs/analysis/standby_reserve_plan.json`（562 組合／193 站，六個月）。
