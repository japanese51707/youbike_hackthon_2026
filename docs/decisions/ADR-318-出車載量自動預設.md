# ADR-318：出車載量自動預設（取消人工回報並重算）

## 背景與問題

組單三入口在預覽與確認時，會透過 ADR-123 的可行性評估檢查「車上初始載量」（`onboard_bikes`）。
原本的設計是：車上載量未知或觀測過期時，`evaluate_feasibility` 會回 `vehicle_onboard_unknown`
／`vehicle_onboard_stale` 阻擋確認，前端則在組單面板提供一個「回報並重算」的 InputNumber + 按鈕，
要調派員手動填入車上台數、重打組單 API 才能解除阻擋。

系統的目標是走向全自動化流程、人員原則上不介入（唯一介入是緊急人工調度）。要求現場或後台
逐次手動回報車上台數，與此方向相違，也讓「點站就能組單並確認」多了一道人工卡點。

不決策的後果：每張需要確認的派工單都可能卡在 onboard 未知，需人工回報，無法自動流轉。

## 決策

**取消人工「回報並重算」，改由系統在組單時自動預設出車載量**，規則（採 **(甲) 純預設**）：

- 車上載量「**未知**」（`onboard_bikes` 為 `None`）時才套預設：
  - **非總部載運車**（`is_depot=False`）→ 車上預設 **0** 台（就近取車補足，不預先載車）。
  - **總部載運車**（`is_depot=True`）→ 車上預設 = **本趟補車需求量**（總部載滿出發），
    不超過車輛容量。
- 車上「**已有回報值**」時**尊重實際值、不覆蓋**（保留「車上有車就用車上的車」能力）。

此預設在**預覽層**（`dispatch_builder._make_draft` → `_preset_onboard`，回傳覆寫過的 vehicle
副本供可行性評估）與**落地層**（`dispatcher._persist_trip_atomic`，僅在 DB 車 onboard 未知時
用 `report_onboard(source="task_completion")` 寫回，讓可行性重評、執行端、ADR-310 自動偵測
基準三者同一口徑）皆套用同一規則。

前端移除 `OrderBuilder` 的「回報並重算」整塊 UI（InputNumber + 按鈕）與 `DashboardPage` 的
`reportOnboardAndRebuild`；總部載滿的醒目警示（ADR-315 `needs_depot_refill`）改述為「系統已
自動預設載滿所需車量，請確認該車已在總部載滿後再確認派發」。

## 理由與判準

- **對齊全自動化方向**：免人工回報，點站即可組單並確認，符合「人員原則上不介入」的設計目標。
- **語意正確**：非總部車不預先載車、靠就近取車補足，符合 ADR-315 車源階梯；總部車載滿需求量
  符合「總部載滿出發」的既有語意。
- **(甲) 尊重已知值**：不覆蓋已回報的真實載量，保留「預先裝載後直接補車」的合法用法，避免把
  已知資訊當未知丟棄；也讓既有以「先回報再補車」為前提的流程與測試維持正確。
- **可追溯**：落地寫回時來源標 `task_completion`（ADR-123 允許的可追溯來源之一），非臆造字串。
- **低破壞**：複用既有 `onboard_start_of` 語意（未知仍會擋），只是在組單／落地前把「未知」以
  規則補成明確值，不放寬全域對「未知不得當零」的守則。

## 考慮過的替代方案

### 方案（甲）：純預設、僅在未知時套用（採用）

- 優點：尊重已回報值、保留預先裝載能力；不破壞既有補車流程與測試。
- 缺點：若現場已有錯誤的舊回報值，會沿用該值而非重設。
- 未採用原因：無——這是採用方案（owner 明確選擇）。

### 方案（乙）：一律以規則決定、無視回報值

- 優點：完全自動、司機完全不必回報。
- 缺點：會廢掉「預先裝載後補車」用法，且需改寫多個以人工回報為前提的既有測試。
- 未採用原因：owner 選擇 (甲)；(乙) 對既有語意破壞較大，保留為未來全自動化升級選項。

### 方案（丙）：放寬 `onboard_start_of`，未知一律當 0

- 優點：改動最小。
- 缺點：污染全域可行性語意（ADR-123 明訂未知不得當零），且無法表達「總部車載滿需求量」。
- 未採用原因：破壞既有安全守則，且無法涵蓋總部車情境。

## 影響與後果

### 正面

- 組單→確認不再卡在 onboard 未知，可自動流轉；前端少一道人工操作。
- 總部車自動帶入載滿需求量、非總部車帶 0，與車源階梯語意一致。

### 負面與代價

- 落地時若車 onboard 未知會寫回一筆 `task_completion` 載量記錄（可追溯，但屬系統推算而非實測）。
- 若現場實際車上載量與預設不符（例如非總部車其實已載車卻未回報），預設 0 可能低估——但此時
  可行性只會更保守（傾向要求取車補足），不會高估載量造成超載。

### 尚未解決

- 未接車輛即時載量感測；預設值為組單當下推算，實際搬運仍以 ADR-310 自動偵測站況變化為準。

## 介面與相容性

- **行為**：組單三入口在 `_make_draft` 內對「未知載量」套預設（回 vehicle 副本，不動 DB）；
  確認落地在 `_persist_trip_atomic` 對「未知載量」寫回 DB 預設值。已知值兩處皆不覆蓋。
- **前端**：移除 `OrderBuilder` 回報區塊與相關 prop（`onReportOnboard`）、`DashboardPage`
  的 `reportOnboardAndRebuild` 與 `reportVehicleOnboard` import；`dispatchApi.reportVehicleOnboard`
  保留（司機端仍可用）。
- **設定**：無新增。
- **相容性**：`onboard_start_of` 語意不變（未知仍擋）；本 ADR 只在組單／落地前補值，未改可行性規則。

## 資安與隱私

- 無新增對外邊界；寫回載量走既有 `report_onboard` 白名單來源，不臆造來源字串。不涉個資。

## 回復或取代方式

- 移除 `_preset_onboard` 呼叫與 `_persist_trip_atomic` 的預設寫回，即回到「未知則擋、需人工回報」
  的舊行為；前端可還原回報 UI。未來若改採 (乙) 全自動語意，以新 ADR supersede。

## 驗證方式

- 後端：`test_dispatch_builder` / `test_dispatch_feasibility` / `test_dispatch_safety` 全通過
  （含「車上已回報 15 台可補車」情境不被預設覆蓋，驗證 (甲) 語意）；全套僅餘 pre-existing 失敗。
- 前端：`npm run build` 通過；OrderBuilder 移除回報區塊後仍可預覽／確認。
