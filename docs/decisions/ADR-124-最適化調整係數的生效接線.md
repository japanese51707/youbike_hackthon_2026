# ADR-124：最適化調整係數的生效接線

## 背景與問題

ADR-120 定下「做法 Y」：optimizer 算偏差、產生站點調整係數、由 controller 核准後存成 `ai_optimized`
參數版本，但明確把「係數真的被消費」列為尚未解決項。第三批以 `grep` 查核確認此事屬實——
`params.get_current()` 的消費端只有 `api/stations.py` 三個唯讀端點，`rule_engine`、`dispatcher`、
`prediction` 完全沒有讀取。ADR-304 第 7 條因此要求前端不得把「已套用」呈現成「調度行為已改變」。

結果是一個完整但空轉的閉環：算得出來、核准得了、存得進版本，卻不影響任何一次派工。
再不接線，這條路徑會持續累積無人使用的參數版本，且沒有任何回饋能驗證係數算得對不對。

## 決策

沿用 ADR-004（AI 只估計、確定性規則才能決定調度）、ADR-115（動態目標水位）、ADR-120、ADR-122、ADR-304。

1. **係數是規則的參數，不是模型的輸出**：係數由 optimizer 提出、由 maintainer 核准、存成可回溯的參數版本，
   生效時作用在 ADR-115 動態目標水位的「預期流量」項上。決策仍由確定性規則做出，未違反 ADR-004。
2. **套用位置**：補車看 P10 推得的「後續最大流出」、取車看 P90 推得的「後續最大流入」，
   兩者乘上該站的生效係數。基礎係數為 `base_outflow_coef`；當日為放假型態時再乘 `env_coef_weekend`。
   安全緩衝與 80/20 護欄不受係數影響。
3. **三態開關，預設關閉**：`config.optimization.係數套用模式 ∈ {off, shadow, on}`，預設 `off`。
   - `off`：完全不讀參數，行為與接線前完全相同。
   - `shadow`：照常計算套用後的目標水位，但**不採用**，只在建議輸出附上影子值與差異，供比對。
   - `on`：實際採用。
   切換模式是營運決定，不在程式內自動升級。
4. **絕對護欄**：生效係數一律夾在 `config.optimization.係數上下限`（預設 0.8～1.25）之內。
   ADR-120 的「單次最大調幅 ±10%」管的是每次調整量，本條管的是**累積後的絕對值**，兩者並存。
   係數缺漏、非數值或非正數時一律視為 1.0（不影響），不得讓壞資料放大調度量。
5. **可追溯**：套用係數的建議必須帶 `param_version`、`applied_coefficients` 與 `coefficient_mode`，
   讓後台看得出這次目標水位為什麼和基準不同。參數以單次批次查詢取得，不逐站打 DB。
6. **不改的東西**：觸發判斷的門檻與三層判斷（ADR-111）、緊急度公式（ADR-112）、
   人在迴圈確認閘門（ADR-302）、模型輸出語意（ADR-122）皆不變。係數只影響目標水位這一個量。

## 理由與判準

- **空轉的閉環比沒有閉環更糟**：會讓人誤以為系統已經在自適應。
- **可逆優先**：三態開關讓「接線」與「生效」分開，接線的風險趨近於零。
- **影子模式是必要的中間態**：係數目前只用「近 N 日 vs 全期流出比值」算出，沒有經過任何預測品質驗證，
  直接生效等於拿未驗證的數字改調度量。先跑影子模式累積差異資料才是負責任的順序。
- **護欄防呆**：參數來自資料管線，資料管線會壞；壞掉時應退回不影響，而不是放大。

## 考慮過的替代方案

### 方案 A：直接生效，不做三態

- 優點：最簡單，閉環立刻完整。
- 缺點：未驗證的係數立即改變派工量，且沒有中間觀察期。
- 未採用原因：風險與收益不對稱。

### 方案 B：把係數餵進模型當特徵

- 優點：讓模型自己學要不要用。
- 缺點：係數是人核准的營運參數，餵進模型會讓「人核准」失去意義，也違反 ADR-004 的分工。
- 未採用原因：破壞決策邊界。

### 方案 C：繼續不接線，等模型重訓後再說

- 優點：零風險。
- 缺點：ADR-120 的未解決項無限延後，且無法累積驗證係數的資料。
- 未採用原因：影子模式已足以把風險降到可接受。

## 影響與後果

### 正面

- ADR-120 的閉環從「存得進版本」進到「可被消費」，且每一步都看得到。
- 影子模式提供「係數到底該不該生效」的實證基礎。
- 壞參數有明確護欄，不會靜默放大調度量。

### 負面與代價

- 規則引擎多一個資料來源（參數表），多一次批次查詢。
- 建議輸出多三個欄位，前端需知道 `coefficient_mode` 才能正確呈現。
- 影子模式會算兩次目標水位，成本略增。

### 尚未解決

- 係數的正確性本身沒有驗證方法；需要影子模式累積資料後另行評估。
- 只接了 `base_outflow_coef` 與 `env_coef_weekend`；ADR-120 規劃的雨天、活動等情境係數 optimizer 尚未產生。
- 何時把模式從 `shadow` 切到 `on`，屬營運決定，不在本 ADR 範圍。

## 介面與相容性

`config.yaml` 的 `optimization` 新增 `係數套用模式`（預設 `off`）與 `係數上下限`。
規則引擎輸出新增 `coefficient_mode`、`param_version`、`applied_coefficients`，
`shadow` 模式另加 `shadow_target_available` 與 `shadow_quantity`；既有欄位不變、不移除，
未更新的前端維持原行為。資料庫無新表，沿用既有 `station_params`。

## 資安與隱私

無新增外部請求、憑證或個資。參數讀取為唯讀，寫入仍需 maintainer（ADR-304）。
係數值一律經型別與範圍檢查後才使用，不信任資料庫內容的合理性。

## 回復或取代方式

把 `係數套用模式` 設回 `off` 即完全回到接線前行為，不需回退程式碼。要改變套用位置或公式，另立新 ADR。

## 驗證方式

- pytest：`off` 模式輸出與未接線完全相同；`shadow` 模式決策不變但附影子值；`on` 模式目標水位依係數變動且方向正確；
  係數超出上下限被夾住；係數缺漏／非數值／非正數視為 1.0；參數查詢為批次一次取得。
- 既有 `test_rule_engine`、`test_target_level`、`test_params` 回歸不破壞。
- `git diff --check`。
