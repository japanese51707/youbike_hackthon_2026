# ADR-308：人力依歷史分派與雙人派工（司機＋隨車）

## 背景與問題

調度人力清單原本只有「流水號 + role_type（driver/stationed/depot_standby）」，seed 出來的
350 名調度員、30 名駐點員全部沒有預設責任區，開班時無法反映「哪個行政區實際需要多少人」。
主辦方只給 1–6 月官方歷史（S3 Parquet，約 1330 萬筆），需要一個可解釋的方法把人力分派到各區。

同時，派工單目前一趟只能指定「一台車 + 一名司機」。實際調度作業常是兩人一車（司機負責駕駛、
隨車負責搬運），系統缺少第二名人員的欄位與選擇介面。現有 task／資源占用／釋放全鏈路都以單一
`assigned_operator` 為前提，貿然改成「人員陣列」會牽動大量既有邏輯。

不決策的後果：人力配置與現場需求脫節（山區配過多、都會配不足）；派工單無法如實反映兩人作業，
現場執行與系統紀錄對不上。

## 決策

1. **人力依歷史工作量分派到行政區**（離線分析 + 啟動時 seed）：
   - 離線腳本 `analysis_workforce_allocation.py` 讀 S3 全 6 個月官方資料，算各行政區的
     「調度工作量分數 = 標準化(周轉量)×2 + 標準化(空站絕對次數) + 標準化(滿站絕對次數)」，
     以**周轉量為主導**；用最大餘數法把 350 名調度員整數分配到各區（每區至少 1）。
   - 駐點員 30 名依各區「高周轉尖峰站（日均周轉量 ≥ 全市 P75）」數分配，並取各區周轉量前列
     站作為駐點候選站。結果輸出 `docs/analysis/workforce_allocation.json`。
   - 後端啟動時 `seed_workforce_allocation()` 讀該 JSON，把已 seed 的調度員／駐點員預設分派到
     各區（調度員設 `current_district`；駐點員另設 `stationed_at`）。找不到分析檔則不預設分派。

2. **雙人派工（司機 + 可選隨車）**：
   - 保留 `assigned_operator`（司機／主責，維持既有單人全鏈路），**新增可選的**
     `assigned_escort`（隨車，第二名）。一趟仍只選一台車。
   - 隨車不影響載量／工時／路徑可行性計算（那些只依司機算），僅作為第二名資源在確認時一併
     占用、任務結束時一併釋放。司機與隨車不可為同一人。

## 理由與判準

- **正確性**：周轉量主導能貼近「哪裡真的需要人去調度」。第一版用「空站率／滿站率頻率」等權，
  導致偏遠山區（車長期不動、空／滿站率各約 50%）被標準化衝到滿分而配到最多人力；改用周轉量
  主導 + 空／滿站**絕對次數**後，都會區（板橋 41、新莊 23…）正確排前，山區降到合理低檔。
- **可逆性 / 低破壞**：雙人採「保留司機 + 新增可選隨車」而非「改成人員陣列」，既有單人 task、
  資源占用、釋放、可行性判斷全部不動，隨車是純增量欄位（NULL＝只派一名）。
- **可解釋**：分派用的是加權標準化 + 最大餘數法，非黑箱；分析結果落成 JSON，可覆核、可調權重。
- **交付時間**：離線算一次、啟動時讀 JSON，不在請求路徑上做重運算。

## 考慮過的替代方案

### 方案 A：人員改成陣列 `assigned_operators: []`

- 優點：語意最直接，未來要三人以上也容易。
- 缺點：既有 task schema、`validate_resources`、`release`、`claimed_by`、任務轉移、可行性重疊
  檢查全部以單人為前提，全鏈路都要改。
- 未採用原因：破壞面過大、風險高，與「最小改動、不動既有單人邏輯」的目標衝突。

### 方案 B：人力分派用「空站率／滿站率頻率」等權三指標

- 優點：直覺上空站／滿站頻繁＝需要調度。
- 缺點：頻率比例對低活動站有誤導性——偏遠山區站少、車不動，空／滿站率各約 50%，標準化後衝到
  滿分，反而配到最多人力。
- 未採用原因：實跑結果明顯不合理（山區配 29–31 人、都會偏少），改為周轉量主導 + 絕對次數。

## 影響與後果

### 正面

- 開班即有貼近現場需求的行政區人力配置，都會高需求區得到對應人力。
- 派工單能如實記錄兩人作業，現場執行與系統紀錄一致。
- 駐點員預設對到高周轉站，符合 ADR-116/118 駐點顧尖峰站的設計。

### 負面與代價

- 分派依賴離線分析檔（`workforce_allocation.json`）；資料或月份更新後需重跑腳本才會反映。
- 極低周轉但空／滿站事件累計仍多的山區（如平溪、石門）配額略偏高，屬可接受的近似。
- 分派為「開班前靜態預設」，實際任務指派仍以 `assign_district`（動態）為準；兩者語意需分清。

### 尚未解決

- 未接真實 YouBike 人力 API（seed 仍為流水號人員）；隨車是否需要獨立於司機的資格／工時規則
  尚未細化（目前與司機共用同一套可派檢查）。

## 介面與相容性

- **Schema**：`tasks` 表新增 `assigned_escort TEXT`（`schema.sql` + `connection.py` 冪等 migration
  `ALTER TABLE`，既有 DB 自動補欄）。`operators` 沿用既有 `current_district` / `stationed_at`。
- **API**：`/dispatch/build/{from-vehicle,from-station,emergency}` 的 request 新增可選
  `escort_id`；草稿回傳新增 `assigned_escort` 與 `start`（地圖起點座標）。皆為新增欄位，
  舊呼叫（不帶 escort_id）行為不變。
- **模型**：`DispatchTask` 新增 `assigned_escort: Optional[str]`。
- **前端**：組單面板司機下拉之下新增「隨車人員」下拉（選填、可清除、排除已選司機）；
  地圖用後端草稿的 `stations`（含座標、先取後補順序）+ `start` 畫路線。
- 遷移需求：既有 DB 由既有 migration 機制自動補 `assigned_escort` 欄，無需手動處理。

## 資安與隱私

- 分析腳本讀 S3 用最小權限（沿用 ADR-307 的 task role / 本機 profile），只讀不寫歷史資料。
- 人員資料仍為流水號、無真名無密碼，不涉個資。隨車欄位不引入新的對外邊界。
- `workforce_allocation.json` 僅含彙總統計與站名／sno，不含敏感資料，可進版控。

## 回復或取代方式

- 停用預設分派：移除或改名 `workforce_allocation.json`，`seed_workforce_allocation()` 會回
  `applied: False`，退回「不預設分派」的原行為。
- 停用雙人：前端不顯示隨車下拉、後端不帶 `escort_id` 即等同單人；`assigned_escort` 欄留空無害。
- 未來調整分派方法或接真實人力 API，以新 ADR supersede，不改寫本文件。

## 驗證方式

- 分析：`analysis_workforce_allocation.py` 實跑 S3 1330 萬筆，輸出各區配額（調度員合計 350、
  駐點員合計 30），都會區排前、山區降低，結果落 JSON 可覆核。
- seed：記憶體 DB 跑 seed 流程，驗證 347 名調度員（350−3 具名帳號）依工作量分派、30 名駐點員
  全分派且 `stationed_at` 對到真實 sno、OP-001~003 具名帳號不被動到。
- 雙人端到端：組單帶司機 + 隨車 → 草稿含 `assigned_escort` 與 `start` → 確認落地 task 含
  `assigned_escort` 且兩人轉 busy 綁同任務 → 釋放後兩人下工；司機＝隨車時自動忽略隨車。
- 回歸：後端既有 dispatch 測試套除兩個 pre-existing 失敗（與本次無關）外全通過；前端
  `npm run build` 成功。
