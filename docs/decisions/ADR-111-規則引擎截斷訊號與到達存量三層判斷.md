# ADR-111：規則引擎吃截斷訊號與到達存量三層判斷

## 背景與問題

模型（ADR-002/107）輸出各視野（30/60/90/120 分）的**淨變化 Δ 區間**（P10/P50/P90）。
規則引擎（ADR-004）吃預測、判斷是否調度。目前規則引擎的觸發邏輯有兩個缺口：

1. **未明確「現況 + Δ = 到達存量」的組裝點**：現行 `evaluate_station` 吃 `PredictionInterval`
   的 lower/upper_bound（語意為「到達存量區間」），但「模型出 Δ、誰負責加現況變成到達存量」
   的銜接模糊。owner 已釐清：到達存量 = **現況可借 + 預測淨 Δ**（Δ 帶正負，看調度員響應時間的視野）。

2. **未辨識「截斷需求」訊號（owner 核心洞察）**：在已空/已滿站，模型預測的 Δ 若使
   「現況 + Δ < 0（可借穿透底）」或「現況 + Δ 超過總柱（可還穿透頂）」，代表**真實需求被物理邊界壓抑**
   （想借但沒車繼續流出 / 想還但沒位繼續流入）。這種站不只是「空/滿」，是「缺很凶/爆很凶」，
   **必須最高緊急度調度**。現行邏輯可能只當普通觸發，漏掉這個強訊號。

不做決策的後果：最該優先派車的「需求被壓抑」站，緊急度被低估，調度資源錯配。

## 決策（proposed，待 owner 核准）

規則引擎對每站、每個視野，用「**到達存量 = 現況可借 + 預測淨 Δ**」做**三層判斷**：

| 層級 | 條件（到達存量 = 現況 + Δ） | 判定 |
|------|--------------------------|------|
| **最高緊急（截斷）** | 現況+Δ 使 **可借 < 0**（穿透空站底）或 **可還 < 0**（穿透滿站頂） | **一定調度**（補/取），標 `is_censored_demand=true`，最高緊急 |
| **警示** | 現況+Δ 進入安全緩衝範圍（快空/快滿，但未穿透邊界） | 需調度，緊急度依接近程度計算 |
| **正常** | 現況+Δ 在安全範圍內 | 不調度 |

**截斷判定（owner 定，精確式）**：
- 空站截斷：`現況可借 + 預測淨Δ < 0` → 需求被壓抑的缺車，最高緊急**補車**
- 滿站截斷：`(現況可借 + 預測淨Δ) > 總柱` 即可還位 < 0 → 需求被壓抑的爆滿，最高緊急**取車**
- 用哪個視野的 Δ：多視野各自算，取**最早穿透邊界的視野**當緊急關鍵（越早穿透越急，見緊急度）。

**組裝點與 raw/夾過兩套值（owner 核准，2026-09-04 澄清）**：
- **到達存量的組裝在 predictor 層**（現有介面約定 predict 輸出「到達存量」而非 Δ；ADR-005 契約）。
  即 predictor 負責 `到達存量 = 現況可借 + 模型預測Δ`，規則引擎直接吃到達存量。
- **★predictor 須輸出兩套值，不得只給夾過的值**（owner 核心要求，避免假數據蓋掉截斷訊號）：
  - **raw（照實，可為負 / 可超過總柱）**：供規則引擎判斷截斷——`raw < 0` 即穿透空站底、
    缺口 = |raw|；`raw > 總柱` 即穿透滿站頂。**這是誠實的預測，不夾。**
  - **bound（夾過 [0, 總柱]，物理可能值）**：供前端顯示（顯示 -5 台對民眾無意義；顯示 0 台
    + 最高緊急標記才合理）。
  - **禁止只給夾過值**：把穿透底的 -5 夾成 0 會蓋掉「缺 5 台的壓抑需求」訊號，是假數據。
- 需擴充 `PredictionInterval` 加 raw 欄位（新增欄位、向後相容，通知 B）。

**職責邊界（守 ADR-004）**：
- 規則引擎**只辨識三層狀態 + 標記** `is_censored_demand`／緊急層級旗標，**不自己算緊急度分數**
  （緊急度分數計算仍在 urgency 層，見 dispatcher）。規則引擎產出「這站屬哪一層 + 為什麼」，
  urgency 用這個層級當輸入算分數，dispatcher 排序。
- 「需調度 ≠ 一定緊急」（警示層可能只是提醒）；「截斷層一定緊急且必須調度」（owner 釐清）。

**不改**：AI 只估計、規則引擎決策（ADR-004）；截斷訓練排除（ADR-105，訓練層，本 ADR 是上線層）；
confidence_tier 只當排序次要鍵不進觸發（ADR-109）。

## 理由與判準

- **正確性/對齊系統目的**：截斷訊號直接指向「最該派車的站」，是系統存在理由的核心。
- **可解釋**：三層判斷 + 中文 reason（「現況 0 台、預測仍將流出 5 台，需求被壓抑，最高緊急補車」）
  對調度員直覺、簡報好講。
- **職責單一**：規則引擎辨識、urgency 算分、dispatcher 排序，各層不越界（NFR-1/ADR-004）。
- **可逆**：三層邏輯為規則引擎內部，config 可調安全緩衝門檻。

## 考慮過的替代方案

### 方案 A：截斷只當緊急度加成，不改觸發
- 優點：最保守，不動觸發條件。
- 缺點：空站雖多半已被「到達存量低」觸發，但「穿透邊界」的極端缺口沒被明確標為最高級。
- 未採用原因：owner 定「穿透邊界一定最高緊急」，需明確標記層級，非僅加成。

### 方案 B（採用）：三層判斷，截斷穿透邊界=最高緊急且必調度
- 優點：直接落地 owner 洞察，最該派車的站被正確標記。
- 缺點：需明確定義三層門檻與到達存量組裝。
- 採用。

### 方案 C：規則引擎直接算緊急度分數
- 未採用：違反 ADR-004 職責分層（緊急度在 urgency 層）；規則引擎只辨識層級。

## 影響與後果

### 正面
- 需求被壓抑的站被最高緊急標記，調度資源優先投對地方。
- 「現況+Δ=到達存量」的組裝點明確，模型 Δ 到規則引擎的銜接清楚。

### 負面與代價
- 規則引擎輸出新增欄位（is_censored_demand／urgency_tier），下游 urgency/dispatcher 需接。
- 需與 B 的真實 predictor 整合時確認 Δ 的正負號與視野對齊（目前 MockPredictor）。

### 尚未解決
- 緊急度分數的實際公式（urgency 層，本 ADR 只定「截斷=最高層級」的輸入）待另開 ADR-112：
  owner 已提輸入因素——穿透時機(30/60/90/120,越早越急)/嚴重層級(全空滿>快空滿>正常)/
  該時段人流比例(歷史前後2小時平均總淨流量,越高越急)/當下是否已全空滿/穿透幅度(缺口深淺)。
- 多視野都截斷時：取**最早穿透邊界的視野**當緊急關鍵（已定，見上）。
- 安全緩衝門檻（快空/快滿的界線）沿用 config.trigger，值待校準。

## 介面與相容性

- `evaluate_station` 輸出新增 `is_censored_demand`（bool）與 `urgency_tier`（censored/warning/normal）。
- 不改 PredictionInterval 結構；但明確「到達存量 = 現況 + Δ」的計算歸規則引擎（或組裝層）。
- urgency/dispatcher 需讀新欄位（通知 A/C；屬後端內部，不改對外 API 契約主體）。

## 資安與隱私

- 無（純決策邏輯）。

## 回復或取代方式

- 三層判斷為規則引擎內部邏輯，可 config 開關/還原；設計變更以新 ADR supersede。

## 驗證方式

- 單元測試：構造「空站+預測續流出」→ 應標 is_censored_demand + 最高緊急補車；
  「滿站+預測續流入」→ 最高緊急取車；「快空未穿底」→ 警示層；「安全範圍」→ 不調度。
- 確認緊急度分數仍由 urgency 層算（規則引擎只給層級，守 ADR-004）。
- 既有 test_rule_engine 全綠（不破壞現有觸發）。
