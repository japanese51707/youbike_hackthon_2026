# ADR-206：調度面板決策流資訊架構（三入口組單＋執行追蹤）

## 背景與問題

ADR-205 把調度面板定為「無捲動固定視窗」，版面是「工具列＋KPI 條＋地圖＋右側三分頁（調度建議／即時警示／缺口榜）」。
實際檢視後，owner 認為此版面仍**發散、缺乏重點**：三個並排的同級資訊塊，沒有引導調派員「下一步該做什麼決定」。

回到使用者故事：這頁的唯一使用者是**控制室的調派員（後台）**，他的工作是一個閉環——
發現哪些站快出事 → 決定怎麼派 → 預覽 → 送出讓司機接單 → 追蹤執行。
後端 ADR-119（互動式派工單組建）已把「怎麼派」定成**三入口 + 草稿→預覽→確認**，前端應對齊同一心智模型，
而非各做各的。ADR-205 的並排分頁無法承載這條決策流，需要重新定義調度面板的資訊架構。

## 決策（proposed，待 owner 核准）

將調度面板從「並排資訊塊」改為**「一張地圖（舞台）＋右欄狀態機（待命態／組單態）」的決策流架構**，
對齊 ADR-119 的三入口與預覽確認，並加入執行追蹤。

### 一、單一使用者與決策流

- **使用者**：控制室調派員（司機、長官不在此頁）。
- **決策流（五步）**：`發現 → 組單(三入口) → 預覽(草稿+預估) → 送出(確認→進司機池) → 追蹤(執行監控)`。

### 二、版面

- 頂部：極簡（標題＋少數關鍵數字），不放大量操作。
- 主區：左＝**地圖（永遠在的舞台）**，右＝**會換狀態的工作區**。
- 地圖圖層：站點依緊急度上色（**站數完全動態**）＋調度車位置（mock 示意）＋區域死結紅字警報。

### 三、右欄・待命態（平常監控）

1. **死結救火警報**（ADR-118 區域連續死結）置頂，最該第一眼看到 → 點擊進「緊急出車」。
2. **需調度清單（緊急站排行）**：緊急度排序；**缺口榜併入此清單**（不再獨立分頁）。
   每列＝站名／空滿狀態／緊急度／補或取／數量／預測是否撞 0 或撞滿。點某站 → 進「站找車」。
3. **進行中任務追蹤（做深）**：每張已送出的單顯示 指派車＋人、逐站進度（stop_status）、
   預估到達／完成、目前在第幾站，並含一個**狀態生命週期欄位**（見第六點）。

### 四、右欄・組單態（右欄整個接管，非抽屜）

三入口都匯入同一條精靈流程（對齊 ADR-119）：

- **入口觸發**：地圖點車＝以車為起點；清單點站＝以站為起點；死結警報＝緊急出車。
- **步驟**：
  1. 選資源（以站/緊急時系統列候選車序：該區閒置 → 鄰近區閒置 → 總站待命；人員池＝該區閒置＋總站待命）。
  2. 系統算「**先載後放**」路線（先滿站取車至接近載運上限 → 再空站放車），畫在地圖上。
  3. **預估卡**：總距離／交通時間／作業時間／總載運量（≤ 車輛 max_capacity，預設 15）／緊急度加總。
  4. 微調：改行政區重算、加減站（順序調整深度先做輕量）。
  5. **預覽 → 確認**（人在迴圈閘門）。確認後右欄收回待命態，該單進「進行中任務追蹤」。

### 五、資料與 mock

- **站數完全動態**：後端給幾站就渲染幾站（地圖／清單／統計皆不寫死站數）；**不提供站點增刪 UI**。
- **補極簡 mock 車輛**（對齊 ADR-114 欄位）：`vehicle_id` / `max_capacity`(15) / `status`
  (available/dispatched/maintenance/standby) / `current_district` / `is_reserve`；供三入口與載運量成立。
- 沿用既有 mock（stations／recommendations／operators(含 current_location)／tasks）。

### 六、執行追蹤的狀態生命週期（owner 第 3 點）

- 追蹤清單需有明確**狀態欄位**呈現送出後的變化：
  `已送出/待接單(assigned) → 司機已接 → 執行中(in_progress) → 完成(completed)`，逐站帶 `stop_status`。
- mock 階段以**示意方式**呈現狀態推進（標「示意」），做**豐富靜態 + 依 stop_status 的示意進度**，
  **不做假 GPS 移動**。

### 不改 / 範圍界線

- **不 supersede ADR-205**：四頁角色導向與無捲動原則不變；本 ADR 只細化「調度面板」該頁的資訊架構，
  ADR-205 加註指向本 ADR。
- **本分支只做調度面板**：確認送出後僅標「已送出、進入司機池」並留在追蹤清單；
  「司機頁真的接走該單」的跨頁 mock 串接**不在本 ADR 範圍**（另分支/另議）。
- **不串接後端**：本階段全走前端 mock；真實 API 對接（httpAdapter、X-Operator-Id、horizons[] 等）另議。
- 守 ADR-004：前端不自行做調度決策；「先載後放」為前端**示意排序**，真正最優組單在後端 `dispatch_builder`。

## 理由與判準

- **聚焦**：狀態機讓畫面永遠只強調「該做的下一個決定」，消除並排同級塊造成的發散。
- **前後端對齊**：三入口與預覽確認直接對映 ADR-119，降低整合落差與重工。
- **貼合真實操作**：調派員是互動組單（看站況一單一單組），非讀一堆並排報表。
- **人在迴圈**：預覽→確認為唯一送出閘門，符合 steering §6 與 ADR-004。
- **健壯性**：站數動態渲染，避免寫死；對接真實 1500+ 站時不需改結構。

## 考慮過的替代方案

### 保留 ADR-205 現版面（建議／警示／缺口榜三分頁並排）
- 缺點：發散、無決策引導、缺口榜與緊急站排行重疊。未採用（正是本 ADR 要解的問題）。

### 組單用浮層抽屜而非右欄接管
- 缺點：組單是調派員當下的主要動作，抽屜較不沉浸、資訊空間受限。owner 選右欄接管。未採用抽屜。

### 三入口拆成三個分頁／三頁
- 缺點：割裂同一條「預覽→確認」流程，重複 UI。未採用，改為同一精靈的三個進入點。

### 提供站點新增/刪除 UI
- 缺點：非調派員每日決策、稀釋焦點。owner 明確不要，改為純動態渲染。未採用。

## 影響與後果

### 正面
- 調度面板聚焦於調派員決策流；與後端 ADR-119 對齊；站數動態更健壯。

### 負面與代價
- 需重寫 DashboardPage 的右欄為狀態機，新增組單精靈與追蹤清單元件、極簡 mock 車輛 fixture。
- 三入口的先載後放示意排序、狀態示意推進需前端實作（皆標示意）。

### 尚未解決
- 站點順序人工微調的互動深度（先做輕量：加減站/改區重算）。
- 跨頁「司機接單」的 mock 串接（另議）。
- 真實後端對接（httpAdapter/身分/horizons[]）留待整合階段。

## 介面與相容性

- 影響前端 `DashboardPage` 及其子元件；不改後端契約、不改 payload。
- 新增前端 mock `vehicles`（對齊 ADR-114 欄位），不影響既有 mock 結構。
- ADR-205 維持 accepted，加交叉引用指向本 ADR（調度面板段細化）。

## 資安與隱私

- 確認送出於真實環境需 dispatcher/controller 權限（比照 /dispatch/confirm 閘門）；mock 僅模擬。
- 前端操作不進後端 payload、不寫 DB；mock 車輛/人員用編號，不含 PII。
- 無新增對外請求。

## 回復或取代方式

- 回退到 ADR-205 原調度面板版面即可；設計變更以新 ADR supersede 本 ADR。

## 驗證方式

- `npm run build` 通過。
- 待命態：死結警報、需調度清單（缺口榜已併）、進行中任務追蹤三塊正確呈現。
- 組單態：三入口各自可產草稿 → 預覽（含距離/時間/載運量/緊急度加總）→ 確認 → 單進追蹤清單。
- 追蹤：狀態欄位可見 assigned→執行中→完成 的示意推進；逐站 stop_status 呈現。
- 動態站數：改變 mock 站數，地圖/清單/統計自動反映，無寫死。
- 示意標註齊全（車輛位置、先載後放排序、執行進度、確認閘門）。
