# ADR-312：班別人力配置（三班×行政區）與雲端固定位址

## 背景與問題

ADR-308 已把調度人力依歷史工作量分派到各行政區，但**沒有分班別**——所有人視為同時在線。
實際營運是三班輪值（ADR-116 已定義 morning/evening/night 三班時段），需要把 350 名調度員與
30 名駐點員按班別分配，且班內仍要對應行政區，才能反映「哪個時段、哪個區需要多少人」。

另外，雲端後端跑在 ECS Fargate，每次重新部署 public IP 都會變動，導致前端 `.env.example`
（別人從 GitHub 拉的連線設定）要一直更新，demo 也不穩。需要一個固定對外位址。

## 決策

1. **班別人力配置（三班 × 行政區）**：
   - operators 表新增 `shift` 欄位（morning/evening/night）。
   - 各行政區的人力配額（ADR-308 周轉量主導）再依 config `shift_allocation` 比例切三班：
     **早班 40%、晚班 35%、大夜 25%**（合理化依通勤負荷：早班含早高峰、空滿站最多 → 最多；
     晚班含晚高峰 → 次多；大夜離峰做跨區大宗復原 → 最少但仍需一定量）。
   - 切分用最大餘數法保整數；調度員每區每班配額夠時每班至少 1，配額不足的小區優先放早班→晚班→大夜。
   - 駐點員同樣分三班顧尖峰站。總部預備人力（depot_standby）維持不分區不分班（機動支援）。
   - 離線腳本 `analysis_workforce_allocation.py` 輸出 `driver_allocation_by_shift` /
     `stationed_allocation_by_shift`；`seed_workforce_allocation()` 依此設 shift + current_district。
   - 前端「分派任務狀況頁」人力清單改以班別分頁（早/晚/大夜）呈現，班內再依行政區分組。

2. **雲端固定位址（NLB + Elastic IP）**：
   - 建 Network Load Balancer（internet-facing）+ Elastic IP + target group（ip 模式，TCP 8000，
     HTTP `/health` 健康檢查）+ listener；ECS service 掛該 target group，task 由 ECS 自動註冊。
   - 對外位址為 EIP，**ECS task 重啟／重新部署不再變動**。ECS service 網路限定在 NLB 所在
     單一可用區（us-east-1b）的 subnet（單 AZ 單 EIP，維持「單一固定 IP」）。
   - 讓 `docs/analysis/workforce_allocation.json` 進 image（.dockerignore 放行、Dockerfile 複製到
     `/docs/analysis/`），雲端啟動 `seed_workforce_allocation` 才讀得到，行政區×班別分派在雲端生效。

## 理由與判準

- **合理化 / 可解釋**：班別比例對應通勤尖峰負荷，非平均分配；沿用既有周轉量配額再切班，不另造模型。
- **低破壞**：`shift` 為新增可選欄位（migration 補欄），不影響既有單人/派工/釋放邏輯。
- **固定位址正確性**：NLB + EIP 是雲端「對外固定、後端可換」的標準解；task 重啟由 ECS 重新註冊，
  對外 IP 不變。單 AZ 單 EIP 換取單一固定 IP，對 demo 足夠（不需跨 AZ 高可用）。
- **可攜性**：workforce json 進 image 後，別人從 GitHub 拉、前端指固定 IP，即看到正確的班別×行政區分派。

## 考慮過的替代方案

### 班別比例：平均三分（各 33%）

- 優點：最簡單。
- 未採用原因：早/晚有明顯尖峰、大夜離峰，平均分配不符實際負荷。

### 固定位址：EIP 直接綁 Fargate task ENI（不用 NLB）

- 優點：不必建 NLB，最省。
- 缺點：task 重啟 ENI 變，EIP 要重新關聯，不是真正固定。
- 未採用原因：與「重啟不變」的目標衝突。

### 固定位址：ALB（應用層）

- 優點：支援 path routing、HTTPS 終結。
- 缺點：本專案只需單一後端 TCP 轉發，ALB 較重且不直接支援固定 IP（要另接 EIP）。
- 未採用原因：NLB + EIP 更貼合「固定 IP + 單一後端」需求。

## 影響與後果

### 正面

- 人力配置反映三班輪值與尖峰負荷，分派任務狀況頁可依班別檢視各區人力。
- 雲端對外位址固定，`.env.example` 不必再隨部署更新，別人拉 GitHub 即可穩定連線。

### 負面與代價

- 單 AZ 部署：該 AZ 故障時服務中斷（demo 可接受；正式需跨 AZ + 多 EIP 或 DNS）。
- 多了 NLB + EIP 雲端資源（賽後需一併關閉，避免 EIP 閒置計費）。
- 班別為靜態預設分派，實際輪值換班未接真實排班系統。

### 尚未解決

- 未接真實人力排班 API；跨午夜大夜班的實際交接、跨班支援規則未細化。

## 介面與相容性

- **Schema**：operators 新增 `shift TEXT`（connection.py 冪等 migration 補欄）。
- **設定**：config 新增 `shift_allocation`（morning/evening/night 比例）。
- **分析輸出**：`workforce_allocation.json` 新增 `driver_allocation_by_shift`、
  `stationed_allocation_by_shift`、`meta.shift_ratios`、`meta.shift_totals`。
- **API**：`GET /operators` 回傳因 migration 自動帶 `shift` 欄位；無其他契約變更。
- **部署**：Dockerfile 複製 workforce json 到 `/docs/analysis/`；.dockerignore 放行該檔。
  雲端新增 NLB `youbike-backend-nlb`、target group `youbike-backend-tg`、EIP、listener。
- 前端 `.env.example` 後端位址改為 NLB EIP 固定位址。

## 資安與隱私

- NLB 只轉發 8000；SG 沿用既有（只開 8000）。EIP 為公網固定位址，後端仍是受控 demo。
- 人員資料仍為流水號、無個資。workforce json 僅含彙總統計與站名/sno，可進 image。

## 回復或取代方式

- 班別：config `shift_allocation` 可調比例；不分班則移除 by_shift 欄位，seed 退回只設區。
- 固定位址：解除 service 的 target group、刪 NLB/EIP/target group 即回到直接 public IP。
- 調整班別法或接真實排班，以新 ADR supersede。

## 驗證方式

- 分析：腳本實跑 S3 產各區各班配額（早 136/晚 121/夜 93），小區優雅退化。
- seed：本機 seed 驗證調度員早 134/晚 120/夜 93、板橋 16/14/11、駐點員分三班、總部預備不分區。
- 雲端：透過固定 IP 驗證資料源 youbike_official（1606 站 live）、人力班別×行政區分派、Bedrock
  source=bedrock、NLB target healthy。
- 回歸：後端測試套除兩個 pre-existing 失敗外全通過；前端 `npm run build` 成功。
