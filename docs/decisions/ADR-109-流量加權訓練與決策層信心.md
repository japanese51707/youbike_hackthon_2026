# ADR-109：流量加權訓練（樣本權重）與決策層信心標註

## 背景與問題

多輪實測（ADR-002 消融、ADR-108 新舊站分報）反覆撞到同一個結構性現象：

- **目標 Δ 約 78% 為 0（零膨脹）**，其中大量來自**低流量站**——這些站本來就沒什麼借還，時段淨變化長期接近 0。
- 後果一：低流量站的大量 0 把消融數字洗淡（分位數 P50 全被 0 主導 → 所有因子 +0.00%，已於 ADR-002 改用 L2 探針緩解）。
- 後果二：**模型把等量的擬合精力花在「反正都是 0」的低流量站**，稀釋了它在高流量站（真正需要調度、因子影響看得清楚）的表現。
- 後果三（ADR-108 佐證）：6 月新站 MAE 反而低於老站，正是因為新站多為低流量、Δ 小天生好預測——**低流量 = 低資訊量**，卻在等權訓練/評估下被當成一般樣本。

核心洞察（owner）：**人流量大的站，越真實反映因子影響，應在模型中佔更大比重；人流量小的站，對模型的影響應變小。**

不做決策的後果：模型持續被低資訊量樣本稀釋，因子消融與整體準度都低估了「在真正重要的站上」的能力。

## 決策（proposed，待 owner 核准）

分三個機制，機制 A 為核心，機制 C 受既有 ADR-104 約束。

### A. 訓練樣本權重（核心）

- 訓練 LightGBM 時給每列 `sample_weight`，依該站**訓練期周轉量**決定：高周轉站權重大、低周轉站權重小。
- 效果：模型更努力擬合高流量站（誤差被放大），低流量站猜錯罰得輕。直接實現 owner 洞察。

### B. 周轉量定義（流量的正確度量）

- **周轉量 turnover = |available_bikes(t) − available_bikes(t−1)| 的累加/平均**（每站，訓練期）。
- 用**絕對變化累加**，不是淨變化 Δ——淨變化會被「借出又還回」相抵洗成 0，無法反映真實人流；絕對變化才是真周轉。
- **★防洩漏鐵律**：只用訓練期（1~5 月）計算，6 月驗證期**不參與**權重計算。算好每站一個值 merge 回 frame。
- 以 station_key（ADR-108 歸併後主鍵）計算。

### C. 決策層信心標註（受 ADR-104 約束）

- 依訓練期周轉量分級產出每站 `confidence_tier`（高/中/低流量）。
- **★紅線（守 ADR-104，owner 2026-09-03 確認）**：`confidence_tier` **只作為排序與信心標註**，
  **不得**進入「是否叫調度員來調車」的觸發判斷。ADR-104 已定：需求密度/流量導出的決策輸出是**加分項，非觸發依據**。
- 若未來要讓信心進入觸發邏輯，須另開 ADR 修正 ADR-104，不在本 ADR 範圍。

### 權重轉換方式（三方案對比 → 實測後 A 不採用）

直接用 turnover 當權重會讓超高流量站碾壓模型，故跑三方案對比：
- 方案 1：`weight = 1`（等權，現況基準）
- 方案 2：`weight = log(1 + turnover)`（溫和）
- 方案 3：`weight = turnover`（線性）

**實測結論（2026-09-03 全量，見下方驗證段）：三方案中「等權」幾乎全面最佳，
加權在高流量站/全樣本/Δ≠0 皆略差，低流量站明顯被犧牲。故機制 A（樣本權重）不採用。**

### 定案（owner 2026-09-03 核准，依實測負結果）

- **機制 A（樣本權重）：不採用**。實測證明加權沒幫助反而略差——LightGBM 已內建處理樣本重要性，
  且低流量站的 Δ=0 是「何時不需調度」的有效訊號，加權犧牲它反而拖累整體。保留等權訓練。
- **機制 B（周轉量定義）：保留**。`station_turnover`（訓練期 |Δ| 平均）仍用於機制 C 與簡報。
- **機制 C（決策層信心）：採用並落地**。`confidence_tier`（high/mid/low）接入 dispatcher 排序，
  當**同緊急度分數時的次要排序鍵**（high 流量站優先）。★不進 rule_engine 觸發判斷（守 ADR-104）。

## 理由與判準

- **正確性/資訊量**：低流量站 = 低資訊量，等權訓練是把雜訊當訊號；加權讓模型專注在有訊號的站。
- **對齊系統目的**：需要調度的正是高流量、會空/滿的站，加權方向與系統存在理由一致。
- **可解釋**：「模型更重視高周轉站」對評審是直覺、好講的設計。
- **可逆**：權重是 config，可關可調；不改模型選型（ADR-002）與核心約束（ADR-004）。

## 考慮過的替代方案

### 方案 A：不加權，等權訓練（現況）
- 優點：最簡單。
- 缺點：低流量站稀釋高流量站表現；消融與準度低估關鍵區能力。
- 未採用原因：正是本 ADR 要解的問題。

### 方案 B：直接刪除低流量站
- 優點：一勞永逸去雜訊。
- 缺點：低流量站仍需預測（也可能突然變熱，或本身就是「不需調度」的有效訊號）；硬刪破壞覆蓋完整性。
- 未採用原因：加權比硬刪溫和且可逆；「不需調度」本身是有價值的負樣本。

### 方案 C：只改評估指標（weighted MAE），不改訓練
- 優點：不動模型。
- 缺點：只改「怎麼看分數」，模型本身仍被稀釋。
- 未採用原因：治標；我們已有 Δ≠0 切面部分達成評估層目的，本 ADR 要治本（訓練層）。

## 影響與後果

### 正面
- 模型在高流量、需調度的站上表現提升（待實驗證實）。
- 因子消融更能反映因子在「重要站」上的真實影響。
- confidence_tier 提供決策層可用的信心標註（加分項）。

### 負面與代價
- 權重過強會讓極端站主宰、低流量站預測變差——用 log 溫和轉換 + 對比實驗控制。
- 增加訓練期周轉量計算與 merge（一次性，成本低）。
- sample_weight 讓 MAE 的絕對值不再跨方案直接可比，需固定同一評估口徑。

### 尚未解決
- 三方案權重哪個最佳，待對比實驗定（本 ADR 核准後跑）。
- confidence_tier 的分級界線（高/中/低的 turnover 門檻）待資料分布出來後校準。
- 是否對評估也採加權（機制 C 的評估版）暫不做，先保持評估口徑一致。

## 介面與相容性

- 影響 `feature_pipeline.py`（周轉量 + 權重欄）、`train.py`（fit 帶 sample_weight + 三方案對比）。
- `confidence_tier` 若要對外，需確認不破壞 core/interfaces.py 的 PredictionInterval 契約；本輪先在內部產出，不改 API。
- **不改** ADR-002（選型）、ADR-004（AI 只估計/規則引擎決策）、ADR-104（需求密度非觸發依據）、ADR-105（截斷處理）。權重與截斷互補：截斷排除假樣本，權重調整真樣本的重要度。

## 資安與隱私

- 無（純訓練權重與站點統計，皆公開場站行為資料）。

## 回復或取代方式

- 樣本權重與 confidence_tier 皆為 config 開關，可還原為等權；設計變更以新 ADR supersede。

## 驗證方式

- **防洩漏**：實測印證周轉量只用訓練期（6 月資料不參與權重計算）。
- **三方案對比**：等權/log/線性，各報全樣本/已空區/Δ≠0/高流量站/低流量站 MAE。
- **關鍵區改善**：確認高流量站 MAE 改善，且低流量站未被嚴重犧牲、極端站未主宰整體。
- **ADR-104 合規**：確認 confidence_tier 未接入任何調度觸發判斷。

### 實測結果（2026-09-03 全量 1583 站 × 6 月，L2 探針，含天氣）

**防洩漏印證通過**：turnover 由訓練期 1552 站算；驗證期 turnover=0 的列僅 1.0%
（就是 6 月才上線、訓練期無資料的新站，符合預期，無洩漏）。

**三方案 MAE 對比（節錄 30/120 分，越低越好）**：

| 視野 | 方案 | 全樣本 | 已空區 | Δ≠0 | 高流量站 | 低流量站 |
|------|------|--------|--------|------|---------|---------|
| 30分 | 等權 | **1.585** | **3.768** | 2.371 | **2.390** | **1.012** |
| 30分 | log | 1.614 | 3.998 | 2.371 | 2.403 | 1.069 |
| 30分 | 線性 | 1.619 | 3.921 | 2.373 | 2.408 | 1.070 |
| 120分 | 等權 | **3.002** | 3.436 | **3.603** | **4.629** | **1.792** |
| 120分 | log | 3.052 | 3.535 | 3.619 | 4.645 | 1.885 |
| 120分 | 線性 | 3.070 | **3.395** | 3.635 | 4.663 | 1.895 |

**負結果解讀（有價值）**：
- **等權幾乎全面最佳**，尤其在加權最該幫到的「高流量站」，等權反而每個視野都最好。
- 加權唯一零星贏：僅「線性的已空區長視野」（120 分 3.395 < 3.436），不穩定、不足以採用。
- 低流量站被加權明顯犧牲（符合預期），但沒換到高流量站的改善——取捨不划算。
- **研判**：LightGBM 已自行處理樣本重要性；且低流量站的 Δ=0 是「何時不需調度」的有效訊號，
  加權砍它反而拖累模型對「不會變」的判斷。`station_slot_p50` 也已把站點活躍度編碼進模型。
- **這是用實驗誠實否決一個看似合理直覺的案例**——記錄負結果比只記成功更有治理價值。

### 機制 C 落地驗證

- rule_engine `_mk_rec` 輸出加 `confidence_tier` 標註欄；觸發判斷（evaluate_station）完全不讀它 → 守 ADR-104。
- dispatcher 排序 key 加 `_tier_rank`（high=0/mid=1/low=2）當同分次要鍵；不改觸發、不改緊急度分數。
- 既有測試全綠（backend/tests 43 passed），確認接入未破壞規則引擎/dispatcher 行為。
