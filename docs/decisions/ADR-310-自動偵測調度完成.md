# ADR-310：自動偵測調度完成（免人工回報，達標即結）

## 背景與問題

調度員執行派工單時，目前需要在每一站人工回報「拉了幾台／放了幾台車」（`report_station`
帶 `actual_available`），系統才知道該站處理完、才能推進任務與結案。這增加現場負擔，也讓
任務進度依賴人工操作的即時性。

系統其實已握有判斷該站是否處理完的資料：官方即時站況會回傳每站的可借車數，`observations.py`
也已維護每站的即時序列。派工單本身帶有明確的目標水位（`target_available`）與方向（補車／取車）。
因此「某站是否已達派工目標」是可以從即時站況自動推斷的，不必等人回報。

不決策的後果：現場需逐站手動回報，任務進度更新滯後、易漏報，demo 也少一個能自動運轉的亮點。

## 決策

新增**自動偵測調度完成**：背景輪詢官方即時站況，對進行中任務的待處理站判斷是否已達派工目標，
達標即自動標記該站完成並推進任務（**方案 A：直接自動完成**），最後一站完成時走既有鏈路自動
結案並釋放人車。判斷規則：

- **補車站**：可借車數相對任務開始時的基準「上升」，且逼近目標（現值 ≥ `target_available` − 容差）。
- **取車站**：可借車數「下降」，且逼近目標（現值 ≤ `target_available` + 容差）。
- **最小變化量門檻**：車數變化需至少達派工量（`quantity`）的一定比例（預設 0.5），濾掉自然借還波動。
- 基準值取即時序列中「任務開始後最早的觀測點」；序列不足時退回組單當下記錄的 `current_available`。

**判斷哲學**：不論那批車是調度員搬的、還是剛好有一批人借／還造成的，只要該站已達目標水位，
對該站而言調度需求即已消化，任務對該站即完成。與既有 `_demand_resolved`（抽離站點時判斷需求
是否消化）同一思路。

自動偵測代呼叫既有 `report_station(auto=True)`，完全複用既有的完成標記／載量結算（ADR-123）／
結案釋放鏈路，不另造寫入路徑；以 `system-auto` 標記 `reported_by` 與稽核，與人工回報區分。
僅在真實資料源（非 mock）且 config 開關 `auto_detect.enabled` 開啟時運作。

## 理由與判準

- **正確性 / 語意一致**：以「達目標水位＝需求消化」為判準，與規則引擎、`_demand_resolved` 的
  既有語意一致；有明確 target 方向的監督式比對，誤判風險遠低於無標籤的異常偵測。
- **低破壞 / 可維護**：複用 `report_station` 與狀態機，不重寫結案／釋放；判斷核心為純函式
  （`reached_target`）可獨立測試。
- **與人工回報天然互斥**：`report_station` 對已非 pending 的站會擋（`DispatchConflict`），
  背景迴圈吞掉該例外，人工與自動誰先誰後都不會產生資料衝突。
- **可控 / 可逆**：config 開關 + 僅真實源啟用；關掉即回到純人工回報。
- **交付時間**：背景輪詢對齊官方源刷新頻率，不在請求路徑上做重運算。

## 考慮過的替代方案

### 方案 A：偵測到達標即直接自動完成（採用）

- 優點：真正免人工回報、進度即時、最順。
- 缺點：偵測有誤判可能（剛好一批人借還）。
- 未採用原因：無——這是採用方案。誤判的代價可接受：owner 明確認同「不論車是誰移動的，
  只要接近目標，對該站就是減少了調度需求」，故直接完成合理。

### 方案 B：偵測後只標「疑似完成」，仍需人工確認才結案

- 優點：人在迴圈、最保守。
- 缺點：沒有真正免除人工操作，只是把回報換成確認；進度仍依賴人。
- 未採用原因：與「免人工回報」的目標相違；且達目標水位本身就代表需求消化，額外的人工確認
  價值有限。

## 影響與後果

### 正面

- 調度員不必逐站回報，任務進度隨即時站況自動更新、自動結案。
- 稽核可用 `system-auto` 區分自動與人工回報，保有可追溯性。

### 負面與代價

- 可能把「非調度造成的達標」也計為完成——但依決策哲學這是刻意接受的（需求已消化）。
- 自動完成用即時可借車數當 `actual_available`，載量結算（ADR-123）以此為準；若即時值與實際
  搬運量有落差，收車載量估計會帶入該誤差（原本人工回報也有同類風險）。
- 背景輪詢新增一個 daemon thread 與週期性即時站況抓取（已對齊官方源刷新頻率，負擔有限）。

### 尚未解決

- 未接車輛即時定位；「基準值」目前用任務開始後首個觀測點或組單當下車況，若任務開始前站況
  劇烈變動，基準可能略偏。容差與最小變化比例為經驗預設，未來可依實測調校。

## 介面與相容性

- **API / 行為**：`report_station` 新增可選參數 `auto=False`；`auto=True` 跳過 `require_executor`、
  `reported_by` 標 `system-auto`、stop 加 `auto_detected` 旗標。舊呼叫（人工回報）行為不變。
- **資料**：`tasks` 的 route 每站新增持久化欄位 `current_available`（自動偵測基準來源）；
  route 以 JSON 存於既有 `route_json`，無需 schema 遷移。
- **設定**：`config.yaml` 新增 `auto_detect`（`enabled` / `輪詢間隔_秒` / `逼近容差_台數` /
  `最小變化比例`）。預設 `enabled: true`，但僅真實源生效。
- **啟動**：`main.py` lifespan 於真實源時啟動背景 daemon thread，關機時停止。
- 前端無強制改動；`auto_detected` 旗標可供前端標示「系統自動完成」（本 ADR 不含前端變更）。

## 資安與隱私

- 自動偵測只讀官方即時站況（沿用既有資料源與 TLS 驗證），不新增對外邊界。
- 以任務既有 `assigned_operator` 身分過權限、`system-auto` 標記來源，稽核留痕；不繞過 dispatcher
  權限模型（`auto=True` 僅跳過「執行者本人」檢查，因偵測非執行者操作）。
- 不涉個資；不寫入猜測性載量（缺數字時 ADR-123 既有邏輯會把載量標未知）。

## 回復或取代方式

- 關閉：`config.yaml` 設 `auto_detect.enabled: false`（或資料源為 mock），即回到純人工回報，
  背景 thread 不啟動。
- 程式層面可移除 lifespan 的 `start_background` 呼叫；`report_station(auto=...)` 為相容性新增，
  不影響既有呼叫。
- 未來調整判斷法或改為「疑似完成需確認」，以新 ADR supersede，不改寫本文件。

## 驗證方式

- 純函式 `reached_target`：補車上升逼近達標、取車下降逼近達標、方向錯不判、變化量不足不判、
  無 target 保守回 False，皆驗證通過。
- 端到端：建進行中任務→模擬即時站況 A 站達標→`scan_once` 自動完成 A（`auto_detected=True`、
  `reported_by=system-auto`）、B 未達標仍 pending→B 也達標→全部完成自動結案且人車釋放；
  自然波動（升幅不足）不誤判。
- 回歸：後端既有測試套除兩個 pre-existing 失敗（與本次無關）外全通過。
