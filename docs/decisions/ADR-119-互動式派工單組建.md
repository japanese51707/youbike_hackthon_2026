# ADR-119：互動式派工單組建（三入口 + 預覽確認）

## 背景與問題

ADR-117 的排程產出方式是「系統自動批次」（`assign_by_district` 一次把全部需調度站分區、配車配人、
切成一堆派工單）。與後台管理人員的實際操作對照後發現落差：

- 實際上後台是**互動式**組單——看著即時站況與緊急度清單，一單一單主動組建，不是系統一次派完。
- 後台有三種組單起點（以車 / 以站 / 緊急），且要能人工介入（改行政區、選車、調順序）。
- 產出的派工單要先**預覽**（看預估）再**確認**才成立（人在迴圈閘門，steering §6）。

自動批次仍有價值（可當底層演算、離線規劃、demo 一次看全貌），但**主要操作模式應改為後台互動組單**。
owner 已定調三入口與預覽確認流程，本 ADR 落地。

## 決策（proposed，待 owner 核准）

### 一、三個組單入口（後台主動觸發，系統算「先取後放」的站點順序）

**(a) 以車為起點（build_from_vehicle）**
- 後台選一台閒置車 + 人員。
- 系統預設用**車當前位置**算最適出車站點順序（該車所在區的需調度站）。
- 後台可人工改「目標行政區」→ 改了系統**自動重算**（換區 = 重跑）。

**(b) 以站為起點（build_from_station）**
- 後台從緊急度清單點某站要出單（不必從最急的開始）。
- 系統依該站所屬行政區的最適化，找可用車 + 人員，算站點順序。
- **找車候選順序（系統列出供後台選）**：該區閒置車 → 鄰近區閒置車 → 總站待命車。
- **可用人員池 = 該區閒置者 + 總站待命人力**（總站待命為獨立資源類別，可支援各區，見下）。

**(c) 緊急出車（build_emergency）**
- 後台自選車（可含預備車）+ 人員 + 要跑的站；順序自動算（預設）或人工調。
- 與死結救火（ADR-118）同一資源池邏輯，差別在觸發者（人工 vs 自動）。
- **資源優先序**（系統建議，後台可覆寫）：
  1. 優先「附近閒置的一般調度車」（成本低，不動用戰備）
  2. 其次才動用「預備車 standby」（保留給真的無車可調的死結）

### 二、一趟 = 先載後放的完整流程（任務邊界）

- 一張派工單 = 「先到滿站取車（載到接近車載運上限）→ 再到空站放車（放完數站）」走完 = 一個完整任務。
- 站數不固定：受**車載運上限**約束（載滿就開始放）。沿用 ADR-117 `_order_route`（先取後放最近鄰）
  + `_pack_trips`（載運量切趟）的底層邏輯。

### 三、預覽 → 確認 兩階段（人在迴圈閘門）

- 三入口都先產出**草稿派工單（draft，不落地 DB）**，附**預估資訊**：
  總距離 / 預估交通時間 / 預估作業時間 / 總載運量 / 緊急度加總。
- 後台**確認**後才真正成立（task_status=assigned、寫 DB、回寫車/人 current_district、認領標註）。
- 未確認的草稿不佔用資源、不影響認領地圖。

### 四、與 ADR-117 自動批次的關係（保留為底層）

- ADR-117 `assign_by_district` / `assign_peak_shuttle` / `suggest_next_trip` **保留**，作為
  「系統建議底層」與「離線批次規劃/demo 全貌」用途。
- ADR-119 三入口是**主要操作層**，內部**複用**底層能力（`_order_route`/`_pack_trips`/`_estimate_trip_kpi`/
  緊急度排序/available_vehicles/operators/list_standby）。
- 不是取代，是在自動批次之上加一層「後台互動 + 預覽確認」入口。ADR-117 加註指向本 ADR。

### 不改
- ADR-114 資源模型、ADR-115 目標水位、ADR-116 班別（三入口仍依班別判跨區/工時）、
  ADR-117 底層演算、ADR-118 預備車與死結救火、task_execution 執行閉環（確認後的任務走它）。

## 理由與判準

- **貼合真實操作**：後台是駕駛、系統是副駕（決策輔助）；互動組單比自動批次更符合實務與「人在迴圈」。
- **三入口涵蓋真實情境**：以車（車閒著找活）、以站（站危急找車）、緊急（死結/突發）。
- **預覽確認守閘門**：草稿不落地，確認才成立，符合 steering §6（預覽→確認→執行→驗證）。
- **複用不重造**：底層演算全沿用 ADR-117，只加互動入口與草稿/確認，降低風險與工程量。
- **緊急資源優先序**：就近閒置車優先、預備車殿後，保護靜態戰備（ADR-118 保留率）。

## 考慮過的替代方案

### 只保留 ADR-117 自動批次
- 缺點：不符合後台實際「一單一單互動組」的操作；無法選車/選站/緊急手動。未採用。

### 廢掉自動批次，全改互動
- 缺點：失去「一次看全貌/離線規劃/demo」的價值；底層演算仍需要。未採用，改保留為底層。

### 確認前就落地派工單
- 缺點：違反人在迴圈；草稿佔資源、污染認領地圖。未採用，改草稿不落地。

## 影響與後果

### 正面
- 後台可依三種真實情境互動組單；預覽預估後再確認；底層演算複用。

### 負面與代價
- 新增三個組單函式 + 草稿/確認兩階段 + 預估彙整；API 層需對應端點（串接工作）。

### 已於核准時拍板
- **總站待命為獨立資源類別**（owner 核准）：operators 加 role_type `depot_standby`（總站待命人力）、
  vehicles 加總站待命標記（`is_depot` 或狀態），與一般 driver/一般閒置車區分。可被調派去任何行政區。
- **草稿記憶體短期暫存**（owner 核准）：草稿只供預覽顯示，不落 DB，確認才寫入。
- **入口 b 找車候選順序**（owner 核准）：該區閒置 → 鄰近區閒置 → 總站待命車，系統列出供後台選（人拍板）。

### 尚未解決
- 人工調整站點順序的介面互動細節（前端），後端提供「重算順序」能力即可。
- 「鄰近區」的判定（相鄰行政區清單 vs 距離半徑）——實作時定，先用車位置距離最近的候選站。

## 介面與相容性

- 新增（dispatcher 或新模組 dispatch_builder）：
  `build_from_vehicle(vehicle_id, operator_id, district=None)` → draft trip
  `build_from_station(station_id, ...)` → draft trip（含跨區人力池）
  `build_emergency(station_ids, vehicle_id=None, operator_id=None, ...)` → draft trip（資源優先序建議）
  `confirm_trip(draft)` → 落地（走既有 _persist_trip + task_manager）
- draft trip 結構 = ADR-117 trip + `is_draft:true` + `estimate`（距離/時間/載運量/緊急度加總）。
- 確認後走既有 task_execution 執行閉環（逐站回報/認領/介入）。
- 不改對 predictor/rule_engine/urgency 的依賴。

## 資安與隱私

- 組單/確認為人為關鍵動作 → 記 audit_logs（誰/何時/組了哪張單/確認）。
- 確認派發需 dispatcher/controller 權限（比照既有 /dispatch/confirm 閘門）。
- 無新增 PII。

## 回復或取代方式

- 移除三入口、回退到 ADR-117 自動批次即可；改方向以新 ADR supersede。

## 驗證方式

- 入口 a：選車 → 出草稿（以車位置排序）；改行政區 → 重算順序不同。
- 入口 b：選站 → 找到該區可用車/人（含總站待命）→ 出草稿；該區無車 → 明確提示/建議跨區或預備車。
- 入口 c：選預備車/就近車皆可；資源優先序建議正確（就近閒置 > 預備）。
- 共同：草稿含預估（距離/時間/載運量/緊急度加總）；草稿不落地；確認後才 assigned + 認領標註 + 回寫。
- 先取後放順序、載運量不超上限；跑既有 dispatcher/task_execution 測試不破壞。
