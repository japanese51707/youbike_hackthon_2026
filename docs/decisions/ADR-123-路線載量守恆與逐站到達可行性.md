# ADR-123：路線載量守恆與逐站到達可行性

## 背景與問題

第三批審查確認派工單目前只檢查「總量不超過車容量」，不保證路線可執行：

1. `vehicles` 主檔沒有任何載量欄位，`_pack_trips` 與 `validate_stations` 隱含假設出車時車上為零。實務上車輛完成上一趟後可能仍有剩車，這個假設會低估超載風險。
2. `validate_stations` 以 `sum(quantity) <= capacity` 判斷，不分取車／補車、不依路線順序累計。「先到三個滿站各取 7 台再去補車」在容量 15 的車上會通過驗證，實際第二站就爆量；反向的「先補車但車上沒車」也不會被擋。
3. `_estimate_trip_kpi` 只回整趟總時間，規則引擎的 `predicted_at_arrival` 對整趟所有站套用同一個視野。路線第三站可能 90 分後才到，卻用 30 分視野的預測決定目標存量。
4. `core/shift.py` 的 `check_labor` 定義完整但全 repo 零呼叫；`today_work_minutes`、`on_duty_since` 有欄位無寫入。班別跨區限制只在自動批次用到，三入口互動組單沒有工時或任務時間重疊檢查。

ADR-302 的限制段已寫明「本批容量檢查沿用現行保守總量規則，不宣稱已完成路線載量模型」，第二批限制也把逐站載量守恆與 ETA 列為第三批。

## 決策

沿用 ADR-114～119、121、302、303；不取代任何 ADR。

1. **可追溯的車輛初始載量**：`vehicles` 新增 `onboard_bikes`、`onboard_source`、`onboard_observed_at`（冪等擴欄，比照既有作法）。來源必須可追溯（人工回報、任務結案推算或未來車隊 API），**不得在未知時假設為零**。載量未知或觀測過期的車輛仍可產生草稿以供預覽，但草稿標記阻擋原因，確認一律拒絕，由後台先補回報。
2. **逐站載量守恆**：依 `_order_route` 產生的實際順序逐站累計——取車加上該站搬運量、補車減去該站搬運量——全程車上載量必須落在 `[0, max_capacity]`。違反即為不可執行，預覽標記、確認拒絕。搬運量以主指令 `target_available` 與當下觀測存量推算，與 ADR-115 一致。
3. **逐站到達時間與對應視野**：依 `config.travel` 的平均車速與每站搬運分鐘，累計每站的到達時間偏移；每站取「最接近該偏移」的預測視野（30／60／90／120）作為該站的到達存量依據，不得整趟共用同一視野。超出最長視野的站點標記為超出預測範圍，不得以外推冒充預測。
4. **班別、工時與任務重疊**：組單與確認都要檢查——該班別是否允許跨區（ADR-116）、執行人員的剩餘連續工時是否足以完成本趟預估總時間（`check_labor` 正式接線）、本趟時間區間是否與該人／該車既有未結束任務重疊。任一不通過即為阻擋原因。
5. **預覽與確認共用同一驗證**：三入口組單與 `confirm-trip` 呼叫同一個可行性評估函式，草稿回傳逐站載量計畫與 `blocking_reasons`；確認時以確認當下的資源與觀測重新執行同一驗證。預覽通過而確認失敗只應源於期間內狀態改變，不得源於兩邊規則不同。
6. **保留既有安全機制**：人工確認閘門、單一交易全成或全退、同草稿版本重送回原任務、結案釋放人車與認領，全部沿用 ADR-302，不放寬。
7. **不新增付費路線服務**：距離與時間沿用既有 haversine 直線距離與 `config.travel` 估算。此估算低估實際路程，必須在輸出與報告中標示為估算值。

## 理由與判準

- **可執行性是安全問題**：一張數學上不可能完成的派工單送到司機手上，成本由現場承擔。
- **未知不等於零**：以零填補未知載量會把風險藏起來，違反「失敗要看得見」的開發原則。
- **與既有決策相容**：全部建立在 ADR-114～119 的資源模型與 ADR-302 的確認閘門之上，不改其核心。
- **成本可控**：沿用既有距離估算，不引入外部服務與新依賴。

## 考慮過的替代方案

### 方案 A：維持總量檢查，只在前端提示

- 優點：後端零改動。
- 缺點：前端提示可被直接呼叫 API 繞過，且不解決錯誤的目標存量。
- 未採用原因：與 ADR-302「不信任 client」相牴觸。

### 方案 B：未知載量時預設為零並標記

- 優點：不擋住流程，demo 順暢。
- 缺點：把不確定性變成看似確定的數字，正是本批要修的問題類型。
- 未採用原因：owner 明確選擇擋下確認。

### 方案 C：導入真實路線規劃服務取得 ETA

- 優點：到達時間準確。
- 缺點：需付費服務與新外部依賴，超出本批範圍。
- 未採用原因：明確排除；沿用既有估算並標示限制。

## 影響與後果

### 正面

- 派工單在送出前即保證載量與時間上可執行。
- 各站使用對應視野的預測，目標存量不再被單一視野誤導。
- 工時與任務重疊檢查從紙上規則變成實際閘門。

### 負面與代價

- 部分原本可確認的草稿會被擋下（載量未知、超載、工時不足），可派工站數下降。
- `vehicles` 需要載量回報流程，Demo seed 需補初始值。
- 逐站計算使組單與確認的運算量上升。

### 尚未解決

- 車輛載量的自動回報（車隊 API）未接，現階段靠人工或結案推算。
- 直線距離低估實際路程，ETA 為估算值。
- 跨趟的載量結轉（上一趟剩餘自動成為下一趟初始）僅在結案推算層面處理，未做完整車輛庫存帳。

## 介面與相容性

`vehicles` 表新增三個可為空的欄位，以 IF NOT EXISTS／冪等擴欄新增，既有資料不需遷移。草稿與任務 route stop 新增 `arrival_offset_min`、`horizon_used_min`、`onboard_after`（逐站到達後車上載量）等欄位；`blocking_reasons` 為新增陣列欄位。既有欄位名稱與型別不變，未更新的前端仍可運作，只是看不到新欄位。確認錯誤沿用 ADR-302 的 409 語意，新增的阻擋原因以訊息表達。

## 資安與隱私

不新增外部請求、憑證或個資。載量回報寫入沿用既有 dispatcher／maintainer 與執行者授權檢查，並寫稽核。輸入值沿用既有嚴格整數與範圍檢查，不信任 client 提供的載量計畫。

## 回復或取代方式

可行性評估集中在單一模組，停用該模組即回到既有總量檢查；新增欄位可保留不用。若要改變載量或 ETA 策略，以新 ADR supersede 本 ADR。

## 驗證方式

- pytest：超載趟、途中負載量趟、未知載量擋確認、工時不足、任務時間重疊、逐站視野對應正確、預覽與確認結論一致，各一案。
- 既有 `test_dispatch_safety`、`test_dispatch_builder`、`test_task_execution`、`test_dispatch_assignment`、`test_emergency` 回歸不破壞。
- `git diff --check`；不 commit／push。
