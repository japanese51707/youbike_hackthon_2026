# ADR-319：系統為主的自動配單（依緊急度逐張配對鄰近人車）

## 背景與問題

系統目標是走向全自動化調度、人員原則上不介入。既有的組單三入口（ADR-119）是「人在迴圈」的
互動組單——由後台選站、預覽、確認落地。要達成自動化，需要一個系統為主的迴圈：把目前的緊急
調度清單，依緊急度自動配對鄰近適合的人與車並直接落地成派工單。

關鍵約束（owner 明確要求）：

1. 依緊急度由高到低**逐一**配單；車源與人力遵循既有階梯（同區→跨區→總部）。
2. **先配完一張，讓對應站被標註「已配單」、系統過濾掉，再跑下一筆**——不可把同一站配進多張單。
3. 自動配單**為主**；人工手動組單改為**緊急人工介入專用**，自動配單要**避開人正在手動預覽/草稿**
   的站，不與人搶單。
4. 對齊官方即時資料約 5 分鐘更新的節奏（**300 秒**一輪），不過度頻繁。

既有缺口：`build_dispatch_list` 與 `_current_dispatch_list` 只把 override 站置頂，**沒有過濾
已被任務認領的站**；也沒有機制避開人工草稿佔用的站。若直接自動配單會重複配同一站。

## 決策

新增**自動配單背景迴圈**（`backend/core/auto_dispatch.py`），每輪：

1. 取當前需調度清單（`build_dispatch_list`，`apply_capacity=False` 完整排序，與組單同口徑）。
2. **過濾**掉：已被進行中任務認領的站（`task_execution.station_claim_map`）＋人正在手動預覽/草稿
   佔用的站（新增 `dispatch_drafts.active_draft_station_ids`，只計人工建立的草稿）。
3. 依 `priority_score` 由高到低，對每個緊急站**逐一**配單：**複用 `dispatch_builder.build_from_station`**
   組草稿 → `dispatch_confirmation.confirm` 落地。`build_from_station` 已內建所要的車源階梯
   （同區取車站就近取 → 同區湊不足跨區取一站補足 → 都不行由總部載滿車出發並警示 `needs_depot_refill`）
   與人力階梯（同區優先、需總部時派總部待命人車）。
4. **序列化配單**：每配完一張，該站即被新任務認領；同輪內就地累積「已配站」集合（含該張單一次
   涵蓋的多站），下一筆不再碰這些站，並以「扣掉已配站」的清單組下一張。
5. 落地層 `validate_resources` + `ensure_unclaimed`（ADR-302）為可靠防重複防線；配單過程吞
   `DispatchConflict`／`DispatchForbidden`（資源被搶、無人車、被人工搶走）換下一站，不中斷整輪。
6. 每輪配單數上限（config `每輪最大配單數`，預設 20）防單輪暴衝。

**避開手動草稿**：新增 `active_draft_station_ids()` 列出未過期、非系統身分建立的草稿所佔用的站；
自動配單以系統 dispatcher 身分（config `operator_id`，預設 OP-002）建草稿與確認，故其自身草稿
不列入「人工佔用」。

**與 auto_detect（自動偵測完成，ADR-310）序列化**：兩個背景迴圈共用一把 `threading.Lock`
（`auto_dispatch.COORDINATION_LOCK`，auto_detect 的 `scan_once` 亦取用），避免同時動任務／車／人。

節奏：config `auto_dispatch.輪詢間隔_秒` 預設 **300**（對齊官方約 5 分更新）；同時把 auto_detect
輪詢間隔由 60 調為 300（偵測的是站別狀況變化，官方 5 分才更新，60 秒為白做工）。僅真實資料源
（非 mock）且 `enabled=true` 時運作。

## 理由與判準

- **對齊全自動化目標**：系統依緊急度自動配對人車並落地，人員只在緊急時手動介入。
- **複用勝過新造**：`build_from_station` 已具備完整車源／人力階梯與 `needs_depot_refill` 警示，
  直接複用即滿足「沒有鄰近甚至跨區都沒有就找總部」的需求；不採 `assign_by_district`（缺 depot 階梯）。
- **正確過濾**：以 `station_claim_map`（任務認領）＋ `active_draft_station_ids`（人工草稿）雙來源
  過濾，並同輪就地累積已配站，達成「先配完一張、標記已配、過濾後再配下一筆」；落地層例外為最終防線。
- **不與人搶**：自動配單避開人工草稿站，貫徹「自動為主、人工=緊急介入」的定位。
- **無競態**：一把鎖序列化自動配單與自動偵測完成；官方源 5 分更新，300 秒節奏足夠且不過度外呼。
- **可控 / 可逆**：config 開關 + 僅真實源；關掉即回到純人工組單。

## 考慮過的替代方案

### 方案：獨立自動配單迴圈 + 複用 build_from_station + 共用鎖 + 雙來源過濾（採用）

- 優點：滿足全部需求、複用既有階梯、與既有背景迴圈無競態、可控可逆。
- 缺點：新增一個背景 daemon 與一把跨模組鎖。
- 未採用原因：無——採用方案。

### 方案：用 assign_by_district 做自動指派

- 優點：已有行政區切趟指派邏輯。
- 缺點：缺總部載滿的 depot 階梯與 `needs_depot_refill` 警示，不符「都沒有就找總部」需求。
- 未採用原因：能力不足，需另補階梯，不如複用 `build_from_station`。

### 方案：只在清單層過濾、不新增背景迴圈（沿用人工組單）

- 優點：改動最小。
- 缺點：無法達成「系統每次更新自動配單」的自動化目標。
- 未採用原因：與 owner 的自動化要求相違。

## 影響與後果

### 正面

- 緊急單依緊急度自動配對鄰近人車並落地，逐張序列化、不重配；人只在緊急時介入。
- 與自動偵測完成（ADR-310）串起：自動配單→自動偵測達標→自動結案釋放，形成閉環。

### 負面與代價

- 新增背景 daemon 與跨模組鎖；自動配單與自動偵測互斥執行（節奏 300 秒，互等影響可忽略）。
- 自動配單以系統 dispatcher 身分落地，稽核以該身分留痕（可追溯，但非真人操作）。
- 快取／官方源約 5 分延遲，「每次更新配一次」實際最快約 5 分一輪（刻意，避免過度外呼）。

### 尚未解決

- 尚未針對「跨區/總部」情境做更精細的成本最小化（目前沿用 `build_from_station` 的階梯與就近規則）。
- 每輪配單上限與輪詢間隔為經驗預設，未來可依實測調校。

## 介面與相容性

- **新增**：`core/auto_dispatch.py`（`scan_once` / `start_background` / `stop_background` /
  `COORDINATION_LOCK`）；`dispatch_drafts.active_draft_station_ids()`。
- **修改**：`auto_detect.scan_once` 改為在 `COORDINATION_LOCK` 下呼叫 `_scan_once_locked`（行為不變，
  僅加鎖序列化）；`main.py` lifespan 啟動／停止自動配單背景。
- **設定**：`config.yaml` 新增 `auto_dispatch`（`enabled` / `輪詢間隔_秒` / `每輪最大配單數` /
  `operator_id` / `只配緊急級別`）；`auto_detect.輪詢間隔_秒` 60→300。預設 `enabled: true`，僅真實源生效。
- **相容性**：組單三入口與 `confirm` 行為不變；自動配單複用其鏈路，不新增寫入路徑。

## 資安與隱私

- 自動配單只讀官方即時站況（沿用既有資料源與 TLS）；落地走既有 `confirm`／`validate_resources`
  權限與一致性檢查，以系統 dispatcher 身分過權限並稽核留痕，不繞過權限模型。不涉個資。

## 回復或取代方式

- 關閉：`config.yaml` 設 `auto_dispatch.enabled: false`（或資料源為 mock），即回到純人工組單，
  背景不啟動。程式層面可移除 lifespan 的 `start_background` 呼叫。未來調整配單策略以新 ADR supersede。

## 驗證方式

- 單元/整合（`tests/test_auto_dispatch.py`）：配出單且站被認領、第二輪不重配已認領站、避開人工
  草稿站、遵守每輪上限、只配指定緊急級別，皆通過。
- 回歸：後端全套測試僅餘 pre-existing 失敗（與本次無關），auto_detect 加鎖無回歸。
- 前端不受影響（`npm run build` 通過）。
