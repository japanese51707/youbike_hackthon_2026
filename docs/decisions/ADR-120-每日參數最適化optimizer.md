# ADR-120：每日參數最適化 optimizer（站點調整係數自適應）

## 背景與問題

系統有站點參數三層（ADR-001）：base（基準）→ ai_optimized（每日 AI 微調）→ override（即時覆寫）。
`ai_optimized` 這層一直沒有真正的演算法——`/optimization/daily-review` 端點目前回 mock。
params 版本管理（set_base/commit_optimized/rollback）、config（回看天數/單次最大調幅/自動套用）、
daily-review UI 骨架都已備，缺的就是中間「算偏差、產生建議」的 optimizer 演算法。

owner 要求（本 session）：
- 不能只調流出率/目標水位——每站每天遇到的情況不同（雨天、活動…），只抓少數參數誤差極大。
- 要調「所有可調參數」，且**環境影響也因站而異**（同樣下雨，河濱站掉很多、通勤站掉不多，
  不該全市統一 0.7）。
- 一天做一次——要累積足夠資料分情境比對，讓 AI 有時間找出哪裡該修正。

## 決策（proposed，待 owner 核准）

### 核心：optimizer 學習並調整每站的「調整係數」，不改基準值

不直接改基準參數/環境係數，而是**每站維護一組「調整係數」（預設 1.0 = 無調整），乘在基準上**：

```
站點基礎參數實際值 = base 參數 × 站點基礎調整係數
站點環境影響實際值 = 全市環境係數(如雨0.7) × 該站環境敏感度調整係數
```

- 基準值（全市物理規律，如雨天 0.7）保持乾淨、可解釋、不動。
- 站點差異用調整係數捕捉（這站的獨特性格）。
- optimizer 每天調的就是這些**調整係數**。

### optimizer 每天做的事（離線批次，一天一次）

1. 拿近 N 天實際資料（config `optimization.回看天數`，預設 3）+ 歷史。
2. **分情境**算「該站實際 vs 系統預測」的偏差——情境維度：
   天氣（晴/雨/大雨/颱）、假日類（平日/假日/國定/颱風假）、活動（有/無）、時段。
3. 把偏差**歸因到對應的調整係數**：
   - 一般情境（晴天平日）偏差 → 調「站點基礎調整係數」
   - 特定環境情境（雨天）偏差（扣掉基礎後仍有的）→ 調「該站該環境敏感度調整係數」
4. 用「單次最大調幅」夾住（config `單次最大調幅百分比`，預設 10%，防暴衝）。
5. 情境樣本量不足時不調（避免用少數樣本亂調）。
6. 產生「建議調整清單」（逐站逐係數：舊值/新值/幅度/原因/情境/樣本數）。
7. **人工核准閘門**（config `自動套用: false`）：建議 → controller 逐站 accept/keep/re_adjust →
   approve 才寫入 ai_optimized 層（走既有 params.commit_optimized，存版本可回溯）。

### 可調參數範圍（每站，全部可調）

| 類別 | 參數 | 調整方式 |
|------|------|---------|
| 站點基礎 | 流出率/流入率（各時段）、目標水位、安全緩衝、觸發靈敏度 | × 站點基礎調整係數 |
| 環境敏感度 | 天氣（晴/雨/大雨/颱）、假日類、活動 | × 該站該情境敏感度調整係數 |

所有調整係數預設 1.0（未學習前＝用全市基準，行為同現況）。

### 偏差歸因（防誤判關鍵，呼應 owner「只抓流出率會有極大誤差」）

先扣環境影響、再看基礎偏差，避免把「雨天少騎」誤當成「這站基礎流出率要改」：
- 晴天平日的偏差 → 純基礎參數問題 → 調基礎係數。
- 雨天的偏差**扣掉基礎係數修正後**仍系統性存在 → 該站對雨的反應與全市不同 → 調該站雨天敏感度係數。

### 不改
- 模型（LightGBM 預測，ADR-113）——optimizer 調的是規則參數，不重訓模型（兩層分工）。
- params 三層結構、版本管理、daily-review 人工核准閘門（既有，沿用）。
- 全市環境係數基準值（weather_factor/holiday_factor 等，config 不動，只被站點係數乘）。
- 規則引擎/緊急度/目標水位（ADR-111/112/115）——它們讀「疊加後的有效參數」，邏輯不變。

## 理由與判準

- **對準 owner intent**：每天 AI 微調固定數據（站點性格），讓系統越用越準。
- **調整係數設計**：基準乾淨、站點差異用係數捕捉、預設 1.0 向後相容（未學習=現況）。
- **因站而異的環境敏感度**：解決「全市統一係數誤差大」（河濱 vs 通勤站雨天反應不同）。
- **分情境歸因 + 先扣環境**：避免把天氣/活動誤判成站點基礎性格（owner 明確要求）。
- **一天一次**：累積足夠分情境樣本才調得準；符合「靜態層每日批次」（ADR-113 特徵三層）。
- **人在迴圈**：AI 只建議、人核准才套用（config 自動套用 false），可解釋、可回溯、可回滾。
- **不重訓模型**：optimizer 調規則參數（快、可解釋），與模型預測分層清楚（守 ADR-004）。

## 考慮過的替代方案

### 只調流出率/目標水位（少數關鍵參數）
- 缺點：owner 指出——不分情境、只抓少數參數，雨天/活動一定造成極大誤差。未採用。

### 直接改基準值（不用調整係數）
- 缺點：基準值失去「全市物理規律」的乾淨語意、不可解釋、難回退。未採用，改調整係數乘法。

### 全市統一環境係數（不因站而異）
- 缺點：同樣下雨各站反應差很多（owner 指出），統一係數誤差大。未採用，加站點環境敏感度係數。

### 每次即時調（非每天一次）
- 缺點：即時樣本不足以分情境比對，易被雜訊亂調。未採用，維持每日批次。

### 用模型重訓取代 optimizer
- 缺點：重訓慢、黑箱、與規則參數是不同層。未採用，optimizer 只調規則參數。

## 影響與後果

### 正面
- ai_optimized 層有真實演算法；系統每天自我修正、越用越準；站點/環境差異被捕捉。
- 展示「AI 建議 → 人核准 → 套用」的自適應閉環。

### 負面與代價
- 需寫 optimizer 模組（分情境偏差計算 + 歸因 + 夾調幅 + 樣本量門檻）——中等工程量。
- 需「近 N 天實際 vs 系統預測」的比對資料（可由歷史 + 預測重建）。
- 站點參數 schema 需容納各情境調整係數（params_json 擴充）。

### 尚未解決
- 「系統預測」在回看期怎麼取（重跑模型 vs 存預測日誌）——實作時定，開發期可用歷史重算。
- 各情境樣本量門檻的具體值——實作時定，先保守（樣本不足不調）。
- 調整係數的上下限護欄（除單次調幅外，累積是否設絕對區間）——實作時定。

## 介面與相容性

- 新增 optimizer 模組（如 backend/optimization/param_optimizer.py）：
  `compute_daily_review(review_date, lookback_days) -> 建議清單`。
- `/optimization/daily-review` 端點接它（取代 mock）；核准/退回沿用既有 params.commit_optimized。
- params_json 擴充「調整係數」欄位（向後相容，缺欄視為 1.0）。
- 規則引擎/緊急度讀「有效參數（三層疊加）」介面不變。

## 資安與隱私

- 純內部參數計算，無對外通訊、無 PII。人為核准動作記 audit（param_edit/optimization）。

## 回復或取代方式

- 調整係數全設 1.0 即回復到基準（等同未優化）；ai_optimized 層可 rollback 到任一版本（既有）。
- 改方向以新 ADR supersede。

## 驗證方式

- 分情境偏差計算正確（晴/雨/假日分開算）。
- 歸因正確：晴天偏差調基礎係數、雨天殘差調雨天敏感度係數（先扣基礎）。
- 單次調幅夾住（不超過 config 上限）；樣本不足不調。
- 建議 → 核准 → 寫 ai_optimized 版本 → 可回溯/回滾。
- 有效參數（三層疊加）計算正確；規則引擎讀取行為不變。
- 全設 1.0 時系統行為等同現況（向後相容）。
