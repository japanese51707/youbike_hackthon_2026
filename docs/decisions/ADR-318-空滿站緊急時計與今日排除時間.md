# ADR-318：空滿站緊急時計與今日排除時間

## 背景與問題

值班處長盯盤要看到「這站空／滿了多久」以及「今天各區平均多久才排除」。
既有 `alerts.triggered_at` 會因警示重建或已讀重算而歸零（ADR-309 已說明）。
既有 `alert_cases.opened_at` 雖不重置，但案件會在**已派工**時關案——站還空著時計就停，不能當「問題還在燒」的時計，也不能當「排除＝站況恢復」的統計。

不做決策的後果：前端 session 計時重整即歸零；或誤用警示／升級案件，數字會在不該停的時候停。

## 決策

1. **另建 `service_problems` 表**，不重用 `alerts` 或 `alert_cases`。
2. **開時計**：站況一進入 `empty` 或 `full` 就開一筆未結案 incident；`opened_at` 之後不再改。
3. **關時計**：站況離開空／滿（恢復或離線）才關，`close_reason=recovered`。派工不關。
4. **空↔滿互轉**：關舊筆（`kind_changed`，不計入排除平均），再開新筆。
5. **今日排除時間**：台北日曆日、只算 `recovered` 的 `closed_at − opened_at`。全市平均＋各區平均；各區另列最差幾個站（進行中經過時間與今日已排除耗時，取最長）。
6. **空快照不關案**：本輪站況為空陣列時不同步，避免上游短暫失敗把全部時計關掉。
7. **API**：`GET /api/v1/service-problems` 回進行中與今日彙總。時間一律後端算；前端可用 `opened_at` 做畫面秒針，不得自造開案時間。
8. **看板**：服務水準看板（ADR-209）加第五張燈「今日各區平均問題排除時間」；空／滿燈與行政區列顯示進行中最長時間。本頁仍不派工（ADR-004）。

## 理由與判準

- **正確性**：排除＝市民借得到／還得到，不是「已派人」。
- **可追溯**：時鐘掛在持久化 incident，重整與警示重建都不重置。
- **可維護**：與 ADR-309 升級案件分責，避免改關案條件 ripple 到處長看板。

## 考慮過的替代方案

### 沿用 alert_cases

- 優點：少一張表。
- 缺點：派工關案後空站時計消失；案件也會因最高緊急建議開案（非空非滿）。
- 未採用原因：語意不是「空／滿還在燒多久」。

### 只在前端 session 計時

- 優點：不必改 schema。
- 缺點：重整、換瀏覽器、多螢幕對時全部失真。
- 未採用原因：處長盯盤要跨刷新可信。

## 影響與後果

### 正面

- 空／滿一出現就有經過時間；今日排除平均可問責到行政區與最差站。

### 負面與代價

- 每次完整站況快照多一次寫入。空快照刻意跳過，短暫上游失敗不會洗掉時計。

### 尚未解決

- 跨日未結案的進行中時計會延續，但不計入「昨日平均」（只算當日 recovered）。
- 歷史回補（系統上線前已空／滿的站）只能從第一次看到的快照起算。

## 介面與相容性

- 新表 `service_problems`（`schema.sql` `IF NOT EXISTS`）。
- `GET /api/v1/service-problems`：`city`、`open`、`districts`（含 `worst_stations`）。
- 服務水準看板多讀此端點；既有 KPI／派工契約不變。

## 資安與隱私

- 只讀彙總與站名；不擴大寫入權限；不含 PII。

## 回復或取代方式

- 以新 ADR supersede；停用同步後表可留作稽核，看板隱藏第五張燈即可。

## 驗證方式

- 空站開案後再次同步，`opened_at` 不變。
- 派工不關案；恢復才關且計入今日平均。
- 空↔滿互轉不計入平均。
- `/overview` 空／滿列得出經過時間；第五張燈點開看得到各區平均與最差站。
