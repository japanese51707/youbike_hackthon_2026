# ADR-314：前端與後端同源上雲（ECS 出 SPA）

## 背景與問題

ADR-307 只把後端放到 ECS，前端留在使用者本機 `npm run dev`，靠 Vite proxy 打雲端。
評審與隊友必須自己裝 Node 才能看完整系統。owner 要求前端也上雲，並要單一可分享網址。

限制：S3 不可公開（競賽規範）；App Runner 被 SCP 擋；NLB + Elastic IP（ADR-312）已固定
`http://54.227.205.77:8000`。

## 決策

1. **前端 production build 打進同一後端 image**，由 FastAPI 同源提供 SPA。
   對外只維持既有 NLB：`http://54.227.205.77:8000/` 是畫面，`/api/v1` 是 API。
2. **不另開**公開 S3 網站、CloudFront、第二個 Fargate、App Runner。
3. 打包時 `VITE_API_BASE_URL=/api/v1`、`VITE_DATA_MODE=api`（相對路徑，走同源，不必 CORS）。
4. 本機 `uvicorn` 若沒有 `frontend_dist/`，行為與現在相同（只提供 API）。
5. SPA 深連結（`/dashboard`、`/twin`）回 `index.html`；`/api`、`/docs`、`/health`、`/openapi.json` 不交給前端。

本 ADR **不**涵蓋「每次 git push 自動部署」；那是後續獨立決策。

## 理由與判準

- **交付速度**：沿用既有 ECS／NLB／EIP，不新增雲端服務。
- **同源**：沒有 Vite 時不必改 CORS、不必把後端 IP 寫進前端 bundle。
- **規範**：靜態檔在容器內，S3 維持 Block Public Access。
- **可逆**：拿掉 image 裡的 `frontend_dist` 即回到純 API。

## 考慮過的替代方案

### 公開 S3 靜態網站

- 優點：簡單。
- 未採用原因：規範禁止公開 S3。

### S3 私有 + CloudFront

- 優點：HTTPS、靜態與 API 分離。
- 未採用原因：多一個服務與費用；瀏覽器跨域要開 CORS；比賽時程不值得。

### 第二個 Fargate（nginx）

- 優點：前後端生命週期分離。
- 未採用原因：多一倍常駐成本，且仍要處理跨域或 path 路由。

## 影響與後果

### 正面

- 評審打開一個網址即可用完整前後端。
- 本機開發路徑不變。

### 負面與代價

- 改前端也要重編後端 image、ECS 滾動更新（約數分鐘）。
- image 變大（Node 只在 build 階段，runtime 仍是 Python slim + dist）。
- 仍是 HTTP（既有 NLB 未上 TLS）。

### 尚未解決

- HTTPS／自訂網域。
- git push 自動部署改由 ADR-317 處理。

## 介面與相容性

- API 契約不變。
- Dockerfile 改多階段：Node 建 `frontend/dist` → 複製到 `/app/frontend_dist`。
- `.dockerignore` 放行 `frontend/` 原始碼，排除 `node_modules`／`dist`。
- `GET /` 在有靜態檔時回 SPA；無檔時維持 404。
- 限流豁免 `/assets/`，避免首屏靜態檔吃光每分 120 次額度。

## 資安與隱私

- 靜態檔不含金鑰；CWA／AWS 仍只在容器環境變數。
- 入向仍只開 8000。
- SPA 不擴大 API 權限模型（仍要 `X-Operator-Id` 才能寫入）。

## 回復或取代方式

- 回上一版 image（不含 `frontend_dist`）即關前端上雲。
- 若改獨立靜態站或 CDN，以新 ADR supersede。

## 驗證方式

- 本機：有 `frontend_dist` 時 `/`、`/dashboard` 回 HTML；`/health`、`/api/v1/kpi` 仍是 JSON。
- 雲端：`http://54.227.205.77:8000/` 可開調度面板，XHR 打同源 `/api/v1`。
