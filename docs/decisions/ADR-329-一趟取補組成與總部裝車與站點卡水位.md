# ADR-329：一趟派工的取補組成、總部裝車與站點卡水位

## 背景與問題

自動／互動組單會產出「做不完」的殘缺趟次：

1. **只有補車、沒有車源**：一趟排了補車站，但趟內沒有任何取車站、車上也沒車，車從哪來？
2. **只有取車、沒有去處**：一趟排了取車站，卻沒有補車站可放，取來的車無處去。

營運上「一趟」的定義是**先到滿站取車、再到空站放車**，兩種行為都要有才算完成。此外，當車源
不在趟內取車站、而是「從總部裝滿車出發」時（ADR-315 車源階梯最後一階），任務必須明確帶出
「在總部裝幾台」，否則司機端只看到一堆補車站，不知道車從哪來、要裝多少。

分派任務狀況頁的站點卡也只顯示目標台數，缺「當下可借／可還」現況，調度員看不出落差；且無法
從卡片快速看到「車現在在哪、還要幾站到這站」。

## 決策

1. **一趟取補組成規則**（`dispatch_builder._ensure_trip_composition`）：組單後補齊殘缺趟次——
   只有補車站時，設法納入車源（趟內取車站或總部裝車）；確保「一趟同時有車源與去處」。
2. **總部裝車指示**：從總部裝車出發的趟次，把「在總部裝幾台」（`depot_load`）一起存進任務
   （`tasks.depot_load_json`，`connection.py` 加欄、`tasks_repo` 讀寫），司機端當第 0 步顯示。
3. **站點當下水位補丁**（`api/dispatch._attach_live_station_status`）：把每個停靠站的「當下站況」
   （live 可借／可還）補進進行中任務路線；路線裡的 `current_available` 只是組單當下快照，改以
   後端補的 `live_*` 優先顯示。
4. **分派任務狀況頁站點卡**（`DispatchStatusPage.jsx`）：站點卡標當下三個水位數字，點卡開路線
   地圖（用任務停靠順序畫實走道路，焦點標在被點的站）。

## 理由與判準

- **正確性**：杜絕「做不完的單」——一趟一定有車源也有去處，符合先取後補的營運定義。
- **可執行性**：總部裝車指示讓司機知道車從哪來、裝多少，避免只看到補車站的困惑。
- **可觀測**：站點卡顯示現況 vs 目標 + 路線地圖，調度員一眼看出落差與車輛位置。
- **複用**：路線地圖沿用 ADR-319 的道路路線；水位補丁用既有即時站況。

## 考慮過的替代方案

### 方案 A：組單後補齊取補組成 + 總部裝車指示 + 站點卡水位（採用）

- 優點：直接解決殘缺單、車源可追溯、可觀測。
- 缺點：組單邏輯與任務結構略增。
- 未採用原因：無——採用方案。

### 方案 B：只在前端提示殘缺，不改組單

- 優點：改動小。
- 缺點：殘缺單仍會產生，治標不治本。
- 未採用原因：無法根除做不完的單。

## 影響與後果

### 正面

- 派工單一定可執行；司機清楚車源；調度員看得到站況落差與路線。

### 負面與代價

- `tasks` 新增 `depot_load_json` 欄位；組單多一步組成檢查。

### 尚未解決

- 取補配平的最優化（多站組合、成本最小）尚未深入，目前以「補齊可執行」為準。

## 介面與相容性

- **資料**：`tasks` 新增 `depot_load_json`（`connection.py` migration；無則 NULL，相容）。
- **API**：進行中任務路線補 `live_available_bikes` / `live_available_docks` 等當下站況欄位。
- **前端**：`DispatchStatusPage` 站點卡加水位數字與點擊開路線地圖。
- **相容性**：既有單人／既有任務不受影響；depot_load 僅總部裝車趟次帶。

## 資安與隱私

- 只讀既有即時站況、只帶站點座標畫路線；不涉個資、不新增對外邊界。

## 回復或取代方式

- 移除 `_ensure_trip_composition` 呼叫即回到舊組單（會再現殘缺單）；`depot_load_json` 留 NULL 相容。
  站點卡水位／路線地圖為前端加強，可獨立移除。

## 驗證方式

- `tests/test_trip_composition.py`：一趟必須同時有取車與補車、殘缺趟次被補齊，通過。
- 前端 `npm run build` 通過；分派任務狀況頁站點卡顯示水位、點卡開路線地圖。
