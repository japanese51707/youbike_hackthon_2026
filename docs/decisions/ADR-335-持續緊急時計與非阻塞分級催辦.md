# ADR-335：持續緊急時計與非阻塞分級催辦

## 背景與問題

Owner 於 2026-09-13 要求校正逐任務指派時間、站點持續緊急時間，以及 30／45／60 分鐘對承辦司機與管理後台的非阻塞提醒。

現行 ADR-309 明定有未結案任務涵蓋即關案，45 分鐘強制彈窗；因此派工後仍緊急的站不再催辦，且彈窗阻塞操作。ADR-324 的物理時計另計空滿時間，但離線會當恢復，且不能代表提前緊急預警的起點。任務寫無時區 assigned_at，前端以分鐘顯示，司機端超過 12 小時隱藏。

Owner 已於 2026-09-13 核准（見 approval-evidence），依此實作。詳細查核與契約見 [修正設計](../analysis/alert_timing_redesign_20260913.md)。

## 決策

1. 任務與緊急事件的時計獨立。assigned_at 使用原子指派時的一個帶時區時間值；重送不重設。同秒指派合法；UI 同時顯示指派時刻（含秒）及耗時，不以錯開時間製造差異。舊值先依確認收據對帳，無證據不猜時區。
2. 營運緊急事件由首次可信觸發開始（★「可信」在正式資料路徑要求 `data_freshness == 'live'`；欄位缺漏一律視為不可信，只有測試 fixture 例外。這條路徑會用來判斷「緊急解除」，把欄位缺漏當成可信會直接關掉不該關的案），派工、轉派、已讀、任務完成及跨日均不關案；新鮮觀測與規則確認解除才結束。再次危急建立新事件；空↔滿持續視為同一營運緊急事件。
3. 物理空滿時計與排除 KPI 保留 ADR-324～328 原有分段責任，但離線、過期、缺站、缺規則結果不視為恢復；空↔滿的物理分段仍保留 kind_changed 且不算排除。未結束事件不被 24 小時清理。
4. 緊急同步移至既有背景流程；顯示 API 只讀已保存狀態並算時間。外部時計模式維持 worker 單寫、網站讀，不由網站資料查詢隱式寫入。原子同步、觀測順序與來源檢查防誤關案。
5. 依設定 [30,45,60] 升 L1/L2/L3，60 分後以可設定間隔（預設 15 分）持續提醒。★同批提醒必須先聚合再送出：同一行政區同階段超過 `escalation.合併門檻_件數`（預設 3）時，合併成一則區級摘要（「板橋區 7 站超過 45 分」），不逐站送；全域同時最多一則彙總橫幅與一張短暫通知。早尖峰同時上百站緊急是常態，不設合併上限會把後台洗版，等於另一種形式的阻塞。通知以事件／階段／收件人／承辦版本／提醒批次冪等保存；重連只提示當前階段摘要。
6. 司機收到自己有效承辦站點的提醒，管理端看到所有未解除案件；無有效任務只通知管理端。已釋放任務及 completed／removed stop 不當作承辦。轉派更新收件者，不重算緊急時間。
7. 已讀、靜音及電話紀錄採每人每階段；不遮掉常駐清單、不阻止下一階段、不算恢復。建立通知不等於已送達／已閱讀。
8. 所有自動警示改為可收合彙總橫幅與有數量上限的短暫通知；詳情由使用者主動開啟並隨時可關。API 失敗不阻止關閉。背景配單進度也不自動蓋住操作。
9. 本批交付站內通知與稽核，不接外部推播。後端授權檢查收件人；提醒不觸發新派工，也不擴大司機寫入權限。LLM 不參與時計或升級決策。

核准後，本 ADR 承接 ADR-309 的案件唯一性、確定性判斷、稽核與外部通知邊界，取代其派工關案、全域靜音、查詢同步與強制彈窗條款；承接 ADR-324 的物理時計、API 與 KPI，僅修訂無法確認恢復時的關案行為。ADR-325～328 的保存窗口／獨立 worker／專用庫／快照責任繼續適用。

## 理由與判準

使用者要追蹤「問題還沒解除多久」，有派單只代表有人承辦。保留兩種時計可同時衡量站点延誤與任務責任，避免將派工前等待歸咎司機。資料未知不得當成功排除。分級催辦必須讓使用者仍能執行處理動作。

## 考慮過的替代方案

### 只增加 60 分鐘設定

改動小，但派工關案後仍收不到提醒，強制視窗仍阻塞，不足以滿足需求。

### 只在前端計時與去重

容易製作展示，但關頁、換人、跨瀏覽器與重啟不一致，不適合問責與追蹤。

### 以物理空滿時計取代所有案件

減少資料表，但丟失尚未空滿的最高緊急事件，並混淆提前預警與實際無車／無位時間，不採用。

### 新增外部佇列、推播及資料平台

可支援跨裝置離線送達，但需新的服務／成本／資安／部署選擇，本次站內功能先沿用既有技術；不靜默擴大。

## 影響與後果

- 優點：分派與恢復分開、耗時可追溯、責任對象明確、非阻塞操作。
- 代價：增加通知與每人已讀資料；未解除案件比舊版多，須分頁聚合。
- 舊資料：已派工關案不能全部重開；有連續物理時計與觀測才能接續，無證據標首次偵測。
- 未解決：本機 DB 無使用者看到的十張進行中任務，不能斷言那些任務的實際時差；需目標環境唯讀驗證。
- 雲端主庫保存：ADR-327 只涵蓋 service_clock.db，營運案件／通知的部署持久化須核實主庫掛載。新雲端儲存或掛載另走部署決策，本提案不授權部署。
- 關閉瀏覽器無法保證收到站內提醒；若需離線送達另提外部通知方案。

## 介面與相容性

任務時間補來源狀態，overview 回 server_now；緊急案件補觀測、承辦、責任與新鮮度。新增通知／每人已讀表及後端角色查詢。保留既有陣列端點 shape，具體欄位與迁移見設計文件第五節。保留 /alerts 分派任務頁，另加 /alert-tracking。新 migration 必須可重跑，歷史 action 保留。

## 資安與隱私

沿用受控 Demo 的後端身分驗證限制。司機只讀／已讀自己通知；管理操作仍需相應角色。查詢不接受前端自報 actor 覆蓋登入身分，不新增真實聯絡資訊、不呼叫簡訊或電話服務。

## 回復或取代方式

保留新增資料表與歷史，暫停通知工作流程可停止提醒；回復須前後端配套，不能把新事件套回舊版派工即關案邏輯。物理時計維持收集。後續調整以新 ADR supersede，本提案不刪除資料。

## 驗證方式

固定時間測試兩張不同指派時刻、同秒指派、跨時區、跨日、重送、長時間；事件測試派工／已讀不結束、恢復再開、stale／offline／缺站／亂序不誤關；通知測試門檻秒界、重送去重、轉派、角色隔離及靜音不遮下一階段。瀏覽器以 100 個同時超時案件與 API 失敗驗證派工／地圖／身分切換／關閉仍可操作。pytest／Node utility tests／build／diff-check 指令見設計文件。
