# ADR-330：人車值勤三態同步、任務看板重整與人類可讀編號

## 背景與問題

自動配單重新檢視時發現數個問題：

1. **顯示閒置卻配不出**：儀表板顯示「大夜班 109 閒置人力」，但一堆任務掛在緊急/次安排不派出。
   根因是**呈現層與可派池用兩套不同的狀態判斷**——`api/operators._apply_shift_duty` 把「當班未
   派工」算成 on_duty 閒置（顯示用），但 `providers` 的可派池直接讀 DB 原始 status，而 seed 的
   總部待命人員 DB status 是 off_duty，導致 `depot_standby_operators()`（舊判斷要求 on_duty）
   永遠回空，需總部載車的單派不到人。
2. **任務編號不可讀**：task_id 是 `TRIP-{uuid}`，無日期/班別/序號語意。
3. **儀表板任務追蹤冗餘**：已派單的站仍留在緊急/次安排清單，且另有「任務追蹤」分頁與進行中任務
   重複，資訊分散。
4. **進行中任務顯示雜亂**：任務卡垂直堆疊，缺「單起始至今」與「該站變空/滿到現在多久」兩種計時，
   也沒有一眼看清車/人/路線的版面。
5. **人力配置不易看**：資源分散在班別排班與車輛兩區，缺依類別（調度員/駐點員/調度車/預備車）的
   整齊分類。

## 決策

**A. 值勤三態單一真相（核心）**：新增 `core.shift.duty_status_of(operator)` 回三態
`busy`（有任務）/`on_duty`（閒置可派）/`off_duty`（未上班），與 `is_dispatchable()`（可派＝
on_duty）。判斷規則：有 current_task_id→busy；depot_standby→on_duty（不綁班別，隨時機動）；
有 shift 欄位看班別（當班→on_duty，否則 off_duty）；無 shift 欄位尊重 DB 明確 on_duty。
`providers`（可派池）與 `api/operators._apply_shift_duty`（顯示）**共用同一判斷**，讓「顯示閒置
的人＝自動配單派得到的人」。自動配單只派當班閒置人力（不再收 off_duty），總部待命恆可派。

**B. 人類可讀任務編號**：task_id 改 `{YYYYMMDD}-{班別}{三位流水}`（如 20260911-早001）。新增
`task_seq` 表（seq_key=日期-班別代碼，seq）+ `tasks_repo.next_task_id()` 在寫入交易內原子遞增；
`dispatch_confirmation._confirm` 改用它。冪等由既有 `confirmations_repo` 收據維持（同 draft 重送
先命中收據直接回傳，不產生第二編號）。tasks 加 shift 欄位。

**C. 儀表板收斂**：移除「任務追蹤」分頁；`dispatch_cache.get_recommendations` 用
`station_claim_map()` 即時過濾已被進行中任務認領的站，讓已派單的站立刻從緊急/次安排消失
（追蹤改到分派任務狀況頁）。

**D. 進行中任務看板**：分派任務狀況頁進行中任務改「左任務列表 + 右選中任務地圖 + 資源(車/人) +
逐站狀況」。兩種計時：任務卡旁＝`assigned_at` 起算（單起始至今）；站點旁＝`service_problems`
空滿時計 `opened_at` 起算（該站變空/滿到現在多久）。後端 `_attach_live_station_status` 把
service_problems 的 `opened_at`/`kind` 接進 task route。**所有計時一律用後端時間戳 + 前端只算
差值**，關閉頁面後端持續計時、重開不歸零。

**E. 人力配置視圖**：分派任務狀況頁加頂層切換（任務狀況 / 人力配置）。人力配置用顏色分類六類
資源：調度員(藍)/駐點員(青)/總部待命人(紫)/調度車(綠)/預備車(金)/總部待命車(紫)，每類顯示
閒置/任務中/未上班三態計數。

## 理由與判準

- **正確性/一致性**：狀態判斷收斂成單一函式，杜絕「兩套判斷」的結構性缺人，解決 109 閒置卻不派。
- **可觀測**：可讀編號 + 雙計時 + 顏色分類，調度員一眼看懂現況與落差。
- **低破壞**：三態判斷保留「無 shift 尊重 DB on_duty」相容既有測試與手動上班；編號冪等靠既有收據；
  service_problems 接線 try/except 包住（獨立時計庫拿不到不中斷 overview）。
- **持久計時**：計時靠後端時間戳（service_problems 存 DB/EFS、assigned_at 存 tasks），前端無狀態，
  符合「介面關掉雲端持續計時」。

## 考慮過的替代方案

### 讓 providers 直接改讀 _apply_shift_duty 後的資料

- 缺點：呈現層與資料層循環相依；provider 是後端內部可派池，不該依賴 API 呈現函式。
- 未採用：改為兩者共用 core.shift 的純判斷函式（無相依方向問題）。

### 任務編號用全域流水號（不分班別）

- 缺點：看不出班別；跨班連號不利現場辨識。
- 未採用：owner 要求日期+班別+當班流水。

## 影響與後果

### 正面

- 自動配單可派池與顯示一致，閒置人力真的派得出；編號可讀；任務/資源一目了然。

### 負面與代價

- 自動配單改成只派當班人力：若某班別完全無排班且無總部待命，該班不自動配（符合語意，但需確保
  排班資料完整）。
- 新增 task_seq 表與 tasks.shift 欄（migration，相容）。

### 尚未解決

- service_problems 為隊友獨立時計庫（EFS），本機 mock 無資料時站點緊急計時不顯示（不影響任務計時）。

## 介面與相容性

- **後端**：`core.shift.duty_status_of/is_dispatchable`；`providers` 三個 operator 池改用之；
  `api/operators._apply_shift_duty` 改用之。`tasks_repo.next_task_id`；`dispatch_confirmation`
  改用之；tasks 加 shift。`dispatch_cache.get_recommendations` 加 claim 過濾。
  `dispatch.py _attach_live_station_status` 加接 service_problems opened_at/kind。
  schema 加 task_seq 表、connection migration 加 tasks.shift。
- **前端**：DispatchSidePanel 移除任務追蹤分頁；DashboardPage 移除 track 分支；DispatchStatusPage
  進行中任務改左右看板 + 站況緊急計時 + 人力配置切換視圖。
- **相容性**：舊 TRIP- 編號的既有任務不受影響（只影響新建）；三態顯示值仍是 busy/on_duty/off_duty。

## 資安與隱私

- 無新增對外邊界；只讀既有站況/時計/任務。編號不含個資。

## 回復或取代方式

- 三態：改回 providers 讀 DB status 即回舊行為。編號：改回 draft_id.replace 即回 TRIP-。看板/切換
  為前端呈現，可獨立還原。以新 ADR supersede，不改本文件。

## 驗證方式

  next_task_id 編號格式驗證正確（早001/晚001/夜001、同班遞增）。
- 前端 `npm run build` 通過。
