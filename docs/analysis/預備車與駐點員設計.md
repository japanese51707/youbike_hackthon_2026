# 預備車與駐點員：歷史數據 + 系統設計

> 分析區間 2026-01 ~ 2026-06（六個月、1,583 站）。
> 產出資料：`docs/analysis/standby_reserve_plan.json`
> 產生腳本：`analysis_standby_reserve.py`
> 對應決策：ADR-336（**proposed，尚未核准**）

---

## 一、先講結論：這件事的核心不是「派車」，是「庫存」

直覺上「預備車」像是提早派一趟車。但只要往下推一步就會發現不是：

**如果預備車直接插進車柱，它十分鐘內就會被市民借走。**
早上七點半放十台進去，八點就空了，跟沒放一樣。

所以預備車只有在「**放在站上、但市民借不到**」的狀態下才有意義——
例如放在拖車／圍欄／鎖具裡，由**駐點員看管**。

這樣一來整個功能的本質是：

```
預備車 = 站上的一批「鎖住的庫存」
駐點員 = 那批庫存的閥門（站空→放車進柱；站滿→把車收出來）
總部車 = 尖峰前把庫存送過去、尖峰後把剩的收回來
```

想通這件事，後面所有的資料模型、排程、與既有系統的接法都會自己長出來。
沒想通的話，會做出一個「提早派車」的功能，然後上線第一天就發現車全被借光。

## 二、歷史數據怎麼說

### 判準（三關都要過）

| 關卡 | 定義 | 為什麼 |
|---|---|---|
| 熱門 | 該尖峰日均振幅（當日最高可借 − 最低可借）≥ 全市 P75 | 不忙的站空著也沒人受影響 |
| 反覆 | 同一星期幾 × 同一尖峰，出事日數 ≥ 50% | **只有反覆發生才值得每天提前佈車**；偶發的交給既有緊急派工 |
| 樣本 | 該星期幾至少 8 天觀測 | 避免拿三天的巧合當規律 |

再加一道**排除**：全時段空站率 ≥ 35% 的站不進名單。

### 排除掉的 9 站（重要）

```
三貂嶺隧道(金字橋) 51.8%   牡丹車站 51.7%   翡翠灣停車場 50.1%
野柳地質公園 49.8%         淺水灣 49.8%      猴硐火車站 49.6%
雙溪車站 49.5%             白沙灣 49.5%      興華公園 47.1%
```

這幾站一開始在「反覆率 100%」的榜首，但它們**一天有一半時間是空的**——
不是尖峰才空，是**長期配置量就不夠**。對這種站佈預備車是每天派人去補一個漏水的桶子。
它們該走的是**基準配置量調整**，不是預備車。這條界線要在系統裡守住，
否則預備車會被這種站吃掉全部產能。

（其餘 184 站的全時段空站率中位數只有 **5.7%**，確認它們真的是「尖峰才空」。）

### 剩下的名單

| 尖峰 | 類型 | 站×星期組合 | 站數 |
|---|---|---|---|
| 早尖峰 07–09 | 全空風險 | 313 | 120 |
| 早尖峰 07–09 | 全滿風險 | 20 | 8 |
| 晚尖峰 17–19 | 全空風險 | 166 | 58 |

**行政區分布**：板橋 183、新莊 72、土城 45、三重 45、中和 37、新店 34、永和 26、淡水 19。

### 每日佈車負荷（這是最該先看的數字）

| 星期 | 尖峰 | 站數 | 預備車總數 | 約需車次（容量 15） |
|---|---|---|---|---|
| 一 | 早 | **103** | **948** | **64** |
| 一 | 晚 | 34 | 309 | 21 |
| 二 | 早 | 62 | 574 | 39 |
| 二 | 晚 | 38 | 360 | 24 |
| 三 | 早 | 63 | 541 | 37 |
| 三 | 晚 | 40 | 339 | 23 |
| 四 | 早 | 65 | 551 | 37 |
| 四 | 晚 | 24 | 226 | 16 |
| 五 | 早 | 17 | 130 | 9 |
| 五 | 晚 | 21 | 140 | 10 |
| 六 | 早／晚 | 1 / 5 | 3 / 27 | 1 / 2 |
| 日 | 早／晚 | 2 / 4 | 9 / 27 | 1 / 2 |

兩個要講清楚的事實：

1. **週一早上 64 車次是不可能的。** 目前總部待命車只有 5 台（`config.yaml: reserve.總站待命車數`）。
   所以這份名單**不能當成派工清單直接用**，它是**候選池**，必須配上每日上限與優先序。
   系統設計必須把「做不完」當成正常狀態來設計，而不是當成錯誤。
2. **週末幾乎不用做。** 這很合理——通勤潮沒了。排程要按星期幾開關，不要每天空轉。

備車量用**該時段淨流出的中位數**（不是平均），夾在 3~15 台。
用中位數是因為極端日會把平均拉高，備過頭等於**把車鎖死在一個站**——
那些車本來可以去別的地方，機會成本是實的。

## 三、系統設計：怎麼接才最流暢

原則只有一條：**不要造第二套派工引擎。** 能用既有的就用既有的。

好消息是這個專案裡已經有一半的零件了：

| 已經有的 | 在哪 | 這次怎麼用 |
|---|---|---|
| `role_type = 'stationed'` + `stationed_at` | `operators` 表（ADR-116） | 直接當駐點員與駐守站 |
| `seed_stationed_operators()` / 各區配額 | `db/operators_repo.py` | 已能按區、按班別配駐點員 |
| `reserve_bikes_for_station()`（含 `capped_by_space`） | `core/emergency.py`（ADR-118） | 算每站該放幾台、被現場空間夾住時自動收斂 |
| `plan_stationed_reserves()` | `core/emergency.py` | 骨架已在，改吃歷史名單而非即時週轉量 |
| DEPOT 車 + `list_standby()` | `db/vehicles_repo.py`（ADR-119） | 佈車批次的車源 |
| 自動配單背景執行緒 `_loop()` | `core/auto_dispatch.py` | **預備車排程掛在同一個 loop，不要開第三條 thread** |
| 配單診斷 `_tally()` / `stopped_because` | `core/auto_dispatch.py` | 「N 站由預備車自解」直接出現在既有儀表板 |

### 資料模型（新增最小集合）

```
reserve_plan                          ← 從歷史分析產出，後台可改
  station_id, weekday, peak, planned_qty, source('history'|'manual'), enabled

station_reserves                      ← 當日實況，單一真相
  date, station_id, peak,
  planned_qty, delivered_qty, released_qty, recalled_qty,
  custodian_operator_id,              ← 今天守這站的駐點員
  deliver_task_id, recall_task_id, status, updated_at
```

**站上現有預備車 `on_hand = delivered − released + recalled`。**
只有這一條公式，前端後端都算它，不要在任何地方另存一份數字——
兩份數字一定會不一致，而且一定是在 demo 當下不一致。

### 三個時點（全部掛在既有那條 loop 上）

**① 尖峰前 T 分鐘（預設 120，`config.yaml` 可調）**

```
取今天星期幾 × 尖峰 → reserve_plan 候選
  → 排除「今天該站已被一般配單覆蓋」的站
  → 排除「該區今天沒有駐點員在班」的站   ★ 沒人看管的預備車 = 送去給市民借
  → 依優先序排序：反覆率 × 建議備量 × 站柱數
  → 砍到每日上限（車次上限 = 可用 DEPOT 車 × 每車趟次）
  → 產生佈車批次「草稿」
```

**草稿，不是直接派工。** 這裡必須守 ADR-302：偵測與建議可以自動，
派車一律人工確認。週一早上砍掉的 40 幾車次也要列出來給調度員看，
標明「產能不足未佈署」——做不完要看得見，不要無聲吞掉。

佈車任務本身就是一張**普通 task**，站點卡片 action 用「放預備車」，
司機工作台不用改任何東西。

**② 尖峰中（站點變空）**

這是整個設計最值錢的一步。既有 `auto_dispatch.scan_once()` 掃到緊急站時，加一道前置：

```
if station_reserves.on_hand(station) > 0 and 該站駐點員在班:
      → 開一張「駐點員釋放預備車」輕任務（不用路線、不佔貨車）
      → 這站從貨車配單候選移除
      → _tally("由站上預備車自解")            ← 儀表板看得到
else:
      → 照既有流程走貨車配單
```

效果是：**預備車把一部分緊急事件從「要開車去救」降級成「站上有人放車進柱」**，
貨車產能被省下來給真正沒有預備車的站。這也正好解掉先前那個
「太多緊急單都顯示此區附近無足夠車源」的問題——把尖峰最可預期的那部分需求
從即時派工裡移走。

**③ 尖峰後（回收窗，預設尖峰結束 +60 分）**

```
on_hand 還有剩 → 併進回收任務（可搭既有回程路線，不要專程跑一趟）
滿站未處理    → 駐點員把車從柱上收進預備區（這就是「全滿風險」那 83 組合的用途）
```

**一定要有回收窗。** 沒有回收，預備車會一天一天沉澱在站上，
兩個禮拜後全市一半的機動車輛被鎖在 193 個站的圍欄裡。

### 一條不能忘的帳：水位別算兩次

預備車放在站上但市民借不到，所以它**不算在該站的可借車數裡**。
水位計算、LightGBM 特徵、負載守恆檢查（ADR-123）都必須把 `on_hand` 排除在 available 之外，
只在 `released` 的那一刻才轉進去。

漏掉這條，預測模型會看到一個不存在的高水位，然後不再對這站示警——
**等於花力氣佈了車，再親手把警報關掉。**

## 四、建議的實作順序

| 階段 | 內容 | 可獨立驗收 |
|---|---|---|
| 1 | `reserve_plan` / `station_reserves` schema + repo（冪等 migration） | 單元測試 |
| 2 | 匯入歷史名單 + 後台檢視／調整頁 | 看得到 193 站名單 |
| 3 | 尖峰前批次草稿（含上限與「產能不足」清單） | 調度員按確認就派得出去 |
| 4 | `auto_dispatch` 前置判斷 + 駐點員釋放任務 | 診斷面板出現「由預備車自解 N 站」 |
| 5 | 回收窗 + 滿站收車 | 隔天 on_hand 歸零 |
| 6 | 水位帳排除 `on_hand`（ADR-123 一致性） | 守恆測試 |

第 1~3 階段就能 demo「提前佈車」；第 4 階段才是真正把緊急單壓下來的那一步。

## 五、三個最容易翻車的地方（先寫下來）

1. **預備車被借走** — 若現場沒有實體隔離，這功能在營運上不成立。
   系統只能保證帳，保證不了鎖；這點要跟業主確認現場做法。
2. **週一早上做不完** — 64 車次 vs 5 台總部車。優先序與上限是必需品不是選配，
   而且「未佈署」清單要看得見。
3. **備過頭** — 中位數 + `capped_by_space` + 回收窗，三個一起才擋得住。
