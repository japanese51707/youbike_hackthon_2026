# 模擬引擎（Before/After 重放）概念備忘 — 未來功能，暫不實作

> 狀態：**概念記錄，暫不做**（owner 2026-09-10 決定：放到前端全做完、有餘裕再做）。
> 對應端點：`/api/v1/simulation/replay`（目前 mock）。

## 這是什麼

拿歷史某一天的資料，做「用我們系統 vs 沒用」的 Before/After 對照，把「系統有沒有用」變成可量化、可展示的數字（簡報最有說服力的一頁）。

## 為什麼有價值

1. 回答評審必問的「用了改善多少」——量化「空滿站少了幾次、改善 Z%」。
2. 把技術指標（MAE）翻譯成營運指標（少幾次無車可借/無位可還）。
3. 對準題目宗旨「縮短失衡到介入的時間差」——量化縮短了多少。

## 為什麼暫不做（代價）

1. **反事實很難**：「如果當時派了車，後來會怎樣」是模擬沒發生過的平行世界，需要假設（補車後需求怎麼演變），做不好會失真。
2. **易做成假的漂亮數字**：假設太寬鬆會做出「改善 90%」這種不可信數字，反傷公信力。
3. **要時間**：設計模擬邏輯 + 驗證合理性，非包端點等級。

## 建議做法（真要做時，用這個折衷版，不做完整反事實模擬）

**「單日事件 × 我們的預警召回」對照**（可信、工程量小）：
- **Before（真實，100% 可信）**：拿歷史某天，數「實際發生了幾次空站/滿站事件」。
- **After（保守，不宣稱救回）**：用我們的預測，數「其中有幾次我們能**提前 30-120 分鐘預警**」。
- 呈現：「這天發生 X 次空滿，我們的系統能在事發前抓到其中 Y 次（召回率）」。
- 這其實就是已有的**決策層召回率 84-92%**（見 ADR-002/dispatch analysis），只是套到「某一天的具體事件」呈現。

好處：不假裝救回（只講「能提前抓到」）、完全可信、複用既有召回邏輯、不需反事實假設。
