一句話：我們用六個月的歷史資料訓練出一個「猜未來車數」的公式，讓它每幾分鐘猜一次全市 1,583 站，把快出事的站排出先後順序，再自動組成一張張「先收車再放車」的派工單。

ELI5

想像全市 1,583 個水桶，有人一直在舀水、有人一直在倒水。以前的做法是等某個桶空了，路人打電話抱怨，才派人拿水去補。

我們做的是：先看六個月每個桶的水位變化，學會「這個桶星期一早上八點通常會被舀光」。然後每隔幾分鐘看一次現在水位，算出「再過半小時、一小時、兩小時，這桶大概剩多少水」。哪個桶最快見底、而且平常最多人用，就先派人去。

§01

模型端：LightGBM 到底怎麼學

這節回答「歷史資料丟進 LightGBM，它在做什麼」。簡報上只需要三張圖：一群樹、接力改錯、三條線。

ELI5：一群笨學生接力改考卷

第一個學生很笨，他對每一站都猜同一個數字，錯得一塌糊塗。
第二個學生不重新猜答案，他只負責猜第一個人錯了多少，然後把修正量加上去。
第三個學生再猜「前兩個人加起來還錯多少」……如此接力幾百輪。

每個學生都只是一棵很淺的決策樹（一連串 if／else，像「現在是不是尖峰？是→往左；這站海拔高不高？高→往左」）。單獨一棵蠢得可以，幾百棵疊起來就很準。這就是 Gradient Boosting，LightGBM 是它跑得最快的實作之一。

三個技術重點（給比較懂的評審聽）

直方圖分箱

連續數值（溫度、距離、lag）先切成離散的箱子再找切點。1,300 萬列資料因此能在幾分鐘內訓練完，不用逐點掃描。

Leaf-wise 長樹

每次只挑「能讓誤差降最多」的那一片葉子往下長，不是整層齊頭長。同樣的樹數下更準，但也更容易過擬合——所以要用 min_child_samples 夾住。

分位數回歸

改一下損失函數，同一組資料可以分別訓練出 P10／P50／P90 三個模型。這就是我們預測區間的來源——不是「估計值 ± 誤差」硬湊的。

我們實際訓練出什麼

不是一個模型，是 12 個 booster：4 個預測視野（30／60／90／120 分）× 3 個分位數（P10／P50／P90）。全部 1,583 站共用同一組模型，站與站的差異靠特徵表達（見 §02），不是訓練 1,583 個模型。

§02

45 個因子與消融試驗

因子分兩種角色，簡報上一定要講清楚，不然評審會問「天氣為什麼不直接讓它變緊急」。

預測因子決定「未來供需會怎樣」
餵進模型
預測結果（含區間）未來車數
緊急度因子決定「現在有多急」
不進模型，另外加權

天氣不會直接產生緊急度，而是：下雨 → 需求下降 → 預測改變 → 緊急度改變。兩者不能混在一起算。

消融試驗：怎麼證明某個因子有用

ELI5

消融＝把某個因子抽掉，重跑一次，看準度掉多少。掉很多＝這因子有用；沒差＝它只是佔記憶體。就像把食譜裡的一味調料拿掉，看菜還好不好吃。

我們踩過的一個坑值得寫進簡報，因為它展現方法論的嚴謹：

坑：78% 的答案是 0

預測目標是「車數的變化量 Δ」，而約 78% 的樣本 Δ＝0（大多數站大多數時候沒動靜）。用 MAE 做消融時，這一大堆 0 把所有因子的差異都稀釋掉，跑出來每個因子都「+0.00%」。

解法有二：(1) 消融改用 L2 探針放大差異；(2) 訓練時用流量加權，讓高周轉站的樣本權重更高——因為系統的價值本來就在那些站，不在一天借兩次的郊區站。

§03

異常點分析：從噪音裡挖出營運真相

這一節是整份簡報最有記憶點的地方——我們沒有任何調度紀錄，卻從存量曲線反推出整間公司的調度規模，還跟官方數字對上了。

ELI5

如果一個水桶在三十分鐘內少了三十公升，那不會是路人一瓢一瓢舀走的，一定是有人開卡車來載走。我們就是在六個月的資料裡找這種「不可能是自然借還」的跳動。

三步驟

① 標出異常點以「該站 × 平假日 × 時段」的自身分布為基準：偏離超過 3σ 且 單次變動量超過總車柱數的 50% → 標為疑似人為調度。全期約 5.1 萬筆，佔 0.38%。
② 配對成調度鏈同一行政區內，把「淨流出暴增（取車）」與 60 分鐘內、5 公里內的「淨流入暴增（放車）」配成一趟。數同時進行中的鏈條數 → 推估同時作業車數。
③ 跟官方數字對答案拿新北市交通局 2025-09-01 公開新聞稿的車隊規模交叉驗證。
45 台我們反推的尖峰同時作業車數
41 輛官方公布調度貨車數
480 次我們反推的每日調度次數
330–490官方 41 車 × 8–12 趟推估

兩個完全獨立的來源落在同一個數量級。這同時證明兩件事：異常偵測抓對了真實的調度行為；而系統有能力只靠公開存量資料就還原營運實況——這對還沒開放資料的縣市是可複製的。

異常點的第二個用途：清訓練資料

被標為「調度介入」的樣本，代表那段時間的車數變化不是使用者行為。如果照單全收餵進模型，模型會學到「這站下午三點會突然多 20 台車」這種假規律。所以訓練時把這些格子遮掉（is_rebalancing 逐視野判定），只學真實的借還節奏。

你提到但目前還沒做的：成因歸類

你的構想是把異常點再分類成「補車／天氣／活動造成」。目前 repo 只做到二元判定（是不是調度介入）＋規模反推，還沒有做成因歸因。這是加分項而非必要項——若時間允許，最快的做法是拿已有的天氣欄位與活動日期做交叉表，不需要新模型。

§04

從預測到緊急度：怎麼決定誰先派

預測出來是一堆數字，要變成「先去哪一站」需要兩層轉換：先分層，再排序。

第一層：規則引擎三層判斷

截斷 censored

預測下界已經穿透 0（或穿透滿柱）。代表已經或即將真的出事，一定排在警示層前面。

警示 warning

快空／快滿但還沒穿透。需要調度，但可以排在截斷層之後。

正常 normal

不進調度清單、不給分數。減少雜訊，調度員只看該看的。

第二層：緊急度分數 0–100

採分層打底 + 層內排序的結構，數學上保證截斷層一定大於警示層，不會因為權重亂調而出現「快空的站排在已空的站前面」。

第三層：補幾台？動態目標水位

ELI5

不要每站都補到一半滿。捷運站早尖峰補到一半，二十分鐘後又空了，等於白跑一趟。

正確做法是補到「撐得過接下來一小時」的水位：拿 60 分鐘的悲觀累積流量當依據，再用 80/20 護欄夾住避免爆掉。過了尖峰、流量趨緩，目標水位會自然回落到接近一半——不用另外寫規則。

安全緩衝也從固定 2 台改成總柱數的 12%：60 柱的大站留 7 台，20 柱的小站留 2 台，自動隨站大小縮放。

§05

調度怎麼排：三種班別，三種策略

同一套演算法不可能同時服務尖峰與大夜。我們依「當前時段」切成三種模式，並且對齊 YouBike 現行以行政區為單位的作業方式。

尖峰模式

折返跑 shuttle

早 07:30–09:30／晚 17:00–19:00。同行政區內選定一組站（例如 1 個滿站收車 + 2 個順路空站放車），這台車就固定在這組站之間循環，直到尖峰結束。

不追求一趟跑很多站，追求高頻循環消化人流。歷史估算早尖峰約 39 台、晚尖峰約 38 台同時作業。

離峰模式

任務型，效率最大化

尖峰前預佈 + 尖峰後至收班。一趟盡量裝滿 + 路徑短 + 依緊急度排序，讓「每公里搬運量」最大化。限本行政區內。

關鍵約束：尖峰前派的任務若預估完成時間會撞到尖峰起點，就不派——避免車卡在半路錯過佈署。

大夜模式

跨區大宗復原

22:00–翌日 06:30，唯一開放跨行政區的班別。趁人流少，用最少趟次把白天累積的跨區失衡一次搬回。

裝滿再跑、長距離可接受。夜間路況好、時間充裕。

一趟任務的定義

出發車在閒置位置
先取到滿站收車
載到接近車容量上限
後放依路徑順序
到數個空站放完
結案釋放車與人
回報當前位置

站數不固定，受車輛載運上限約束——載滿就開始放。這是你說的「先收車再放車，做完一輪就是一次任務」的系統化版本。

人與車的配置

你提的 (a) 已經落地了：離線腳本讀六個月官方資料，算出各行政區的調度工作量分數（標準化周轉量 ×2 ＋ 標準化空站次數 ＋ 標準化滿站次數，以周轉量為主導），用最大餘數法把 350 名調度員整數分配到各區、每區至少 1 人；30 名駐點員依各區「高周轉尖峰站（日均周轉量 ≥ 全市 P75）」數分配。

預備量能也在：全車隊固定保留 12% 為 standby，不參與常態派單，只由緊急救火觸發。加上熱門站的駐點預備車——備多少＝該站尖峰周轉量減去站上現有車，不是「柱數一半」（對大站會備過頭）。

§06

自動化派工的迴圈（你的第 5 點）

你描述的自動出單流程，跟 repo 目前的定案有一個重要分歧。這是全份文件最需要團隊拍板的一件事，先放在最前面。

必須先決定：全自動出單 vs 人在迴圈

你的口述 (b)(c)：系統偵測到緊急度 → 自動媒合車與人 → 自動出單 → 標記已派 → 繼續處理下一筆，全程不需人力介入。

repo 目前定案：系統自動算出草稿派工單（含預估路徑、預估時間、預估影響），但由後台管理人員預覽後按「確認」才成立。理由寫在決策紀錄裡：這是決策輔助工具，不是自動最佳化派工器；派錯了要有人負責。

建議的收斂方式（兩者其實可以共存）：保留自動組單的全部演算法——它就是你說的那套迴圈——但輸出停在「草稿」，後台一鍵確認。Demo 時這反而更強：評審會問「模型錯了怎麼辦」，「人在迴圈 + 全部門檻可調」是最好的答案，而全自動很難回答這題。

自動組單的迴圈（演算法本身，與你描述一致）

① 取最緊急的站從緊急度清單頂端開始（分數相同時，以流量信心當次要排序鍵）
② 媒合最近的閒置資源找車順序：該區閒置車 → 鄰近區閒置車 → 總站待命車。人員池＝該區閒置者 ＋ 總站待命人力。可派兩人（司機 ＋ 隨車）。
③ 串鄰近站看這站附近有沒有其他也需要調度的站（不必是最緊急的），順路一起做
④ 算先取後放路徑最近鄰排序 + 載運量切趟，且逐站檢查「到得了嗎、裝得下嗎」（路線載量守恆）
⑤ 佔用與標記該站標記已派單、該車與該人標記被此單佔用 → 下一輪不會被重複選中
⑥ 回到 ① 處理下一筆直到清單處理完或資源用盡

兩個時鐘（你的第 5 點 d，repo 做得比你想的更嚴謹）

任務時鐘

派工單一出就開始計時，追蹤這趟跑了多久、有沒有超出預估。用於績效與後續預估校準。

站點時鐘（案件追蹤）

某站第一次需要緊急調度時開始計時，追蹤「這站沒人管幾分鐘了」。30 分鐘再提示、45 分鐘再提示並電話聯絡。

這裡有一個很值得講的設計細節

站點時鐘不掛在警示上，掛在「案件」上。因為警示是每次查詢即時重算的——站況一恢復就整筆刪掉重建，alert_id 會換、計時會歸零，根本無法誠實回答「這站已經晾了多久」。

而且「已讀」不關案、不重置時鐘，只靜音一段時間。否則現場的均衡解就是「大家按已讀讓它安靜」，30／45 分鐘的升級永遠不會觸發。關案只認兩種確定性事件：已派工涵蓋該站站況已恢復——由系統判定，不由人宣告。

去重（你的第 5 點 d 後半）

你擔心的「下一輪資料進來，同一站還是緊急，會不會重複派單」已經有三道防線：(1) 站點標記已派單；(2) 同一站同時間最多只有一個未結案案件（資料庫層 partial unique index 強制）；(3) 車與人被該單佔用，不會出現在可用資源池。

另外還有一個你沒提到但已經做了的：自動偵測調度完成。背景輪詢即時站況，補車站的可借數上升且逼近目標、取車站下降且逼近目標，就自動標記該站完成、推進任務，最後一站完成時自動結案並釋放車與人。調度員不必逐站手動回報。判斷哲學很值得放進簡報：不管那批車是調度員搬的、還是剛好一批人還車造成的，只要站點已達目標水位，對該站而言調度需求就已消化。

§07

故障偵測（你的第 6 點 — 這塊還沒做）

目前 repo 只有「騎士主動通報」的收集端（累加數量、不觸發派工），沒有任何從資料自動推斷故障的機制。你這個想法是真的缺口，而且我認為它可以做得比你描述的更強。

ELI5

有些站看起來永遠有 3 台車，好像很健康。但那 3 台可能是壞車，沒人借得走——系統以為這站沒事，實際上使用者一台都騎不到。

怎麼抓？在本來應該很忙的站，如果車數連續很久完全不動，那不是健康，那是卡住了。

建議的判準（比單一訊號可靠）

你提的是「連續 30 分鐘數字不變」。我建議改成雙訊號交叉，因為 repo 裡已經有一個現成但沒被用起來的強訊號：

訊號 A｜死水位（你的想法）

在熱點站，可借車數連續 N 次觀測完全不變，且該站在該時段的歷史周轉量遠高於 0。

熱點站定義直接複用現成的：日均周轉量 ≥ 全市 P75（駐點站分派已經在用同一個門檻，不用另造一套）。

訊號 B｜車柱缺口（現成但沒用）

缺口 = 總柱數 − 可借車數 − 可還空位。柱子既沒車又不能還，通常就是壞柱或壞車卡位。

這個欄位資料裡本來就算得出來，且全期約 23.5% 的紀錄有缺口。目前只當弱特徵餵模型，沒拿來做警示。

A 且 B 同時成立 → 發「疑似故障」警示；只有 A 或只有 B → 降級為觀察，不跳警示。這樣誤判率會低很多，而且不需要任何新資料源。

三個實作上的注意事項
  • 別用「30 分鐘」當單位。歷史資料是 30 分鐘快照，30 分鐘只有 1–2 個點，判不出「連續不動」。要用即時源的頻率定義「連續 N 次觀測」——先確認官方即時 API 的更新頻率（通常 1–5 分鐘），再回推 N。
  • 故障警示不該自動觸發派工。它是「通知維修」不是「通知調度」，派車過去補車解決不了壞車。應該走獨立的通知流，顯示在單站詳情、任務卡片與後台，但不進緊急度清單。
  • 被標記的站要在預測端降級。那 3 台壞車不該算進「可借車數」。建議給該站掛一個「供給受限」旗標，讓規則引擎知道這站的可借數是假的——這跟我們已經在處理的「空站截斷會遮蔽真實需求」是同一類問題，可以沿用同一套邏輯。

另外，既有的騎士通報信箱可以當第三個訊號源：同一站短時間內多筆「車輛故障」通報，直接把該站的故障信心拉高。三個訊號都是免費的，不需要跟 YouBike 要新資料。

§08

誠實邊界：簡報一定要主動講的數字

這一節請隊友務必看完再做投影片。有一組數字已經作廢，如果還放上台，被評審追問會很難看。

⚠️ 已作廢的數字：不要再用

舊簡報素材寫的「MAE 1.51，比 baseline 4.29 改善 64.7%」不可再對外宣稱。原因：那個 baseline 定義不明且過弱（疑為「預測 Δ＝0」），且未確認防資料洩漏。用嚴格的 seasonal naive baseline（站 × 平假日 × 時段的歷史中位數）重跑後，改善幅度蒸發。

正確的說法（建議照抄上台）

「在平均誤差上，我們的模型跟一個很強的歷史查表 baseline 幾乎打平——因為 78% 的時候站點根本沒動靜，平均誤差這個指標被大量的 0 稀釋了。

但調度不是要預測平均，是要抓出真的會出事的站。在這個指標上，模型的召回率是 81–92%，baseline 只有 57–77%——而且視野拉得越長（90／120 分，也就是調度員實際趕得到的時間窗），差距越大。短期查表就夠，長期才需要模型，這正好對應實務需求。」

再補一句對準官方痛點：交通局要求業者「尖峰後 2 小時內恢復平衡」——我們的長視野預測 + 高召回，做的正是這件事。

其他要主動揭露的限制

  • 模擬重放有內生性。系統介入會改變使用者行為，重放模擬捕捉不到這個效應。Before／After 數字適合看方向，不宜精讀小數點。
  • 調度介入辨識是機率性推估（帶信心分數），不是確定性標記。官方 41 輛是 2025 年的數字，我們資料是 2026 年 1–6 月。
  • 沒有做 VRP 路線最佳化求解器，用的是啟發式（最近鄰 + 載量切趟）。這是刻意取捨——兩週要做完 16 個模組，最後會變成 16 個半成品。「刻意不做並講得出為什麼」本身就是工程判斷力的展現。
  • 預測區間覆蓋率約 78%，名目 80%，略低但已在可接受範圍；分位數交叉率 ≈ 0。
§09

缺口清單：你漏掉的與該補的

把你口述的六段跟 repo 現況逐條比對後，以下是需要動作的項目，依急迫度排序。

G1全自動出單 vs 人在迴圈，兩套說法並存今天要決定

你的第 5 點描述的是全自動派工，但架構決策已經定案為「系統出草稿、後台確認才成立」。隊友做簡報時若各講各的，上台會自相矛盾。

建議：對外統一講「系統自動組單 + 一鍵確認」。演算法完全是你那套，只是在最後加一個人類閘門——而這個閘門是面對「模型錯了怎麼辦」這題的最佳答案。

G2簡報素材裡的模型數字已作廢今天要改

簡報素材文件仍寫著「MAE 1.51／改善 64.7%」，但那組數字已被判定虛胖並正式作廢。任何人拿舊檔去做投影片都會踩雷。

建議：把 §08 的表與「正確說法」整段換進去，主打決策區召回 81–92% vs baseline 57–77%，不要主打 MAE。

G3故障偵測完全沒有落地缺口

你的第 6 點在 repo 裡沒有對應的決策紀錄或實作。現有的只是騎士通報收集端（累加數量、不觸發任何動作）。

建議：照 §07 的雙訊號判準寫一份決策紀錄。好消息是兩個訊號的資料都現成（車柱缺口欄位 + 熱點站 P75 門檻），實作成本不高，而且這是一個評審沒看過的亮點。

G4「連續 30 分鐘」在 30 分快照上判不出來定義問題

歷史資料是 30 分鐘一筆，30 分鐘內只有 1–2 個觀測點，無法支撐「連續不動」的判斷。

建議：先確認官方即時 API 的實際更新頻率，再把門檻改寫成「連續 N 次觀測」而非固定分鐘數，並放進 config.yaml 讓現場可調。

G5缺一個對外的 SLA 指標簡報加分

你設計了兩個時鐘，但沒有定義「多久算達標」。官方新聞稿明文要求業者「尖峰後 2 小時內恢復平衡」——這是現成的、官方認證的 KPI。

建議：把「2 小時」設成系統 SLA，儀表板直接顯示「本日達標率 XX%」。用主管機關自己的標準當計分板，說服力最強。

G6異常點成因歸類尚未做加分項

你想把異常點分成補車／天氣／活動造成，目前只有二元判定（是不是調度）。

建議：時間不夠就不做。若要做，用已有的天氣欄位 + 活動日期做交叉表即可，不需要新模型，半天內能出一張圖。

G7尖峰折返組的選法目前是啟發式已知取捨

折返組用「歷史尖峰流向 + 地理鄰近」組成，沒有最佳化求解。

建議：不要迴避，主動講。搭配 §08 的取捨表一起呈現，把它講成工程判斷而不是能力不足。
