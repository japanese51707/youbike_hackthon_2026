YouBike 調度架構審查

五層骨架與 spec 一致，方向是對的。問題出在圖漏掉了三個 spec 明列的模組、把 geo_batch 放錯層、把整份設計最核心的「參數三層」壓成一個方塊，而且底色與方塊同色，圖上等於只剩邊框在撐版面。已更新：動態觸發已完整落地（config、design.md §7、rule_engine.py 都換版並實跑驗證）。另外把七份文件互相對照了一遍，找到 39 處邏輯打架，根因是 api_contract.md 與 requirements.md 停在 8/19 沒跟上 8/31 的改動。

審查對象：design_dataflow.drawio 比對基準：.kiro/specs ×4 + steering 更新：動態觸發已落地 + 七份文件交叉檢查 2026-08-31

結論

分三個面向看：層次骨架、模組完整度、視覺可讀性。

層次骨架
正確

五層切分、A/B/C 分工歸屬、三條資料流敘述，都和 design.md §1.1 / §3 / §4 對得上。

模組完整度
缺 5 項

degradation、simulation/replay、FR-13 站點動態管理、data_source 介面、versioning 都沒出現在圖上。

視覺可讀性
需重做

分區底色與模組方塊同一個色值，方塊等於隱形；箭頭只連到分區框，看不出模組間的呼叫關係。

文件一致性
39 處

七份文件互相對照，12 處會出事、16 處要釐清、11 處小不一致。根因是兩份 spec 停在 8/19 沒跟上。

架構落差

依「會不會讓隊友照著圖做錯事」排序。

01參數三層被壓成一個方塊高

問題：圖上只有控制平面裡的「params 三層」一格。但 model_architecture.md 開宗明義說這是「整個系統最核心的設計決策」，而三層的來源其實散在三個地方——① 建置時的腳本、② 執行平面的 param_optimizer、③ 控制平面的 override_service——彼此還有覆寫優先序。

後果：看圖的人（含評審）看不出「一個模型 × 每站一組參數」這個最有說服力的設計，也看不出 ② 必須過人工確認才會生效。

修正：拉成獨立的參數子系統，由下往上畫 ① → ② → 閘門 → ③ → 生效參數，並用一條線標明生效參數是被 predictor 與 rule_engine 讀走的。
02geo_batch 放錯層高

問題：圖上把 geo_batch 畫在「執行平面」，和 predictor、urgency 並排。但 design.md §2 把它放在 backend/params/geo_batch.py，屬於參數建置，性質是「批次一次算」，不是每次請求都跑的無狀態運算。

後果：並排會讓人以為它在即時路徑上，可能被實作成每次預測都去查高程／POI。

修正：移進參數子系統的 ① 基礎參數，維持 B 主責的紫色，層歸屬和擁有者就都對了。
03箭頭只連分區框，不連模組高

問題：原圖五條主箭頭全部是 l1bg → l2bg 這種背景框對背景框，圖裡沒有任何一條 rule_engine → dispatcher 這種真正的呼叫關係。三條資料流只存在於底下那段文字裡。

後果：「資料流圖」實際上只表達了分層，沒表達流。閘門在哪一步介入、任務回報回到誰身上，都得回去讀文字。

修正：畫出控制平面的主鏈 rule_engine → dispatcher → 閘門 → task_manager，並補上兩條向上的回流：任務回報、緊急覆寫。
04缺 degradation：資料源掛掉沒有路徑中

問題：NFR-10 明列降級策略、design.md 也有 data/degradation.py，但圖上完全沒出現。現場 Demo 最可能出事的就是即時源，這條路徑不畫等於沒設計。

修正：放在資料源層底部，寫清楚「歷史同時段補值 ＋ 標記過期」，讓 NFR-5「失敗可見」在圖上看得到。
05缺 data_source 介面這個抽象本身中

問題：五個資料源並排，但真正的設計價值在「它們都實作同一個介面，換源不用改其他任何地方」。原圖只在分區標題括號裡寫了一句「介面可抽換」。

另外原圖漏了 YouBike 官方即時源——design.md 特別註明現場不確定是 TDX 還是官方源，這正是抽換設計要解決的情境。

修正：把介面畫成一個實體橫條，五個源全部往下匯入它，官方源補進來。
06缺 simulation/replay 與 FR-13 站點動態管理中

問題：API 層的 kpi 端點涵蓋 3.8 模擬重放，stations 端點涵蓋 3.19 新增／刪除站別，但下面對應的模組在圖上都不存在。FR-5 是 Demo 成效的主力，FR-13 又是這套「單一模型 + 外掛參數」設計最好的展示點。

修正：兩者都補進控制平面第二排；FR-13 直接把「新增 → 套鄰近站參數冷啟動」寫在框裡。
07儲存層畫在前端下面，位置說錯了故事低

問題：原圖把儲存壓成最底下一行文字，剛好在前端層正下方。前端層自己寫著「只透過 API 存取，不碰 DB」，視覺上卻是前端直接坐在資料庫上。

修正：移到右側當橫切欄，並補上 versioning 所在的 station_params 表與 prediction/artifacts 模型檔。
08config.yaml 已改為動態判斷版已處理

原本：根目錄 config.yaml 還停在死數字版本（空站危險_可借車數: 3、滿站危險_可還位數: 3），而 design.md §7 已改成動態判斷。

已確認的決策：以 design.md 的動態判斷為準。門檻不是固定台數，而是「當前存量 − 該站該時段的歷史淨流出 = 預測到達時存量」，再比對 trigger.安全緩衝_台數；低水位_借用率百分比 / 高水位_借用率百分比 只當保底輔助門檻。

已更新：config.yaml 直接取自 design.md §7 的完整定義（17 個設定區塊，已通過 YAML 驗證），檔頭寫明動態判斷的決策；舊版原封不動保留成 config.poc_v1.yaml。
09rule_engine.py 已遷移成動態版已處理

原本：PoC 版的條件 1～5 全是固定門檻比較（available <= 空站危險_可借車數），換 config 後還會直接 KeyError。

已改成：主判斷吃 預測區間下界當「預測到達存量」，比對 trigger.安全緩衝_台數；滿站側對稱用區間上界推「預測可還位下界」。觸發靈敏度 有了明確定義：調整後到達存量 = 當前存量 −（當前存量 − 下界）× 靈敏度。

順帶處理的矛盾：design.md §7 原本只寫「用歷史同時段淨流出算到達存量」，但 steering §5 與 design §3 都要求 rule_engine 吃區間下界。兩者若各自實作會變成「繞過模型用歷史均值減法」——跑起來不會報錯，只會在尖峰系統性漏觸發。已把 §7 註解與 config 檔頭都改寫成「吃 lower_bound，歷史淨流出只是沒有預測時的降級路徑」。

已驗證：用 6 月 2026-06-02 08:00 的 1554 站真實快照跑過，輸出 15 筆建議、觸發原因是完整句子。每筆都帶 判斷依據 欄（區間下界／歷史同時段淨流出（降級）／保底門檻），降級絕不偽裝成預測值（NFR-5）。舊版原封保留成 rule_engine.poc_v1.py。
09b實跑發現：預測檔只覆蓋 1／1554 站中

遷移後實跑，output/model_results/prediction_sample.csv 在該時間點只對上 1 站，其餘 1553 站全部走降級路徑。這不是遷移造成的，是 sample 檔本來就只有單站時間序列。

建議：B 產出全站預測時，把 station_id ×（時間點）的完整區間輸出成一份，rule_engine 才會走主判斷而不是降級。現在依據欄會誠實顯示「降級」，正好可以當成對接完成的驗收訊號。
10三個舊 key 已補回 design.md §7 再同步 config已處理

fleet.調度車數量: 20 與 fleet.響應時間_分鐘: 30 已補進 design.md §7（先改 spec 再同步 config，不在 config 偷加 spec 沒有的 key）；每站最大搬運量 由 fleet.每車容量 取代並註明。順手把「時段 = 30 分鐘」寫進註解，因為全套文件從沒定義過「時段」多長。

兩個新 key 都有實際消費者：響應時間_分鐘 成為觸發判斷的前瞻窗口（觸發原因會寫「30 分鐘後預測到達存量…」）；調度車數量 用在容量上限 min(每時段最大調度站數, 調度車數量 × 每趟最大站數)，不再是躺著沒人讀的設定。

會出事

12 項
C-01緊急度尺度自相矛盾：0~100 vs 8.7高
api_contract §4 / §2.12　calc_urgency() 回傳「0~100」、"urgency_score": 65 VS api_contract §2.3 範例　"priority_score": 8.7（明顯是 0~10 尺度）

後果：C 照 §2.3 做 mock 顯示 8.7／10，A 照 config.alert.warning_urgency: 60 判警示等級，B 回 0~100。整合當天所有站點都不會觸發 warning，因為 8.7 < 60。

建議：§2.3 範例改成 87.0，並註明 priority_score 與 urgency_score 同尺度 0~100。
C-02③ 覆寫要把緊急度拉滿，但沒有任何介面能把覆寫送進緊急度高
parameter_groups §緊急度因子　「即時人工覆寫（③層）｜緊急直接拉滿 100」 VS api_contract §4　calc_urgency(prediction, station_meta, arrival_minutes) — 三個參數都不含覆寫狀態 而且 design §1 / §3　urgency 屬「執行平面（無狀態）」、覆寫屬「控制平面（有狀態）」，override_service 明訂「不動模型參數」

後果：B 會說「我拿不到覆寫」，A 會說「我不能改你的 urgency」，最後只能在 dispatcher 裡偷加 if——決策邏輯就散到兩個模組，違反 design §3 的切法。

建議：二選一寫死：calc_urgency() 加第四個參數 override，或明訂「覆寫不進 urgency，只在 dispatcher 排序時當最前綴」。
C-03horizon_minutes 綁死「調度到達時間」，但有三個消費場景根本沒有調度員高
api_contract §2.2　「horizon_minutes：動態，不固定。等於『調度到達時間』…只在調度員要觸發新任務時才計算」 VS api_contract §2.5 + config.refresh_interval_sec: 60　每 60 秒對全市做一次警示掃描，先跑預測 + 緊急度 VS api_contract §2.12 / §8.8　歷史時間軸要為過去每個時間點每站預存 urgency_score

後果：全站警示掃描與歷史回填時，沒有調度員、沒有 arrival time，arrival_minutes 無值可填。同一個介面對三個呼叫端有三種語意，B 寫 predict() 時會卡住。

建議：拆成兩種 horizon——警示與歷史用 config 的固定 default_horizon_minutes，派任務時才用動態到達時間，並在 Prediction 加 horizon_source 標明。
C-04環境係數鎖死 [0,1]，「假日／活動需求上升」在數學上無法表達高
design §7 / config.yaml　「所有係數範圍 [0, 1]，最大 1（完全不影響需求）」，holiday_factor 三個值全是 1.0 VS parameter_groups 群組 4 / §4　「暫時調高該站的需求參數」「影響比越高 → 需求參數上調越多」 VS api_contract §2.7　"influence_factor": 1.8（> 1，直接違反同一份 config 宣告的值域）

後果：B 照值域規則實作，係數永遠只能往下打折。假日尖峰、跨年活動一律預測不足——正好是最需要調度準的時候。

建議：值域改為 [0, 3]（1.0 = 無影響），或明確分成「衰減係數 [0,1]」與「放大係數 [1,N]」兩類。
C-05target_level 的單位與存在與否，同一份文件有兩種說法高
api_contract §2.11　"target_level": 0.5（比例） VS design §7 / config　target.預設借用率百分比: 50（百分比） 而且 api_contract §3.12 回傳範例　params 只有 outflow_rate / inflow_rate / buffer_level——target_level 消失了

後果：FR-3 要求「即時水位 vs 動態目標水位」。C 呼叫 3.12 拿不到 target_level 就畫不出來；就算拿到，usage_rate 是 18.75（百分比）而 target_level 是 0.5（比例），直接比大小會讓所有站顯示滿載。

建議：統一為 0~1 比例（usage_rate 一起改），並補回 3.12 範例的 target_level。
C-06SQLite 三張表放不下至少四種端點狀態高
design §8　「三張主表」tasks / audit_logs / station_params VS api_contract §3.11 / §3.15 / §3.16　需要持久化的還有：警示已讀 acknowledged、機關 webhook 訂閱 callback_url、生效中活動 events、調度員 today_stats（疲勞管理要用）

後果：服務重啟後已讀警示全變未讀、機關訂閱消失、調度員今日工時歸零，fatigue.法定休息間隔小時: 4 直接失效。另外 tasks 表缺 estimated_travel_minutes、estimated_work_minutes、estimated_distance_km、assigned_at、route_map_url 五個 §2.4 欄位，GET /dispatch/tasks 回傳不出完整的 DispatchTask（FR-4 要顯示交通時間與油錢）。

建議：補 alerts / alert_subscriptions / events / operator_daily_stats 四張表，tasks 補齊五個欄位。
C-07事件影響計算沒有任何模組負責，是一條完整的死路高
api_contract §3.15　「系統自動換算影響半徑、找出範圍內站點、計算各站影響度」 VS design §2 / §3　B 的模組只有 predictor / urgency / features / rebalance_detector / param_optimizer / geo_batch；A 的 core 六個決策模組也沒有；api/events.py 被標為「對應端點的轉發」

後果：POST /events 進來之後沒有程式碼算 affected_stations，influence_factor 沒有生產者，config 的 event_radius / event_impact 三個參數沒有任何模組會讀。

建議：design §2/§3 新增 backend/prediction/event_impact.py（B），介面 compute_event_impact(event, stations) → affected_stations。
C-08存取控制整條沒落地，report 端點在資料上就無法驗證身分高
requirements NFR-8 / design §6.2　「調度員只能回報自己的任務」「權限一定在後端驗，前端不可信」 VS config.security　只有 allowed_origins 與 rate_limit_per_min，沒有任何角色設定；design §2 沒有 auth 模組 VS api_contract §3.6 / §3.13　report 的 body 只有 status / note / operator_location，沒有身分

後果：後端收到回報時無從得知是誰送的，「只能回報自己的任務」在 Schema 層面就做不到。POST /dispatch/confirm 這個人在迴圈的唯一閘門，任何人都能直接打，NFR-2 形同虛設。

建議：黑客松規模不必做 OAuth，但閘門要真的存在：加 header X-Operator-Id + config 角色對照表，report body 補 operator_id。
C-09「資料過期標記」沒有任何 Schema 欄位承載高
requirements NFR-10　「標記為『資料過期』，前端顯示提醒」「降級狀態必須明確標示」 VS api_contract §2.1 StationStatus　十一個欄位，沒有任何過期／降級旗標

後果：過期標記掛在哪個欄位沒人定義，C 不知道要讀什麼，降級時前端照樣顯示成即時真實資料——正好是 NFR-10 明文禁止的事。

建議：StationStatus 加 data_freshness: "live" | "stale" | "historical_fallback" 與 source_timestamp。
C-10任務狀態機缺「已指派、未開始」，動態轉派因此無法成立高
model_architecture ③-4 / api_contract §2.4　「已接緊急任務但尚未開始執行 → 可轉派；一旦開始執行 → 鎖定」 VS api_contract §2.4 狀態表　只有 pending（待派發）/ in_progress（執行中）/ … 沒有「已派發但未開始」

後果：已進佇列、assigned_operator 已填、但人還沒動身的緊急任務該填什麼？填 pending 會被 dispatcher 當成未派發再派一次；填 in_progress 則立刻鎖定、永遠不能轉派——FR-10 的動態轉派直接死掉。

建議：task_status 加 assigned，轉派條件明訂為 task_type == emergency AND task_status == assigned。
C-11天氣 API 串接同時指派給 C 和 A高
parameter_groups §實作分工提示　「群組 3（環境）：C — 串接天氣 API + 設定係數」 VS design §2 / §3　data/weather_api.py 與 api/weather.py 都在 A 名下，C 的表格只有 frontend/

後果：兩人都以為對方會做（或各做一份）。而且讓前端工程師去接氣象 API 也違反 design §1 的分層；weather_factor 五個係數的維護者因此無主。

建議：API 串接歸 A、係數校準歸 B，改掉 parameter_groups 的分工提示那行。
C-12車隊三個數字彼此推導不出可行的班表高
config.fleet / fatigue　每車容量 25、每趟最大站數 5、每時段最大調度站數 15、單次最大搬運量 150 VS api_contract §2.3 / §2.4　單站 quantity: 15、一趟三站 estimated_total_minutes: 45

後果：一趟 5 站若都補 15 台需要 75 台車，是每車容量的三倍——純補車路線上「每趟 5 站」不可能成立。而單趟 45 分鐘 > 時段 30 分鐘，一個時段內任何一車都跑不完一趟。「單次最大搬運量 150」的「單次」若指一趟，又和每車容量 25 直接衝突。

建議：「時段 = 30 分鐘」已寫進 config 註解，還需要註明「單次 = 單一輪班」；每趟最大站數 改由 每車容量 ÷ 平均 quantity 推導，或直接降為 2~3。

小不一致

11 項
  1. usage_rate 公式算不出範例值。§2.1 寫 available_bikes / total_docks，但範例 12/64 給的是 18.75——公式漏了 ×100（或範例該是 0.1875）。
  2. 低／高水位兩套數字。§2.1 的 status 用 <15% / >85%，config 保底門檻是 10% / 90%。會出現「地圖顯示綠色但清單建議調度」。
  3. 回報端點路徑兩處不同。design §4.2 寫 POST /tasks/{id}/report，api_contract 是 POST /dispatch/tasks/{task_id}/report。
  4. history_24h 這個參數不存在。§5 給 C 的約定提到它，但 §3.2 實際參數是 history_range=24h|7d。
  5. 天氣類別對不上。parameter_groups 寫「雷雨」，config 與 §2.10 是 heavy_rain（豪雨）——不同氣象條件。
  6. 同一時刻兩個空站數。§3.7 KPI 的 empty_rate: 5.66 × 1583 站約 90 站，§2.9 卻是 empty_stations: 45，兩者 timestamp 相同。
  7. Operator 範例的工時算不出來。§2.8 上班 06:00、total_work_minutes: 285，但 current_task.assigned_at 是 08:05；6 個任務 × 45 分鐘也塞不進 2 小時。拿這組 mock 測疲勞管理會誤判。
  8. steering 仍在示範已淘汰的寫法。§3 的「✅ 正確」範例是 config["trigger"]["空站危險_可借車數"]，但這個 key 已經不存在於 config.yaml。照抄會 KeyError，而且學到的正是想淘汰的做法。
  9. 成效表把未達標打勾。requirements §9「區間覆蓋率 目標 ~80%｜現況 ✅ 78.7%」——78.7 沒過 80，被問到會尷尬。
  10. Schema 版本落差。api_contract 標題還是「v2 草稿」、日期停在 8/19，但已被 design.md 當成定案引用。
  11. 「時段」長度過去從沒定義。已在這次 config 更新中補成「時段 = 30 分鐘（對齊資料解析度）」，parameter_groups 與 api_contract 尚未同步這個定義。
